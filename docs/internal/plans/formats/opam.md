# Plan: opam format

The HTTP opam repository, hosted, proxied and virtual: a `repo` file and an `index.tar.gz` the
client downloads whole on every `opam update`, opam files whose `url` sections name a source
archive by URL and checksum, and an archive cache addressed by checksum path relative to the
repository. opam 2.1.6 and opam 2.6.0 are the oracles on both paths.

## Context

opam sits in Tier 3 of `formats/catalogue.md` as the single-ecosystem family "opam". **Its build
is gated by `project-charter.md` AC9 and `catalogue.md` AC5**: no handler code for a Tier 3
ecosystem exists before every Tier 1 format has met its definition of done and the owner has
recorded a `continue` verdict at the charter's build step 8. This spec exists now because the
owner directed on 2026-09-26 that all 33 ecosystems be specced up front (the catalogue's "Every
ecosystem below is specced now; only building is gated"), so the gate decides what is built and
never what is written; a `shrink` verdict parks it.

**The Git relationship, stated because the authoring hint filed opam as Git-backed.** The
catalogue no longer has a Git-backed family (its resolved decision split that label into the
GOPROXY module proxy, the Swift package registry and the Julia Pkg server families), and opam is
not one of the three. The canonical opam repository, `ocaml/opam-repository`, is a Git
repository, and an opam client can be pointed at a Git URL, in which case it clones and diffs.
But opam.ocaml.org publishes the same content as an **HTTP repository** (`index.tar.gz` plus an
archive cache), which is the form an opam client of any 2.x version consumes over plain HTTP
with no VCS tool, and the only form with an archive cache. That is the registry-shaped path, and
the only one this spec serves.

The HTTP repository format has **no protocol specification beyond the opam Manual's
"Repositories" and "repo" sections and the client's own code**; there is no reference server,
only `opam admin index` and `opam admin cache`, which write files a static web server serves. So
the grounding is captured traffic first and source second, stated up front because the
constitution asks for evidence or silence:

Where the source and the captures disagree, the captures win, and the disagreement is recorded
because it would otherwise be built from the Manual. The Manual says that before opam 2.3 every
file in a version's `files/` directory is copied into the source tree and since 2.3 only those
listed in `extra-files`; with `extra-files` present, 2.1.6 and 2.6.0 both copied only the
listed file (captured, "XF-TREE: hello.sh listed.txt" on both).

Six things make this format worth a careful spec. **The index does not host the archives**: an
opam file names its source by an upstream URL and checksums, so "hosting" and "caching" have to
be defined rather than assumed. **The client silently falls back to the upstream source when
ours refuses**: an archive answered `403` by the repository's cache, or served with the wrong
bytes, was fetched from the opam file's `src` host and installed with exit 0 on both clients
(captured), so a registry that serves opam files as uploaded cannot enforce anything on an
archive. **The client verifies downloads only against checksums the index gave it**, so the
index is the root of trust and nothing on this wire is signed. **Every repository a client has
contributes versions to one union**, the solver taking a higher version from any of them
(captured). **An upstream `repo` file can move a client off this registry permanently** with a
`redirect` (captured on both clients). And **an opam file carries shell commands the client
runs**, which the registry must never evaluate.

## Blocking preconditions

**The handler interface re-open must complete before this handler starts**, as for every
handler (`format-handler-interface.md` AC8). opam is Tier 3, so the catalogue's Tier 1 gate (its
AC5) and the charter's breadth verdict (its AC9, build step 8) both precede it; the re-open is
recorded here anyway, from this side, because a gate enforced on one side only is enforced
nowhere.

**The shared signing and index service must be `planned` before Phase 1.** The index is a
write-triggered generated document produced by `signing-service.md`'s write-path runtime, which
the charter builds at step 7 as the production form of what the step 4a prototype learned. This
handler declares the optional `Indexer` interface and returns a generator from
`internal/format/opam/index` (`signing-service.md`, "The generator contract, and where a
generator lives", which names "opam's byte-range rewrite" among the format knowledge that lives
there); its profile declares no signing profile, so the service creates no key and records no
signature (its AC24). What this format requires is in Design ("What the signing and index service
must provide"), each item mapped onto that contract.

**The management API must be `planned` before Phase 2.** No opam client publishes over HTTP
(`opam publish` opens a pull request against a Git forge; `opam admin` writes a local
directory), so publishing, revising and removing are all operations of `management-api.md`,
placed on its closed kind vocabulary and reaching this handler through the optional `Operator`
interface (its resolved dispatch decision, was Q2), whose core the charter builds at step 2 and
completes at step 9. Until it lands, hosted repositories are populated only by the harness's
`state` seed path, which the index runtime covers like any write, so seeded versions come out
with their record set generated (`signing-service.md` AC21; `conformance-harness.md` AC18 and
AC24), which is how Phase 1's hosted cases run.

**The proxy-layer shapes this format asked for now exist.** An opam file declares an archive by
any of md5, sha256 and sha512, and the client checks all of them (Design, "Six client behaviours
that decide the design"); `proxy-cache.md`'s fetch-and-cache request carries a **declared digest
set**, every declared algorithm verified before commit, with an opam file declared in md5 and
sha512 as its own example, and an **ordered list of candidate sources**, tried in order past an
off-allowlist host, a not-found and a verification failure, with a rate limit stopping the
attempt, naming this spec's "the upstream's own cache, then each declared source host" ("Completion-only
mode and the verifier hook", its resolved completion-only decision, was Q15, AC20). The transport
half of the opam adapter this spec requested is `upstream-adapters.md`'s `https` adapter: an
`hosts` allowlist whose `own` role carries a per-source-host credential (its "Credential scoping
and the off-origin allowlist", naming this format beside `composer.md`), redirects followed inside
it, and the upstream's validators returned verbatim; the protocol half (revalidating
`index.tar.gz` with `If-None-Match`, reading the upstream `repo` file's `archive-mirrors`,
ignoring its `redirect`) stays in this handler's proxied path.

**The virtual phase needs the queue core.** A virtual repository's record set is re-merged by
`signing-service.md`'s `index.merge` job on `internal/async` (its "Virtual merges", AC19), so
Phase 4 waits on `async-operations.md`'s queue core, which the charter builds at the start of
step 4b. Every other write this format makes completes inside its request.
`artifact-verification.md` lists this format among those with nothing to verify (its "Nothing"
row): opam has no signature format (Design, "Signing, provenance and policy"), and checksum
verification is the proxy layer's declared digest set, not a verdict source.

## Scope

**In scope:**

- The HTTP repository read surface under the format-first mount `/opam/{repository}/`: `repo`,
  `index.tar.gz`, the archive cache `cache/{md5|sha256|sha512}/{xx}/{hash}`, and the registry's
  own archive route `archives/{name}.{version}/{key}/{basename}`; `GET` and `HEAD`.
- The index as a write-triggered, unsigned, repository-wide document: rendered by the shared
  service from the repository's version records, deterministically, never by running `opam
  admin`, with a regenerated `repo` file.
- Opam files served with every `url` and `extra-source` source rewritten to the registry's
  archive route and their `mirrors` and `swhid` removed, checksums untouched.
- A non-evaluating opam-file parser for hosted publishes and for upstream indexes: the registry
  never runs a command an opam file declares, never evaluates a filter, and never starts a
  subprocess over repository content.
- The hosted write path as `management-api.md` operations declared through `Operator`: publish a
  version with its opam file, its `files/` entries and every archive it names; revise a version's
  opam file with its archives unchanged; remove a version; remove a package; the write-boundary
  declaration `data-model.md` requires; immutable archives and retirement of removed versions
  through the core-held `Retirement` record.
- Name handling: case-preserving names with case-insensitive uniqueness, and the version grammar
  with `~` and `+`.
- Private reads by a registry token as the Basic password, which the client sends from URL
  userinfo; per-route addressed objects and the pattern-refusal case `auth.md` AC8 requires; the
  rendering of a shared policy refusal.
- The proxied path against opam.ocaml.org or any HTTP opam repository: the index regenerated from
  parsed upstream records and never relayed, conditional revalidation, archives fetched first
  from the upstream's own cache and then from allowlisted source hosts, verified against every
  declared checksum, pinned on first fetch where the upstream declared only md5, versions whose
  source declares no checksum left out (the resolved no-checksum decision below, was Q16),
  negative caching, and this format's rows of the removal table.
- Virtual repositories with per-name member-ordered resolution.
- The handler's `Capabilities()` declaration and repository rename (AC28).
- opam 2.1.6 and 2.6.0 as the conformance oracles on both paths.

**Out of scope for v1**, each with its reason, recorded because the interface spec's definition
of done requires the deliberately unimplemented surface to be named:

- **Git, rsync and local repository transports.** An opam client given a `git+https://` URL
  clones and diffs a VCS checkout, which has no archive cache and makes the registry a Git
  server rather than a package repository; opam.ocaml.org itself serves the HTTP form, and every
  2.x client consumes it (Context).
- **The opam 1.x surface**: `urls.txt`, per-file fetches, the `compilers/` tree, the `version`
  file. No 2.x client requested any of them (captured: an update is one `index.tar.gz` request),
  and opam.ocaml.org's own `repo` file redirects clients below 2.0 to frozen trees.
- **Per-file routes** (`packages/{name}/{name}.{version}/opam` and `files/...`). No captured
  client requested one; every opam file reaches the client inside `index.tar.gz`.
- **`opam publish` and any Git-forge pull-request workflow.** It targets a Git forge, not a
  registry protocol; the registry's publish is the management operation.
- **Repository signing through `repository-validation-command` and trust anchors.** The hook
  runs a user-supplied command against the repository, no signature format is standardised, and
  no deployment exists to be compatible with (opam.ocaml.org serves no signature; `index.tar.gz.sig`
  answers `404`).
- **Serving versions whose source is a VCS URL.** A branch-tracking source has no checksum and no
  bytes the registry can hold, so it is refused on hosted publish and omitted from proxied
  indexes (the resolved VCS-source decision below).
- **Operator-authored `announce` and `redirect` in a hosted `repo` file.** No workflow needs them,
  and `redirect` is the field this spec exists to keep off the wire.
- **opam.ocaml.org as a preconfigured upstream** (the resolved preconfigured-upstream decision
  below): user-configured in v1, for sequencing.

## Design

### The wire surface, as captured

Every path hangs off the repository URL the client is given,
`https://{host}/opam/{repository}`, format-first per `format-handler-interface.md`'s resolved
URL-shape decision. A client adds it with `opam repository add {name} {url}` or `opam init
{name} {url}`, and reads it through its HTTP backend.

| Surface | Shape, as both pinned clients send it |
|---|---|
| Index | `GET {base}/index.tar.gz` on `opam init`, `opam repository add` and every `opam update`, with no conditional header, answered in full each time; the client extracts it (or keeps it as a tarball) and diffs it against its previous copy itself, printing "no changes from {url}" when equal (captured). Nothing else is requested for the repository: not `repo`, which the client reads from inside the tarball, not `urls.txt`, not `version` |
| Archive by checksum | `GET {base}/{mirror}/{alg}/{xx}/{hash}` for each `archive-mirrors` entry of the repository's `repo` file (a relative entry resolved against `{base}`, an absolute one used as given, captured for both), where `{alg}` and `{hash}` are the **first** checksum the opam file lists: `cache/md5/62/62c6...` for a file listing md5 first, `cache/sha256/f5/f51b...` for one listing sha256 only (captured). One request per distinct source; 2.6.0 fetched one archive once for four packages sharing its `url`, where 2.1.6 fetched it per package (captured) |
| Archive by URL | On any failure of every mirror, `GET` the opam file's `url` `src`, then each of its `mirrors`, with no credential unless the URL carries one (captured) |
| Extra source | Each `extra-source` is fetched the same way, by its own first checksum and then its `src` (captured: `cache/sha256/22/2284...` for `extra.patch`) |
| Headers | `User-Agent: opam/2.1.6` or `opam/2.6.0`, `Accept: */*`, nothing else; no `Accept-Encoding`, no `HEAD`, no conditional request anywhere (captured). The download tool is `curl` with `-L`, so a redirect is followed (`opamDownload.ml`, `curl_args`) |
| Error rendering | Only the status: "Could not update repository "team": ... code 403 while downloading .../index.tar.gz" and "Failed to get sources of hello.1.1: HTTP error code 403" on 2.6.0, "curl error code 403" on 2.1.6; no body is ever shown (captured) |

**The two versions agree on the wire** for every route, path spelling and status handling above.
They differ in the order of archive mirrors, in how shared downloads are grouped, in error
wording, and in `extra-files` semantics per the Manual, which the rule below makes irrelevant.

**The one behaviour that changed at 2.2.** A global `archive-mirrors` in the opam root's
`config` is tried **after** the repository's own mirrors by 2.1.6 (`repo_cache @ global_cache`
in its `active_caches`; captured: no request to the global mirror while the repository's cache
answered) and **before** them by 2.2.1, 2.3.0, 2.4.1, 2.5.2 and 2.6.0 (`global_cache @
repo_cache`; captured: the global mirror's `404` preceded the repository's `200` on each). The
official `ocaml/opam` images configure `archive-mirrors: "https://opam.ocaml.org/cache"`
globally (captured in the pinned image's root `config`), so a 2.6.0 client in them asks
opam.ocaml.org for every archive first, whatever repository it installs from.

### Six client behaviours that decide the design

**The client falls back silently to the upstream source.** With the repository's cache answering
`403` for an archive, both clients fetched it from the opam file's `src` host and installed it,
exit 0, printing only "retrieved hello.1.1 (http://opamcap-src:8080/src/hello-1.1.tar.gz)"
(captured). With the cache serving the wrong bytes, both printed "Conflicting file hashes, or
broken or compromised cache!" with every checksum marked MISMATCH and then did the same
(captured). Only when the cache and every source failed did the install fail, exit 40 (captured).
In the source the order is: the client's own download cache, then every archive mirror in turn,
then `src` and each of `mirrors` (`pull_tree_t`, `pull_from_mirrors`), then, where the user
enabled `swh-fallback` and the opam file carries a `swhid`, Software Heritage after a prompt
(`download_package_source_t`, `archive_fallback`). A registry that served opam files as
uploaded could therefore refuse nothing: every refusal would be a detour to github.com. This is
what decides the resolved source-rewrite decision below.

**What the client verifies.** An archive from a mirror must match **every** checksum its opam file
lists (`fetch_from_cache`: `List.for_all ... checksums`; captured, both checksums marked
MISMATCH); an archive from a source URL is checked against the first while downloading ("Bad
checksum, expected md5=62c6...", captured on both, exit 40) and against all before it is added
to the client's download cache (`validate_and_add_to_cache`). A `url` with no checksum is not
checked at all, and a VCS source cannot be ("can't check directory checksum"). **The checksums
come from the index this registry served**, which nothing signs: the client's verification binds
an archive to the index, never the index to anyone. So the registry is the root of trust for
everything installed through it, and what it binds (Design, "What the registry verifies") is
what the client can rely on.

**A rollback is visible at the next update.** After the index lost hello 1.1, `opam update`
reported "synchronised", `opam list --available` showed only 1.0, and `opam upgrade` performed
"downgrade hello 1.1 to 1.0" (with "[no longer available]" on 2.6.0), on both clients (captured).
After an index lost a package entirely, `opam upgrade` removed it and `opam install` failed "No
package named app found.", exit 5 (captured). Because the index is fetched whole with no
conditional request, **no freshness header decides this**; the pointer-scoped `Last-Modified`
that `debian.md`, `conan.md`, `hackage.md` and `luarocks.md` needed is not needed here (Design,
"Freshness headers").

**Every configured repository contributes to one union.** With a second repository holding hello
9.9, both clients installed 9.9 whichever repository was ranked first (captured with `opam
repository add` at rank 1 and at rank 2): rank decides only which repository supplies the
definition of a given `name.version` (the Manual: "the definition of a given version of a package
being taken from the repository with the lowest index where it is found"). That is the
dependency-confusion shape, and `opam init` adds opam.ocaml.org as `default` unless told
otherwise. The operator documentation therefore says to use a virtual repository as the only
configured repository (Design, "Virtual repositories").

**An index refusal leaves the old state in use.** `opam init` against an index answered `401`,
`403` or `404` failed "Initial download of repository failed", exit 40 (captured); `opam update`
against one answered `401`, `403`, `404` or `500` (the last retried four times) failed exit 40,
and the next `opam install` then succeeded from the previously downloaded index (captured on
both). So a refused or unreachable index is not a way to withdraw anything already seen.

**An upstream `repo` file can steer the client.** A `redirect` entry made both clients print
"The repository 'team' will be *permanently* redirected to ..." and rewrite their configured URL,
still in place after the next update (captured); an `announce` entry was printed beside the
repository's URL; an absolute `archive-mirrors` entry sent the archive request to another host
(captured). So a proxied `repo` file is never relayed (the resolved repo-file decision below).

### What hosting and caching mean

Per the resolved hosting decision below, **a hosted repository holds every archive its opam files
name.** A publish carries the opam file and one archive for its `url` and for each
`extra-source`; the handler verifies each archive against every checksum the opam file declares
before any byte is committed, so a hosted version's index entry and its archives land together
and the version installs with no host but the registry reachable. That is what makes hosting
meaningful for opam: an index-only repository whose sources stay on github.com is a
configuration file, not an artifact repository, and it could neither be air-gapped nor enforce a
policy.

**Caching on the proxied path** is the same thing arrived at by fetch: the index is regenerated
from the upstream's records, and each archive becomes a `File` in the remote repository the first
time a client asks for it, fetched from the upstream repository's own archive cache and, on a
miss, from the source hosts the operator allows, verified exactly as a hosted archive is.

**How the archive cache relates to the CAS**, per the resolved cache-mapping decision below: every
archive is one `Blob` keyed by the CAS digest of its bytes, like every blob in this registry. The
md5, sha256 and sha512 of an archive are **metadata aliases** recorded in its version's document
at ingest, never storage keys. The `cache/{alg}/{xx}/{hash}` route is a lookup from `(alg, hash)`
to a `File` through an alias map the shared service keeps beside the index records; it answers
only hashes the repository's current index declares, whatever algorithm the opam file listed
first, because the client asks by the first-listed checksum and two versions may list the same
archive's hashes in a different order (captured: 2.1.6 asked by sha256 for one package and by md5
for another holding the same archive). A hash the index does not declare answers `404`, so the
route is never a probe of the CAS or of another repository's content.

### Serving opam files that cannot leave the registry

Per the resolved source-rewrite decision below, every opam file the registry serves is the stored
opam file with exactly these changes, and no others:

- The `src` (or legacy `archive`) of its `url` section, and of each `extra-source` section, is
  replaced by an absolute URL of the registry's own archive route,
  `{base}/archives/{name}.{version}/{key}/{basename}`, where `{base}` is `deployment.md`'s
  `server.public_url` joined with `/opam/{repository}` under the repository's current name, read
  through `Deps` as `npm.md`, `composer.md` and `chef.md` read it (a named input of
  `format-handler-interface.md`'s re-open) and inserted by the generator package at render time,
  never stored. `{key}` is `sha256-{hex}` or,
  absent a sha256, `sha512-{hex}` of the declared checksum, so a URL names exactly one set of
  bytes and a changed checksum is a new URL; on the proxied path, for a source the upstream
  declared no strong checksum for, it is `url-{hex}` of the sha256 of the upstream source URL.
  `{basename}` is the last path segment of the original source URL, kept because a source that is
  not an archive is copied into the build tree under that name (`opamSystem.ml` detects archives
  by magic bytes, so the name matters only for non-archives).
- The `mirrors` and `swhid` fields of those sections are removed.
- The `checksum` field is left exactly as it was, in the same order, so the client's verification
  and its first-checksum mirror path are unchanged.

The served `repo` file carries `archive-mirrors: "cache"`, which is what makes private
repositories work: the client resolves the relative mirror against the repository URL, including
its userinfo, so the cache request carries the Basic credential (captured: `Authorization: Basic`
on both the index and the cache request), while the rewritten source URL is absolute, carries no
userinfo, and is fetched anonymously (captured: `401` on the fallback with no `Authorization`).
So on a private repository the cache route serves, and the archive route is the terminal fallback
whose `401` makes a refusal at the cache final; on an anonymously readable repository the archive
route answers the same as the cache route. With both routes refusing, both clients failed the
install with exit 40 and **made no request to any other host** (captured against a repository
whose opam files had their sources rewritten to an archive path on the repository itself and whose
`repo` file kept `archive-mirrors: "cache"`, "Failed to get sources of hello.1.1: HTTP error code
403"; the fixture's path lacked the `{key}` segment, which changes nothing the client does with
it). The rewritten files parse identically on both clients apart from the source (captured with
`opam show --raw`).

What this leaves outside the registry's reach, stated for the operator documentation rather than
patched: a **global** `archive-mirrors` the user configured, which 2.2 and later try first
(captured), so a client in the official `ocaml/opam` images asks opam.ocaml.org before this
registry; and the client's own download cache, which served a reinstall with no request
(captured: "retrieved hello.1.0 (cached)"). The documented recipe is a fresh opam root with the
virtual repository as its only repository: a root made by `opam init` carries no global
`archive-mirrors` (captured), and on an existing root 2.6.0 removes one with `opam option
--global archive-mirrors=` ("Reverted field archive-mirrors", captured), while 2.1.6 refuses to
modify the field ("Field archive-mirrors is not modifiable", captured) but tries it only after the
repository's own.

### What the registry verifies

On hosted ingest, and where meaningful on every proxied fetch:

1. **The opam file is parsed, never evaluated** (Design, "Parsing an opam file"), and parses to
   exactly one `url` section at most, `extra-source` sections with distinct names, and an
   optional `extra-files` list; the legacy separate `url` and `descr` files in a version
   directory are refused on hosted publish (none exists on opam.ocaml.org, captured).
2. **Names and versions are the client's grammar.** A name matches `[A-Za-z0-9_+-]+` with at
   least one letter and a version `[A-Za-z0-9_+.~-]+` (`opamPackage.ml`: `Name.of_string`,
   `Version.of_string`); an opam file's own `name:` and `version:` fields, where present, equal
   the coordinate.
3. **Every archive matches every declared checksum**, and at least one declared checksum is
   sha256 or sha512 on hosted publish: md5 alone does not bind bytes, and a source with no
   checksum is one the client itself never checks. A VCS source is refused on hosted publish.
4. **`files/` entries are exactly the files `extra-files` lists, with matching checksums**, so the
   Manual's pre-2.3 "copy every file" and post-2.3 "copy the listed ones" produce the same tree.
5. **On a proxied fetch**, the same checksum rule binds an archive to the coordinate the upstream
   index declared; where the upstream declared no strong checksum, the first verified fetch pins
   the archive's CAS digest on its `File`, and a later fetch after eviction producing another
   digest is an integrity failure (the resolved proxied-archive decision below).

### Parsing an opam file

Per the resolved never-evaluate decision below, the registry reads an opam file with a parser of
the opam file format's grammar (values, lists, options, sections, and the `{ ... }` filter and
`%{...}%` interpolation syntax recognised as inert tokens) that builds a syntax tree and
**evaluates nothing**. It reads `name`, `version`, the `url` section (`src` or `archive`,
`checksum`, `mirrors`, `swhid`, `subpath`), `extra-source` sections, and `extra-files`; every
other field, including `build`, `install`, `remove`, `run-test`, `depends`, `available` and every
filter, is kept as bytes and never interpreted. The file is at most 1 MiB, valid UTF-8, and nested
within a fixed bound; anything else is refused on hosted publish and left out of a proxied index
with a divergence recorded.

The rewrite splices byte ranges the parser reports, so everything outside the replaced `src`
values and removed fields is served byte for byte, comments and formatting included, and a
property test requires both pinned clients to parse every served file to the same fields as the
stored file apart from the rewritten ones (AC3).

**Nothing runs.** No opam file is evaluated, no filter is computed, no `opam admin`, `tar`,
`gzip` or other process is started over repository content, and the index is built in process by
the shared service. An architecture test holds the handler package and the shared index service
to an import allowlist without `os/exec`, `syscall` process creation or cgo (AC4), on top of the
interface's depguard allowlist (`format-handler-interface.md` AC9). The commands in an opam file
run on the installing client, sandboxed there by opam's own `bwrap` wrapper where enabled; the
registry passes them through as it passes a tarball's contents, and says so in the operator
documentation.

### Mapping onto the shared model

The levels are exactly those `data-model.md` provides; no table is added.

- **`Package.name` is the opam name as first published**, case preserved. Removed versions are
  core-held `Retirement` records, not a set in any document (`data-model.md` AC35;
  `management-api.md`, "Retirement is core-held"). The repository-level document holds the set
  of case-folded names, which is what enforces case-insensitive uniqueness (the resolved name
  decision below).
- **`Version.version` is the opam version string**, exactly as published. The version-level
  document holds what the parser read and what ingest computed: for the `url` and each
  `extra-source`, the original source URL, the declared checksums in order, the `{key}` and
  `{basename}`, the md5, sha256 and sha512 of the archive bytes, and the byte ranges the rewrite
  splices; the `extra-files` list; and whether the version has been revised.
- **One `File` per artifact**: `opam` (the opam file exactly as published or revised),
  `files/{path}` for each `extra-files` entry, and `archives/{key}/{basename}` for the `url` and
  each `extra-source`, each `Blob` keyed by its CAS digest. Two versions naming the same archive
  share one blob (captured: four fixture packages shared one source).
- **A `remote` repository** holds, as its current document, the record set the generator's
  `FromUpstream` produced from the parsed upstream index (`signing-service.md`, "The proxied
  path", AC20), unsigned, carrying the cache-scoped freshness record (`data-model.md` AC44) and
  CAS-backed above the inline threshold (the fourth mark root, `storage-and-gc.md` AC16), with
  each upstream opam file's bytes as a CAS blob it declares; and each fetched archive as a `File`
  whose `RemoteFile` provenance records the candidate that succeeded (`proxy-cache.md`, "Candidate
  sources are tried in order"): the upstream's cache path relative to the `Upstream`, or an
  allowlisted source URL verbatim, as `composer.md` records off-origin dists.

### The index: a write-triggered rendering

Per the resolved index-generation decision below, `index.tar.gz` is **never written by a handler,
never produced by `opam admin`, and never relayed from an upstream**. The shared service keeps
one **record set** per repository, `{name.version: opam file digest, rewrite ranges, files/
entries, archive aliases}`, produced inside the write that changes it, and renders from it:

- **The tarball**: `repo` first, then for each name in byte order and each version in byte order,
  the directory entries, `packages/{name}/{name}.{version}/opam` with the source rewrite applied,
  and its `files/` entries. USTAR entries with modification time zero, owner and group zero, mode
  `0644` for files and `0755` for directories, no other entry type, gzip with no name and time
  zero. The same record set renders byte-identical bytes (measured: a deterministic rendering of
  opam.ocaml.org's 43,028 entries is 53,463,040 bytes of tar and 4,044,500 bytes of gzip, in
  under two seconds on this host with a scripting-language prototype).
- **The `repo` file**: exactly `opam-version: "2.0"`, `archive-mirrors: "cache"` and
  `stamp: "{hex}"`, the hex digest of the record set, served both inside the tarball and at
  `{base}/repo`. No `redirect`, no `announce`, no `upstream`, no `browse`.
- **The alias map** from `(alg, hash)` to the `File` for the cache route, derived from the same
  record set.

A rendering is memoised by the shared service keyed by the record set's digest, the base URL and
the repository's current name, and can be dropped and recomputed at any time, since it is not
snapshot state. Only a whole-document gzip is
rendered: a multi-member gzip assembled from per-package members would let a write recompress
one package, but measured 6,519,918 bytes against 4,044,500 for the same content, and the client
downloads the whole index on every update (captured).

**What the signing and index service must provide.** Stated so the dependency could not be
lost, and now mapped item by item onto `signing-service.md`'s generator contract:

1. **Unsigned generation** of the record set from the version-level records of every current
   version; nothing is signed and the service's signing half is not used. Met: a profile with no
   signing profile makes this format an unsigned consumer (its AC24).
2. **Regeneration inside the triggering write**, landing in the same completed logical write and
   the same snapshot, so no snapshot's index names an archive the snapshot does not hold, and two
   concurrent publishes both land. Met by the write-path runtime's pre-commit regeneration and its
   contention rule (its "The write path dispatches; the handler cannot forget" and "Contention:
   serialise per document, then retry", AC1, AC3).
3. **Incremental record-set cost**: a write touching one package reworks that package's records
   and copies the rest, so a publish into an opam.ocaml.org-sized repository does not re-read
   every version (AC18 holds the budget); the tarball itself is rendered whole on first request.
   Met for the record set by the generator's `Affects` and the untouched-key rule (its AC4).
4. **Storage as CAS-backed metadata above the inline threshold**. Met (its AC5;
   `storage-and-gc.md` AC16).
5. **The deterministic tar and gzip renderer with the byte-range rewrite** and the regenerated
   `repo` file; the handler never builds index bytes, which an architecture test enforces (AC4).
   Met by the generator package, which that spec quotes this criterion for. Not yet met: the
   tarball is **rendered on request** from the stored record set and memoised, and
   `signing-service.md`'s contract states a stored output per key and `ServeDocument` serving it,
   with no rendering a profile may declare to run on request; `luarocks.md` reported the same gap
   for its 36 renderings of one record set, and this format is its second consumer. The fallback,
   should that spec decline, is the rejected option B of the resolved index-generation decision
   (was Q5): the tarball stored per write.
6. **The alias map** for the cache route, and **the virtual merge**, per name in member order
   (below), re-run when a member's record set changes. Met: the alias map is part of the stored
   record set, and the merge is the generator's `Merge` run as the `index.merge` job (its
   "Virtual merges", AC19), with its coalescing window and staleness bound.
7. **The same generation on the proxied path** from records parsed out of the upstream index, so
   hosted, proxied and virtual repositories share one generator and one stored form. Met by
   `FromUpstream` (its "The proxied path", AC20, which names this format).

### Freshness headers

Because both clients fetch the index whole with no conditional header (captured), a pointer
change, a rollback included, is seen at the next `opam update` whatever the headers say. What the
headers must still get right is any HTTP cache between the two, and another registry proxying
this one, which revalidates. So the generator's profile declares the freshness rule `ETag` only,
the case `signing-service.md` names this format for ("Freshness scoped to the pointer"):
`index.tar.gz` and `repo` are served through `index.ServeDocument` with a strong `ETag` over the
rendered bytes, `Cache-Control: no-cache`, and **no `Last-Modified`**, so no comparison of times
can go backwards across a rollback, and `If-None-Match` matching the current `ETag` answers
`304`; the handler package sets neither header (`internal/format/freshness_boundary_test.go`,
its AC11). Archive routes carry the `ETag` the shared blob-serving path derives from the CAS
digest and no `Last-Modified`, since a URL's bytes never change and no client revalidates one.
`data-model.md`'s per-pointer freshness record (its AC36) exists for every pointer and is simply
not rendered into any signal this format serves, and on the proxied path the cache-scoped record
(its AC44) orders adopted revisions without being served either.

### The hosted write path, and what counts as a write

Nothing on the opam wire writes, so every hosted operation is an operation of the
registry-owned management API, `management-api.md`, with no binding, because no client route and
no reference API drives any of them. Each is one of that spec's closed kinds, declared through the
optional `Operator` interface (`Operations()` returning `publish`, `annotate`, `delete-version`
and `delete-package`; its "Dispatch: the optional `Operator` interface"). `Submit` refuses a
`remote` or `virtual` target `405` `repository-type` before authorization, evaluates every pair
`Authorize` reports through the central authorizer, checks the retirement set, and runs `Apply`
in one write transaction in which the index runtime regenerates the record set before commit, so
each operation is one completed logical write in one snapshot and records one `Operation`,
completed in the request (its "Every operation is one completed logical write"; `data-model.md`,
"Operations"). A refused operation leaves nothing. Each kind's trigger is verified by this
registry's integration tests and a `script`-driven conformance case (`management-api.md` AC24,
enforced by `conformance-harness.md` AC26), and its effect by the real client. This is PyPI's row
in `docs/internal/analysis/management-surfaces-and-the-oracle.md`, and the first format whose
**publish** is in it.

| Operation | Kind | What the operation carries | Effect a client sees | Action |
|---|---|---|---|---|
| Publish a version | `publish` | The opam file, each `files/` entry and one archive for the `url` and for each `extra-source`, each committed through an upload session, and the declared name and version (`management-api.md`, "Publish through the API") | After `opam update`, the version is available and `opam install` fetches every archive from this registry, matching every checksum | `push` on `{name}` |
| Revise a version's opam file | `annotate` | Name, version and a new opam file committed the same way, whose `url` and `extra-source` sections declare the same sources with the same checksums, and whose `extra-files` match the stored `files/` | After `opam update`, the new fields (a tightened dependency bound, a changed `available`) are what the solver sees; archives unchanged | `push` on `{name}` |
| Remove a version | `delete-version` | Name and version | The version leaves the index; its archive routes answer `404` unless another current version names the same archive; `opam upgrade` downgrades an installed copy (captured) | `delete` on `{name}` |
| Remove a package | `delete-package` | Name | Every version leaves the index; `opam upgrade` removes an installed copy and `opam install` fails "No package named ... found" (captured); the `Package` row stays | `delete` on `{name}` |

`management-api.md`'s reconciliation table carries opam's publish, revision and version deletion
but no package deletion; the `delete-package` kind exists in its vocabulary with exactly this
meaning, so this spec declares it and reports the missing row rather than dropping the operation.

The declaration `data-model.md` requires, per the resolved write-boundary decision below:

- **A publish is one completed logical write**: the version row, its document, its `opam` file,
  its `files/` entries, its archives and the regenerated record set in one snapshot. A refused
  publish writes nothing. `Apply` peeks the committed blobs and refuses `validation` (422) an
  unparseable opam file, a grammar violation, a missing archive, an archive failing any declared
  checksum, no strong checksum, a VCS source, an unlisted or mismatching `files/` entry, and a
  coordinate disagreeing with the opam file's own fields; a name equal to an existing one
  case-insensitively and spelled differently, and a version that exists, are refused `conflict`
  (409); a retired version is refused `retired` (409) by the shared write path.
- **A revision is one write** replacing the `opam` file and the version document; the previous
  opam file stays in retained snapshots and leaves the head. A revision declaring any different
  source, checksum or `files/` entry is refused `conflict` (409): archives are immutable,
  metadata is not (the resolved revision decision below), which is how opam-repository itself
  tightens bounds on released versions.
- **Archives are immutable and a removed version is retired.** A `delete-version` or
  `delete-package` returns the removed `{name}.{version}` coordinates in its `Outcome`, and
  `Submit` writes one core-held `Retirement` record per coordinate in the same transaction
  (`data-model.md` AC35; `management-api.md`, "Retirement is core-held"). A publish naming a
  retired `name.version` is then refused `retired` whatever its bytes, after the removal's
  snapshot is pruned and after a pointer is moved back across the removal, because the record is
  not snapshot content and no write carries it. A new version under the name publishes normally.
- **Each removal is one write**; a package removal is one write however many versions it removes.
- **All are synchronous**: `Apply` runs inline and the `Operation` completes in the request; no
  job is enqueued.
- **A proxied repository creates no snapshots**: arrival and revalidation are cache
  materialisation.

Two concurrent publishes of different versions or packages each regenerate the record set under
the runtime's per-document serialisation and both land; two concurrent publishes of one version
produce one success and one `conflict`. Removal rules apply the precedent rather than re-deciding
it: no blob-store object is deleted directly (`storage-and-gc.md` AC15), a removal of something
absent answers `not-found` (404), and removing a package's last version leaves the `Package` row
(`data-model.md` AC33).

A policy rule never refuses a publish. `supply-chain-policy.md` scans an artifact after ingest
and enforces at resolution ("Scanning is asynchronous; enforcement is synchronous"), so a
byte-dependent rule meets a hosted archive when a client resolves it, under the repository's
serve-or-refuse-until-scanned setting, never at the management API; this spec's earlier "a refusal
at publish answers `403`" is withdrawn in the 2026-09-28 reconciliation.

### Names: case preserved, unique case-insensitively

opam compares names case-sensitively for identity but orders them case-insensitively first
(`OpamStd.String.compare_case`), and both clients resolved `opam install acmetool` to the package
`AcmeTool` (captured). Two names differing only in case would therefore make a lowercase request
ambiguous, and would collide in an index extracted onto a case-insensitive filesystem. Per the
resolved name decision below, a name is stored and served exactly as first published, and a
publish of a name equal to an existing one case-insensitively but spelled differently is refused
`conflict` (409). Versions with `~` and `+` (375 on opam.ocaml.org) appear verbatim in paths, including the
archive route, with `+` never decoded as a space.

### Authentication: Basic from URL userinfo

The opam client has no credential mechanism of its own. What both pinned clients did with a
repository URL carrying userinfo is send `Authorization: Basic` **preemptively** on the index and
every cache request, with no challenge (captured), because the download tool is curl and the cache
URL is built from the repository URL. So the existing Basic form of `auth.md` suffices, with a
registry token as the password: the "Basic password" row of its "Presentation forms" table, a
universal form, which "URL userinfo arrives in"; this handler declares no route-scoped form.
`auth.md`'s client table still has no `opam` row, which this pass reports again (the auth half of
the consequences queue's Open item 29 was never applied). What follows, named rather than
discovered:

- **The client prints and stores the credential.** Both clients printed the token in "retrieved
  hello.1.1 (http://alice:s3cr3tTOKEN@.../cache)", in `opam repository list` and in "no changes
  from ...", and wrote it to the root's `repo/repos-config` and state cache (captured). The
  operator documentation recommends a `pull`-only token scoped to the one repository; no other
  credential path was captured on either client without a custom `download-command`.
- **Plaintext is refused before lookup**: userinfo over `http://` is refused identically for a
  valid and an invalid token, as `auth.md` AC27 requires.
- **The rewritten source URL carries no credential**, which is why the served `repo` file keeps
  `archive-mirrors: "cache"` (Design, "Serving opam files that cannot leave the registry").

**The challenge and the existence rule**, applying `auth.md` as written:

- A credential-less request to a repository that is not anonymously readable answers `401` with
  `WWW-Authenticate: Basic realm="..."` and `{"errors": [...]}`, byte-identical for a private and
  a missing repository (`auth.md` AC17); both clients print "code 401 while downloading ..."
  (captured).
- A rejected token answers `401` and is never served as anonymous (`auth.md` AC12).
- A valid token lacking `pull` answers `404`.

### Addressed objects and pattern scopes

`auth.md`'s pattern scopes narrow a credential within one repository by matching the object each
request addresses, and the format declares which object each route reports
(`format-handler-interface.md` AC12). Per the resolved addressed-object decision below:

| Route | Action | Object kind | Canonical object |
|---|---|---|---|
| `index.tar.gz`, `repo` | `pull` | none | - (the index enumerates every name; the `repo` route, which no client requests, is reported with it) |
| `archives/{name}.{version}/{key}/{basename}` | `pull` | named | `{name}` as stored |
| `cache/{alg}/{xx}/{hash}` | `pull` | content-addressed | the archive identified by the hash |
| Management publish and revision | `push` | named | the publish's name |
| Management removals | `delete` | named | the name |

A request whose path does not have one of these shapes makes `Scope(r)` return an error, which
denies it as an unauthorized request (`format-handler-interface.md` AC10). What that gives and
costs, applying `auth.md` rather than re-deciding it:

- **A patterned `pull` cannot resolve anything**, because resolution starts at the index, whose
  object is none: it enumerates every name, so it is not a descriptor under `auth.md`'s
  resolved name-free-document decision (was Q23), the limitation `helm.md` records for
  `index.yaml`. `opam update` fails and the client keeps its previous state (captured behaviour
  for any index refusal). A patterned `pull` reads in-pattern archives by their archive route
  through `curl`.
- **The cache route is content-addressed**, so under `auth.md` AC24 a patterned `pull` reads any
  archive whose hash it knows, the accepted cost `auth.md` records for content-addressed routes.
- **A pattern refusal is answered as absence**: `404` with `{"errors": ["Not found"]}`,
  indistinguishable from an archive that does not exist.
- **A patterned `push` publishes and revises in-pattern names only**; an out-of-pattern
  operation is refused `unauthorized` (403) with no snapshot, as `management-api.md` AC3 renders
  every management refusal of an object outside the pattern (the `404` pattern rendering above is
  the wire routes', where absence is the existence rule).

### Policy refusals on the wire

When a shared resolution call returns the typed refusal `supply-chain-policy.md` defines, for an
archive on either path, the handler answers `403` with `{"errors": ["{policy and rule, or the
signal}"]}` as `application/json` on both the cache route and the archive route, written through
the shared refusal writer `WriteRefusal(w, r, refusal, body)` in `internal/format`
(`format-handler-interface.md` AC14; `supply-chain-policy.md`, its resolved refusal-status-line
decision, was Q10), so the client's fallback from one to the other meets the same refusal and the
install fails with no request to any other host (captured shape). `403` rather than the existence
rule's `404`, because the caller is authorized and the content is what is refused. Per the
resolved policy-refusal decision below, **the index keeps listing a refused version**, the
no-elision precedent of `conda.md`, `debian.md`, `conan.md`, `chef.md` and `luarocks.md`: a
solver that selects it reaches the refusal rather than silently taking a lower version or another
repository's copy. The user sees only "HTTP error code 403" (2.6.0) or "curl error code 403"
(2.1.6), the code and never the phrase the writer puts in the status line nor the body (captured);
the operator documentation says so. The refusal holds because every URL a served document names
is this registry's, which `supply-chain-policy.md` records as this format's `holds` row ("When a
refusal binds, per format": "by rewrite") and generalises from this spec into the rule that the
registry regenerates every served document and owns every URL in it.

### Signing, provenance and policy

Nothing on this wire is signed: opam.ocaml.org serves no signature, and the client's only hook,
the repository validation command with trust anchors, runs a command the user supplies against
the repository, with no signature format for a server to produce (Scope). The only integrity the
ecosystem has is the archive checksums in the index, which this registry both declares (hosted)
and verifies before serving (both paths); the TLS connection to the registry is what protects the
index itself. No verdict source is needed from `artifact-verification.md`, which lists this
format among those with nothing to verify, and `storage-and-gc.md`'s read-path verification (its
AC21) keeps a storage alteration from reaching a client between the verified commit and the
serve.

**Advisory coverage exists.** OSV carries an opam ecosystem (Context), so coordinate-level rules
match `pkg:opam/{name}@{version}` against OSEC advisories and are accepted at configuration
(`supply-chain-policy.md` AC11 refuses only uncovered ecosystems). What matching requires is in
`supply-chain-policy.md`'s coverage table ("What the feed covers, per ecosystem", its AC17):
`ECOSYSTEM` ranges are ordered by opam's version comparison (`OpamVersionCompare`, Debian-style,
where `~` sorts before everything, so `1.0~rc1` is below `1.0`), one of the vendored orderings its
matcher carries. OSV has no
malicious-package (MAL) entries for opam, so the feed channel of the shared security-signal rule never condemns an
opam coordinate today, and the upstream carries no explicit security signal on the wire (a
removal from opam-repository is a Git commit, visible here only as a version leaving the index).
The byte-level cataloguer sees OCaml source trees; licence rules depend on its coverage of them,
which `supply-chain-policy.md` measures in its own Phase 1 and refuses at configuration where it
has none.

### The proxied path

The handler owns the request and classifies for the proxy layer's fetch-and-cache API per the
settled decisions in `proxy-cache.md`. The upstream is an HTTP opam repository base URL
(`https://opam.ocaml.org`, a static `opam admin` tree, or another registry) on
`upstream-adapters.md`'s `https` adapter, which refuses an `http://` root at configuration unless
the upstream sets `allow_http` and makes no request at configuration: an unreachable but
well-formed upstream is accepted (its AC22, AC23), and `management-api.md` makes no probe at
creation. The upstream index is therefore checked at the first request that needs it, the answer
`cargo.md` reached in its resolved sparse-only decision (was Q7 there): an index the bounded
reader or the parser cannot accept as a whole is never adopted, and that request answers `502`
naming the failure (AC24). An upstream credential, where one is needed, is an upstream credential
of the kind the upstream accepts with role `root`, presented by the adapter; the client's
credential is never forwarded.

| Route | Classification |
|---|---|
| `index.tar.gz`, `repo` | Mutable metadata with a TTL. The handler revalidates the upstream index with `If-None-Match` through the adapter, which returns the upstream's validators verbatim (opam.ocaml.org answers `304`, captured); on a change it downloads the whole index, the handler parses every entry into records, and the generator's `FromUpstream` regenerates the served record set, adopted as the remote's current document under the cache-scoped freshness record (`proxy-cache.md`, "Freshness of what a remote serves", AC22), and served through `ServeDocument` with the same `ETag`-only rule as a hosted index. An upstream index whose `Last-Modified` is older than the adopted revision's is not adopted (the removal table). **Upstream index and `repo` bytes are never served** |
| `cache/...`, `archives/...` | Immutable by URL: fetched once on first request, verified before commit, cached indefinitely |
| Management operations | `405` with problem type `repository-type` (`management-api.md`, "Hosted only") |

**Reading an upstream index** is bounded: at most a fixed decompressed size and entry count; only
regular files and directories under `packages/{name}/{name}.{version}/` plus `repo` and `version`
are read, and an entry with an absolute path, a `..` segment, a link or any other type is ignored
with a divergence recorded; each opam file goes through the same parser as a hosted publish.
The upstream `repo` file is read for `archive-mirrors` only; its `redirect`, `announce` and every
other field are ignored (the resolved repo-file decision below). An index that fails the bounds or
the tar grammar as a whole is an integrity failure: the previous records keep serving under
`proxy-cache.md`'s serve-stale rules and the operator is alerted. A version whose opam file fails
to parse, whose name or version fails the grammar, or whose source is a VCS URL (4 on
opam.ocaml.org, all branch-tracking compiler variants) is left out of the served index with a
divergence recorded (the resolved VCS-source decision below).

**Fetching an archive.** On a miss for a `(name.version, key)` the index declares, the handler
hands fetch-and-cache an **ordered candidate list** (`proxy-cache.md`, "Candidate sources are
tried in order"): each `archive-mirrors` entry of the upstream `repo` file at the path of the
declared first checksum (opam.ocaml.org's `cache/`, which answered all 100 sampled archives,
captured), then the original `src` and each `mirrors` entry. Every candidate host other than the
upstream root must be an entry of the upstream's `hosts` allowlist, this format's **source-host
allowlist** (the resolved proxied-archive decision below; `upstream-adapters.md`, "Credential
scoping and the off-origin allowlist"), each with role `none`, or `own` naming a per-host
credential: empty by default for an opam.ocaml.org upstream, since its cache holds the archives,
and configured by the operator otherwise. A candidate outside the allowlist makes no connection
and returns `HostNotAllowedError`, which moves to the next candidate; a not-found or a failed
verification also moves on; a `RateLimitError` stops the attempt. With no candidate left the route
answers `502`. Redirects are followed inside the adapter, within the allowlist only, and no
`Location` reaches a client (its AC7, AC8).

**Verification before commit.** Every candidate's body is streamed through the **declared digest
set** and committed only if it matches **every** checksum the upstream opam file declared
(`proxy-cache.md` AC20), the initiating client's connection aborted before its final bytes
otherwise and coalesced waiters served only from the CAS after the verified commit, per the
settled waiter rule. Where the upstream declared only md5 (2 url sections on opam.ocaml.org), the
md5 is the declared digest set of the first fetch, whose verified commit pins the CAS digest on
the `File`; a refetch after eviction declares that CAS digest beside the md5, so another digest is
an integrity failure. What that cannot catch is a tamper present on the first fetch of such an
archive, stated as the ecosystem's limit for the two files that declare nothing stronger. Where
the upstream declared **no checksum at all** (19 url sections), fetch-and-cache would refuse the
request, since it carries neither a digest nor a verifier, and no structural check binds a
source that may not even be an archive; per the resolved no-checksum decision below (was Q16),
such a version is left out of the served index with a divergence recorded, the rule a hosted
publish already applies and the treatment VCS sources receive.

- **Missing archives are negatively cached** with the short TTL; a `429` or `5xx` is never cached
  as absence (`proxy-cache.md` AC9).
- **The upstream index is large**: 4.1 MB compressed and 19,187 opam files on opam.ocaml.org,
  fetched only when the TTL has lapsed and usually answered `304`.

Upstream removal maps onto the event classes of `proxy-cache.md`'s "Upstream removal or
replacement", which lists opam-repository among the wires whose removals carry no reason; this is
opam's side of that contract, each row naming its class:

| Upstream event, as observed at revalidation | Classification |
|---|---|
| A new version, or a changed opam file whose sources and checksums are unchanged (opam-repository's routine bound tightening) | An **ordinary metadata change**, propagated at the next revalidation |
| A version's declared checksums or source change | An ordinary metadata change with a **divergence recorded**: the new checksums give a new `{key}` and a new archive URL, and the old archive keeps serving under its old URL until evicted, since opam-repository's convention is that released archives never change |
| A version or package vanishes from the upstream index | **Removal with no signal**: drop it from the proxied record set, since the index follows the upstream; keep serving cached archives by URL; record an operator-visible divergence and alert once. The wire carries no reason |
| An archive answers `404` at every candidate where it was declared | **Removal with no signal**: keep serving a cached copy; record a divergence |
| A fetched archive fails a declared checksum or a pinned digest | An **integrity failure at fetch**: never committed, no negative entry, a cached copy keeps serving, and the operator is alerted |
| The upstream index returned at revalidation carries a `Last-Modified` older than the adopted revision's | **Regression not adopted**: the cached record set keeps serving under its unchanged cache-scoped record and a divergence is recorded (`proxy-cache.md` AC22); a legitimate upstream rollback reaches clients through the operator's refresh (`management-api.md`'s `POST /api/v1/repositories/{name}/refresh`) |

Detection happens at revalidation, passively, per `proxy-cache.md`'s resolved passive-detection
decision (was Q12). **No row is an explicit security signal**: opam-repository removes a package
by commit with no marker on the wire, and OSV has no malicious-package opam entries, so the shared
security-signal rule applies as written and this ecosystem's gap is stated here rather than
patched per format.

### Virtual repositories

A virtual repository of format `opam` is possible: the index is unsigned, names no repository,
and every URL in it is one this registry renders. Per the resolved virtual-repository decision
below, resolution is **per package name, in member order**:

- **The index lists, for each name, the versions of the first member holding that name**, and
  nothing from later members under that name, whatever versions they hold. A hosted member placed
  before an opam.ocaml.org remote shadows the upstream's package of the same name entirely, so
  the captured union (a higher version in another repository winning) cannot occur for a client
  whose only repository is the virtual one. Case-insensitively equal names count as the same name.
- **Every source is rewritten to the virtual repository's own archive route**, and the archive
  and cache routes resolve in the member that supplied the name, so an archive never comes from a
  different member than the index entry that led to it.
- **The merge is the generator's `Merge`, run as the deferred `index.merge` job** on the shared
  runner (`signing-service.md`, "Virtual merges", AC19): enqueued by a member's write with the
  virtual as coalesce key, at the virtual's creation and on every member-list change, never on a
  request's path; it creates no snapshot, and the previous merged record set serves until the new
  one commits, a failed merge leaving it in place with an alert. A member's change therefore
  reaches the virtual within that spec's staleness bound, not inside the member's write. A remote
  member contributes its current record set, the `FromUpstream` output of its last adopted
  upstream index, and is re-merged when it adopts a new one. Two things that sentence does not
  settle are reported rather than invented here: adopting a remote revision is cache
  materialisation, not a write, so no pre-commit hook enqueues the merge (the trigger the
  consequences queue already asks `signing-service.md` to add for conda, Arch, Alpine and RPM);
  and a remote reached only through a virtual receives no request of its own, so nothing drives
  its TTL revalidation, and a freshly created remote contributes nothing until something fetches
  its upstream index. Until those land, the operator recipe warms a new remote once through its
  own URL.
- Every management operation against a virtual repository answers `405` with problem type
  `repository-type`.

The accepted cost: a private package shadows every upstream version of its name, so a team that
wants both must rename; the operator documentation says so beside the recipe (`opam init --bare
default https://{host}/opam/{virtual}`, or `opam repository set-url default ...` on an existing
root, with no other repository configured).

### Content negotiation and the other traps

- **Nothing is negotiated.** `index.tar.gz` is served `application/gzip`, `repo` as `text/plain`,
  archives as `application/octet-stream`, never with a `Content-Encoding` (no client sends
  `Accept-Encoding`, captured). No client reads `Content-Type`.
- **`HEAD`** answers every `GET` route with the same headers, although no pinned client sends one.
- **The routes are served, never redirected**, although curl follows redirects (`-L`), because a
  handler never opens storage directly and a redirect to another host would drop the userinfo
  credential.
- **`opam init` adds opam.ocaml.org unless told otherwise**, and the user's root may carry a
  global `archive-mirrors`; the operator documentation's recipe removes both (Design, "Serving
  opam files that cannot leave the registry").

### Conformance, the clients and the corpus

Two clients from one pinned image: opam 2.1.6 (`opam-2.1`) and opam 2.6.0 (`opam-2.6`) from
`docker.io/ocaml/opam@sha256:52cf759b3ae2463f0c11f0bd03c2db516d4d3630654fe19c5968a88e76982d4f`,
each run with a fresh `OPAMROOT`, `opam init --bare -n --disable-sandboxing` naming the repository
under test, and an empty switch; the image's 2.2.1 to 2.5.2 binaries are available to the
client-drift job. Fixtures install with `build` and `install` commands that need no OCaml
compiler, so a case takes seconds. The catalogue counts one ecosystem and no multiplier row.

Six assertion traps are recorded where the cases are written. **The exit code hides the
fallback**: an install succeeds from an upstream host after this registry refused (captured), so
every refusal and integrity case asserts at the network layer that no request reached any host
but this registry. **The image's own root configures a global mirror**, which 2.2 and later try
first, so a case never uses the image's default root. **The client's download cache hides the
server**: a reinstall made no request (captured), so each case uses a fresh root. **`opam init`
without `--bare` adds opam.ocaml.org and builds a compiler**, so every case passes `--bare`.
**A failed `opam update` leaves the old index in use** (captured), so a refusal case asserts the
update's exit code and message, not a later install. **Two stubs' request logs interleave**, so
transcripts are ordered by timestamp, not by source.

The recorded surface for the replay corpus, named now because a thin recording script yields a
thin specification: against opam.ocaml.org, a cold `opam init` and update, a conditional index
fetch, cache fetches under an md5, a sha256 and a sha512 path, a missing cache path; against the
reference (`opam admin index` and `opam admin cache` over a directory served statically), init,
update, install through the cache, install after a cache miss, and a private repository with
userinfo. Recording gates on the harness's redaction criterion (`conformance-harness.md` AC13);
URL userinfo and `Authorization` values are what the allowlist must name. Every deliberate
divergence from the reference goes on the recorded exception list before its flow is expected to
replay: rewritten sources with `mirrors` and `swhid` removed, the regenerated `repo` file
(`stamp` from the record set, no `announce` or `redirect`), deterministic tar and gzip metadata,
no `urls.txt` or `version`, no `Last-Modified` on the index, `Cache-Control: no-cache`, and JSON
error bodies where a static server sends HTML.

Every client container reaches only the case network (`conformance-harness.md` AC23, its resolved
client-confinement decision, was Q6); the source host a fallback case needs is a `hosts`
sub-entry of the upstream stand-in's `upstreams` entry, resolvable inside the client container,
so "no request reached any host but this registry" is observed at the inspecting proxy rather
than assumed.

### Capabilities and rename

`Capabilities()` declares proxy support `supported`, the reference implementation `available`
(`opam admin` over a static server), `Virtual: supported` and `Rename: supported`
(`format-handler-interface.md` AC13). Rename is supported under `repository-lifecycle.md`'s rule
for handlers whose served documents embed the name, which names this format among the URL
rewriters ("Renaming"): every rewritten source URL is inserted at render time under the
repository's current name and never stored, so a rename changes the served index at the next
request with no snapshot. The client-side cost is that spec's accepted one (its resolved
rename-alias decision, was Q2), in opam's shape: each client's root stores the repository URL it
was given, so `opam update` fails on the old name until `opam repository set-url` points it at
the new one. The case the harness requires of every format (`conformance/opam/rename_test.go`,
`repository-lifecycle.md` AC12, presence enforced by `conformance-harness.md` AC26) proves both
halves on both clients (AC28).

### Resolved: what hosting means (was Q1)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: a hosted repository holds
every archive its opam files name; a publish carries them, each verified against every declared
checksum, with a strong checksum required and VCS sources refused (Design, "What hosting and
caching mean", "What the registry verifies"; AC5).

The question: an opam file names its source by upstream URL and checksums, so a repository could
host only opam files and leave archives where they are.

**Recommendation:** A. Only a repository that holds the archives can be air-gapped, enforce policy
on bytes, or survive the source host disappearing, which is what an artifact repository is for.

| Option | You get | It costs |
|---|---|---|
| **A. Archives supplied with the publish** | Self-contained versions; no egress on the write path | A publisher mirroring someone else's package downloads and re-uploads it (a proxied remote and a freeze serve that case) |
| **B. Archives fetched from their sources at publish** | A publish of an opam file alone | Egress to arbitrary hosts from a hosted write, and a publish that fails when a third-party host does |
| **C. Index-only hosting** | The smallest write path | Installs leave the registry for every archive; nothing is enforceable (captured fallback) |

**Why this is yours:** it defines the product for this ecosystem.

Accepted cost: the re-upload for mirrored packages, and VCS-sourced packages unhostable.

### Resolved: serving sources that point at the registry (was Q2)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: every served opam file's
`url` and `extra-source` sources are rewritten to the registry's archive route with `mirrors` and
`swhid` removed and checksums untouched, and the served `repo` file keeps `archive-mirrors:
"cache"` (Design, "Serving opam files that cannot leave the registry"; AC3, AC13, AC16).

The question: both clients silently fetch from the opam file's source host when the repository's
cache refuses or serves wrong bytes (captured), so an opam file served as uploaded makes every
refusal a detour.

**Recommendation:** A. It is the only shape captured to hold a refusal with no request leaving
the registry, and keeping the relative cache mirror is what lets private repositories pass
userinfo credentials.

| Option | You get | It costs |
|---|---|---|
| **A. Rewrite sources; keep `archive-mirrors: "cache"`** | Refusals, offline mode and air-gapping hold; private repositories work | Served opam files differ from the published bytes in their source fields; the index depends on the external base URL |
| **B. Serve opam files verbatim with the cache mirror** | Byte-faithful opam files | Every refusal and every cache miss falls through to github.com (captured) |
| **C. Rewrite sources, no cache mirror** | One archive route | Private repositories cannot install: the absolute source URL carries no userinfo (captured `401`) |

**Why this is yours:** it modifies authors' metadata to keep a registry guarantee.

Accepted cost: the rewrite, its exception-list entries, and the loss of per-file Software Heritage
fallback for users who enabled it.

### Resolved: how the archive cache maps onto the CAS (was Q3)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: archives are blobs keyed
by the CAS digest; md5, sha256 and sha512 are aliases in the version document; the cache route
resolves an alias through a map the shared service derives from the index records and answers
only hashes the current index declares (Design, "What hosting and caching mean"; AC17).

**Recommendation:** A. The constitution keys blobs by digest only, the client asks by whichever
checksum an opam file lists first, and limiting the route to declared hashes keeps it from being
a probe of the store.

| Option | You get | It costs |
|---|---|---|
| **A. Alias lookup, declared hashes only** | One blob per archive; every algorithm served | An alias map in the record set |
| **B. Also proxy any hash to the upstream cache** | A general archive mirror | A route that fetches content no index vouches for, bound only by an md5 when the path says md5 |
| **C. Store under each algorithm** | Direct paths | Blobs keyed by something other than the CAS digest, which the constitution forbids |

**Why this is yours:** it sets what the cache route is allowed to answer.

Accepted cost: users who point a global `archive-mirrors` at this registry get only archives some
index here declares.

### Resolved: the registry never evaluates an opam file (was Q4)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: a bounded, non-evaluating
parser reads the fields the registry needs; no command, filter or interpolation is evaluated; no
process is started over repository content; an architecture test enforces it (Design, "Parsing an
opam file"; AC4). This follows `luarocks.md`'s never-execute rule.

**Recommendation:** A. opam files are declarative data whose commands only the client should run,
and the rewrite needs positions, not evaluation.

| Option | You get | It costs |
|---|---|---|
| **A. Parse only, in process** | No server-side execution surface | A Go parser of the opam grammar to maintain |
| **B. Validate with `opam lint` or `opam admin` in a sandbox** | The client's own reading | A subprocess and a sandbox on the write path, the surface `luarocks.md` exists to avoid |
| **C. Store opaque bytes, no parse** | Nothing to build | No source rewrite, so no enforceable refusal |

**Why this is yours:** it fixes a security property of the whole format.

Accepted cost: the parser and its equivalence test against both clients.

### Resolved: how the index is generated (was Q5)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: one stored record set per
repository, regenerated inside each write, from which the shared service renders a deterministic
whole-gzip `index.tar.gz` and `repo` on request, memoised by the record set's digest (Design, "The
index: a write-triggered rendering"; AC2, AC18).

**Recommendation:** A. One aggregation per write, a byte-stable rendering that can always be
recomputed, and the smallest download for a client that fetches the whole index on every update.

| Option | You get | It costs |
|---|---|---|
| **A. Record set stored; whole gzip rendered on request** | Smallest index (4.0 MB for opam.ocaml.org's content); a cache miss costs time, never correctness | A first request per record set pays the render |
| **B. Render and store the tarball in every write** | Pure stream copy on serve | A multi-megabyte CAS document per publish, most never requested |
| **C. Multi-member gzip assembled from per-package members** | A write recompresses one package | 6.5 MB instead of 4.0 MB for the same content, paid by every client update |

**Why this is yours:** it fixes the split of work between the shared service and the handler.

Accepted cost: the render on first request. Reconciled 2026-09-28: `signing-service.md` now owns
the generator this decision names, but its contract stores an output per key and states no
rendering run on request, the gap `luarocks.md` reported first; option B here is the fallback
should that spec decline it (Design, "What the signing and index service must provide", item 5).

### Resolved: revising a released version's opam file (was Q6)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: a revision may change any
field of a version's opam file except its sources, checksums and `extra-files`; archives are
immutable (Design, "The hosted write path"; AC8).

**Recommendation:** A. Tightening a released version's dependency bounds is how opam-repository
keeps old versions installable, and fixing sources and checksums keeps every archive URL bound to
one set of bytes.

| Option | You get | It costs |
|---|---|---|
| **A. Metadata revisable, archives immutable** | opam-repository's own workflow | A client with the version installed may be told its opam file changed |
| **B. Opam files immutable** | Simplest model | A broken bound can only be fixed by a new version |
| **C. Everything mutable** | Full freedom | One URL serving several byte sets over time |

**Why this is yours:** it decides whether released metadata can change.

Accepted cost: the revision operation in `management-api.md`, which places it as the `annotate`
kind under `push` in its reconciliation table.

### Resolved: write boundaries, immutability and retirement (was Q7)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: a publish, a revision and
each removal are one write each; a published `name.version` answers `409` on republish; a removed
one is retired (Design, "The hosted write path"; AC5, AC7, AC9, AC19).

**Recommendation:** A. It is the cross-format precedent, and opam's client caches archives by
checksum, so a coordinate returning with other bytes would be a silent inconsistency.

| Option | You get | It costs |
|---|---|---|
| **A. One write per operation; immutable; retired on removal** | One set of bytes per coordinate for the repository's life | A removed version cannot be republished |
| **B. Republish replaces** | Freedom to fix a release | A coordinate that means different bytes over time |

**Why this is yours:** it applies a cross-format rule to a format with no client publish.

Accepted cost: the retirement set, since the 2026-09-28 reconciliation `management-api.md`'s
core-held `Retirement` record written from each removal's `Outcome` (its resolved
retirement-placement decision, was Q3), so no write carries it; the `409` this record names is
`conflict` for an existing version and `retired` for a removed one.

### Resolved: name case (was Q8)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: names are stored as first
published and unique case-insensitively (Design, "Names"; AC11, AC26).

**Recommendation:** A. The client resolved a lowercase request to a mixed-case package (captured),
so two names differing in case would be ambiguous to it, while 68 live names use upper case.

| Option | You get | It costs |
|---|---|---|
| **A. Case preserved, case-insensitively unique** | Real names served as written; no ambiguity | A second spelling of a taken name is refused |
| **B. Case-sensitive, distinct names allowed** | Maximum freedom | Ambiguous lowercase installs and case-insensitive filesystem collisions |
| **C. Lowercase everything** | One spelling | 68 upstream names broken |

**Why this is yours:** it limits what a publisher may name a package.

Accepted cost: the case-folded set in the repository document.

### Resolved: where a proxied archive comes from (was Q9)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: the upstream repository's
own archive mirrors first, then the original source and `mirrors` entries on a per-repository
source-host allowlist that is empty by default for opam.ocaml.org; every fetch verified against
every declared checksum; a source with no strong checksum pinned on first fetch (Design, "The
proxied path"; AC20, AC22, AC23).

**Recommendation:** A. opam.ocaml.org's cache answered all 100 sampled archives, so the default
needs no off-origin egress, and the allowlist is the bounded-egress shape `composer.md` already
adopted.

| Option | You get | It costs |
|---|---|---|
| **A. Upstream cache first; allowlisted sources; verify all; pin weak** | A working cache with bounded egress | An allowlist to configure for upstreams without a cache |
| **B. Fetch any source host the upstream names** | No configuration | An open egress relay from the proxy layer |
| **C. Upstream cache only** | No off-origin egress ever | Archives the upstream never cached are unavailable |

**Why this is yours:** it widens where the proxy layer may send requests.

Accepted cost: the requirement on `proxy-cache.md` and `upstream-adapters.md`, both met (the
declared digest set and ordered candidates in `proxy-cache.md`'s resolved completion-only decision,
was Q15; the `hosts` allowlist with `none` and `own` roles in `upstream-adapters.md`'s resolved
allowlist decision, was Q3), and the first-fetch limit for the archives declaring nothing stronger
than md5. Of the 21 this record counted, the 19 that declare no checksum at all are left out of
the served index by the resolved no-checksum decision (was Q16), because fetch-and-cache refuses a
fetch with neither a digest nor a verifier; the 2 md5-only ones keep this record's pin.

### Resolved: versions whose source is a VCS URL (was Q10)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: refused on hosted publish
and omitted from proxied indexes with a divergence recorded (Scope; Design, "The proxied path";
AC5, AC24).

**Recommendation:** A. A branch-tracking source has no checksum and no bytes to hold, and serving
it sends the client to a Git forge outside every guarantee; only 4 of 19,187 upstream versions are
affected.

| Option | You get | It costs |
|---|---|---|
| **A. Refuse and omit** | Every served version installs from the registry | 4 compiler variants unavailable through the cache |
| **B. Serve with the source untouched** | Upstream parity | The client clones from a forge the registry cannot see or refuse |
| **C. Serve untouched, with an opt-in omission** | Parity by default | An option protecting four versions |

**Why this is yours:** it trades four packages against a containment guarantee.

Accepted cost: the divergence entries and the missing variants.

### Resolved: virtual repositories (was Q11)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: per-name resolution, the
first member holding a name (case-insensitively) supplying all of its versions (Design, "Virtual
repositories"; AC26).

**Recommendation:** A. Member order is `data-model.md`'s resolution rule, and per-name shadowing is
the defence against the captured union.

| Option | You get | It costs |
|---|---|---|
| **A. Per name, first member wins** | Private names cannot be overridden by upstream versions | A private package hides every upstream version of its name |
| **B. Per version, union of all members** | Every version of every member visible | Reproduces the client's confusion inside the registry |
| **C. No virtual repositories** | Nothing to specify | Users configure several repositories and the client's union decides for them |

**Why this is yours:** it sets the precedence between private and public content.

Accepted cost: the documented shadowing.

### Resolved: the addressed object, and what a pattern refusal looks like (was Q12)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: the archive route and
management operations report the name, the cache route is content-addressed, the index and `repo`
report none, and a pattern refusal answers `404` (Design, "Addressed objects and pattern scopes";
AC14).

**Recommendation:** A. It applies `auth.md` as written, as `cargo.md`, `conan.md` and `luarocks.md`
did, and `404` keeps a pattern from being an oracle.

| Option | You get | It costs |
|---|---|---|
| **A. Name object; cache content-addressed; index none; `404`** | No new object kind; no oracle | A patterned `pull` cannot resolve; it reads any archive whose hash it knows |
| **B. Exempt the index from the pattern rule** | Patterned `pull` resolves | The index enumerates every name, the leak the none rule exists to stop |
| **C. Pattern refusal as `403`** | Distinguishable refusals | An oracle over names outside the pattern |

**Why this is yours:** it accepts client-wide limitations rather than bending a settled security
rule.

Accepted cost: the documented limitations.

### Resolved: how a policy refusal is rendered (was Q13)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: `403` with `{"errors":
[...]}` on the cache and archive routes, and no elision from the index (Design, "Policy refusals on
the wire"; AC15).

**Recommendation:** A. With sources rewritten, a listed refused version halts the install with no
other host contacted (captured shape), and it is the no-elision precedent.

| Option | You get | It costs |

### Resolved: proxied versions whose source declares no checksum (was Q16, raised and adopted 2026-09-28)

**Adopted 2026-09-28 under the owner's standing delegation.** Option A: an upstream version whose
`url` section declares no checksum is left out of the served index with a divergence recorded,
and its source is never fetched (Scope; Design, "The proxied path"; AC22). The md5-only case keeps
the resolved proxied-archive decision's first-fetch pin (was Q9).

The question: this spec pinned such archives on their first fetch (was Q9), but `proxy-cache.md`
has since settled that a fetch-and-cache request carries a declared digest or a handler-supplied
verifier and never neither, and refuses one with neither before any upstream request, so that
the layer "never commits bytes it did not verify" (its resolved completion-only decision, was
Q15; AC20). A `url` with no checksum gives no digest, and an opam source may be any file (a
non-archive is copied into the build tree by name), so no structural verifier binds it. On
opam.ocaml.org 19 of 19,187 opam files are in this case.

**Recommendation:** A. It applies to the proxied path the rule the hosted path already has (a
source with no checksum is refused at publish, because the client itself never checks it), it is
the treatment VCS sources receive (was Q10), and it keeps the layer's no-unverified-commit
invariant without a verifier that verifies nothing.

| Option | You get | It costs |
|---|---|---|
| **A. Leave such versions out, with a divergence** | One rule on both paths; the layer's invariant holds | 19 upstream versions unavailable through the cache |
| **B. A structural verifier (archive parses completely) where the source is an archive** | Most of the 19 served | A check that binds nothing to the coordinate, and non-archive sources still unservable, so two rules for one field |
| **C. A verifier that accepts any complete body** | All 19 served | A verifier in name only, defeating the invariant the layer states |

**Why this is yours:** it trades a handful of upstream versions against an invariant you
delegated for the proxy layer.

Accepted cost: the 19 missing versions and their divergence entries.
