# Plan: Vagrant boxes

The Vagrant box format, hosted and proxied, on one handler: a per-box catalog document (the
"box metadata" JSON naming versions, providers, architectures, checksums and box URLs), served
at the paths the three forms of `vagrant box add` request it from, and the box files it points
at, which are routinely several gigabytes. Vagrant 2.3.7 and Vagrant 2.4.9, either side of the
architecture support 2.4.0 introduced, are the oracle on both paths.

## Context

Vagrant sits in Tier 3 of `formats/catalogue.md` as the single-ecosystem family "Vagrant" (the
row "Vagrant boxes"). **Its build is gated by `project-charter.md` AC9 and `catalogue.md` AC5**:
no handler code for a Tier 3 ecosystem exists before every Tier 1 format has met its definition
of done and the owner has recorded a `continue` verdict at the charter's build step 8. This spec
exists now because the owner directed on 2026-09-26 that all 33 ecosystems be specced up front
(the catalogue's "Every ecosystem below is specced now; only building is gated"), so the gate
decides what is built and never what is written; a `shrink` verdict parks it.

**The ecosystem's public registry is being shut down.** HashiCorp's deprecation notice, read this
run on the box versioning page and the HCP deprecation page: "As of October 1, 2026, new boxes can
no longer be created in HCP Vagrant. Existing box deployments will continue to operate until the
end of operations date of December 31, 2026", with end of support on November 2, 2026, and
"Customers using Vagrant boxes hosted on the HCP Vagrant registry must find a new provider and
re-host their boxes." The Vagrant CLI stays. That makes this format unusual in two ways: every
Vagrant user who shares boxes needs a replacement host, which is exactly this registry's hosted
path, and the one public upstream a proxied path would most obviously cache disappears within
three months of this draft. The design treats HCP Vagrant as one catalog among many rather than
as the upstream, and names the migration path off it (Design, "The proxied path").

Grounding for this draft, stated up front because the constitution asks for evidence or silence:

Where the documentation and the captures disagree or the documentation is silent, the captures
and the source win, and the differences are recorded because they would otherwise be built from
the documents. The architecture page says `default_architecture` lets "box owners control which
version pre-2.4.0 Vagrant CLI versions receive"; 2.3.7's parser ignores the field and keeps the
**last** entry for each provider name (`box_metadata.rb` at 2.3.7: `Hash[@provider_map]`), and
the live bento document, whose default is `arm64` listed first, sent 2.3.7 to the `amd64` box
listed after it (captured). The versioning page says versions "must be of the format `X.Y.Z`";
the client accepts any `Gem::Version`, installs a prerelease `1.2.0.rc1` as the latest, and
treats `1.0` and `1.0.0` as one version (captured). Nothing documents that `vagrant box add`
decides whether a URL is a catalog by the `Content-Type` of a `HEAD` response, that the
credential Vagrant sends is chosen by comparing hosts with `VAGRANT_SERVER_URL`, or that URL
userinfo is persisted in plain text on the client's disk (all captured).

Eight things make this format worth a careful spec. **The catalog is one generated document per
box**, rewritten on every write that touches the box and naming absolute box URLs, which a
relative path cannot replace (captured: a relative `url` is opened as a local file). **Pre-2.4
clients take the last entry per provider**, so the document's order decides which architecture
a 2.3 host installs. **The box files are huge and immutable only if we make them so**: Vagrant
resumes an interrupted download with `Range: bytes={n}-` into a temporary file named by the SHA-1
of the URL, so different bytes behind the same URL splice two files, which the checksum catches
and, without one, installs silently (captured). **A catalog is discovered by `HEAD`**, and
`vagrant box add` fails outright on a `HEAD` the server does not answer with JSON. **2.4 probes
two paths for a shorthand name** and uses whichever answers JSON, so a refusal on one path and
not the other is bypassed (captured). **The credential goes wherever the host matches**:
Vagrant attaches `Authorization: Bearer` from `VAGRANT_CLOUD_TOKEN` to any URL whose host equals
`VAGRANT_SERVER_URL`'s, over plain HTTP too, and to a redirect's target under
`--location-trusted` (captured). **A refusal can fall back**, for direct box URL lists only, when
the first URL passes `HEAD` and fails `GET` (captured). And **the public registry ends on
December 31, 2026**, so the proxied path must be useful as a migration path, not only as a
cache.

## Blocking preconditions

**The handler interface re-open must complete before this handler starts**, as for every handler
(`format-handler-interface.md` AC8). Vagrant is Tier 3, so the catalogue's Tier 1 gate (its AC5)
and the charter's breadth verdict (its AC9, build step 8) both precede it; the re-open is
recorded here anyway, from this side, because a gate enforced on one side only is enforced
nowhere. This format adds no root-anchored mount: Vagrant takes a catalog URL with any path, and
`VAGRANT_SERVER_URL` may carry a path (captured), so everything lives under
`/vagrant/{repository}/`. It does need the externally visible base URL, as `npm.md` does, because
the catalog's box URLs must be absolute (Design, "Every catalog is a generated per-box document"):
`deployment.md`'s `server.public_url`, reached through `Deps`, which `format-handler-interface.md`'s
re-open records as a named input beside its route-scoped credential declarations ("The scheduled
re-open", naming this spec and `npm.md`).

**The shared index service must be `planned` before Phase 1 and built before the handler reaches
`main`.** Every hosted box's catalog is a write-triggered generated document produced by
`signing-service.md`'s write-path runtime, which the charter builds at step 7 as the production
form of the step 4a prototype (`write-triggered-services-prototype.md`). This handler declares the
optional `Indexer` interface and returns a generator from `internal/format/vagrant/index`
(`signing-service.md`, "The generator contract, and where a generator lives"), whose profile
declares no signing profile, so the service creates no key for a Vagrant repository and records no
signature: this format is the service's **unsigned** consumer by name (its AC24, citing this
spec's item 6). What this format requires is in Design ("What the index service must provide"),
each item mapped onto that spec's contract. Hosted reads cannot be tested without it, because a
box with no generated catalog has nothing for a client to read.

**The management API must be `planned` before Phase 2, and it is the only hosted write path.**
Publishing versions and provider files, deleting versions, providers and boxes, and changing a
provider's default architecture are operations of `management-api.md`, placed on its closed kind
vocabulary and reaching this handler through the optional `Operator` interface (its resolved
dispatch decision, was Q2), whose core the charter builds at step 2 and completes at step 9. The
upload shape of its "Publish through the API" was fixed by this format's scale finding: streamed,
resumable upload sessions, then a small publish naming committed digests. No client command
writes to a box catalog; `vagrant cloud publish` writes only to HCP's proprietary API, which
`management-api.md` weighed and declined to serve (its resolved compatibility-surfaces decision,
was Q8). Phase 1's hosted reads are testable without it, because the harness's `state` vocabulary
seeds boxes through the shared write path and the index runtime generates the catalog in that
write like any other (`signing-service.md` AC21; `conformance-harness.md` AC24).

**The proxied path depends on shared services that now exist**: the transport half of Design
("The proxied path") is `upstream-adapters.md`'s `https` adapter under the upstream's allowlist
and credential role (its requirements row for this spec names AC6, AC7, AC8 and AC19, the catalog
path template staying the handler's), built at charter step 4; the fetch modes are
`proxy-cache.md`'s, including the completion-only mode for boxes with no upstream checksum (its
resolved completion-only decision, was Q15, AC20); and the box-integrity entry is
`artifact-verification.md`'s (its requirements table's `vagrant.md` row), built at step 4b.
Publish is synchronous once the upload session has committed, and a virtual catalog is resolved
per request (the resolved virtual-catalog decision below, was Q13), so nothing is asked of
`async-operations.md`, which records this spec among those that ask nothing of it.

## Scope

**In scope:**

- **The catalog read surface** under `/vagrant/{repository}/`: the per-box document at
  `/{org}/{name}` and, identically, at `/api/v2/vagrant/{org}/{name}`, on `GET` and `HEAD`,
  answering `Content-Type: application/json` on both methods.
- **Box files** at `/{org}/{name}/{version}/{provider}/{architecture}/vagrant.box`, `GET` and
  `HEAD`, with single byte ranges (`Range: bytes={n}-` is what a resuming client sends), immutable
  for the life of the repository.
- **The three ways a client names a box**: an explicit catalog URL, a shorthand `{org}/{name}`
  expanded against `VAGRANT_SERVER_URL` (by 2.3 to one path, by 2.4 to two), and `vagrant box
  update` and `vagrant box outdated` re-reading the catalog URL the client stored at add time.
- **Hosted boxes** published through the management API, one version with one or more provider
  and architecture files per publish, their bytes stored exactly as uploaded, streamed and
  resumable at any size, their inner `metadata.json` checked against the declared provider and
  architecture.
- **Generated catalogs**: on every write that changes a box, the shared index service regenerates
  that box's document with a SHA-256 checksum on every entry and each provider's default
  architecture ordered last; the generator package expands its relative URLs to absolute ones at
  serve time, served through `index.ServeDocument`.
- Deleting versions, provider files and boxes, each a `management-api.md` kind retiring its
  coordinates through the core-held `Retirement` record, with the write-boundary declaration
  `data-model.md` requires, and changing a provider's default architecture.
- Name and version rules: case-sensitive `{org}/{name}`, names that cannot collide in Vagrant's
  on-disk layout, `X.Y.Z` versions at publish.
- Non-interactive authentication in the forms Vagrant sends: Bearer from `VAGRANT_CLOUD_TOKEN`
  (or the stored `vagrant cloud auth login` token) when `VAGRANT_SERVER_URL`'s host matches, and
  Basic from URL userinfo.
- The per-route addressed objects `auth.md`'s pattern scopes evaluate, and the rendering of a
  shared policy refusal on every route.
- **The proxied path** against any box catalog (HCP Vagrant until its end of operations, an
  S3-style static catalog, another registry): catalogs as mutable metadata with a TTL and every
  box URL rewritten to this registry; boxes as immutable artifacts verified against the
  upstream's checksum or, where the upstream publishes none, bound to the digest of their first
  fetch; negative caching; this format's rows of the removal table; and the migration path off a
  retiring upstream through `immediate` sync and a freeze.
- **Virtual repositories**, resolved per box name at request time with first-member resolution
  (the resolved virtual-catalog decision below, was Q13).
- The handler's `Capabilities()` declaration and repository rename (AC26).
- The two pinned clients above as conformance oracles on both paths, with the client network
  restricted to this registry and its stand-ins.

**Out of scope for v1**, each with its reason, recorded because the interface spec's definition
of done requires the deliberately unimplemented surface to be named:

- **HCP Vagrant's API v2** (`/api/v2/boxes`, `/api/v2/box/...`, `authenticate`, `user/{org}`,
  uploads, release and revoke) and therefore `vagrant cloud publish` and the other `vagrant
  cloud` commands. Its staged publish (an unreleased version, provider rows before bytes, a
  separate release call) is state with no entity in the shared model, 2.3.7's client sends it to
  a different path shape under a format-first mount (captured), and its owner is retiring it; the resolved
  HCP-API decision below records the choice and hands the captured sequence to
  `management-api.md`.
- **Search and any catalog of box names.** Vagrant's box commands never list names; only `vagrant
  cloud search` does, against the API above.
- **Direct box adds without a catalog** (`vagrant box add --name x https://.../vagrant.box`) are
  served as ordinary box reads, but no route exists to serve a box outside its catalog: every box
  route is a catalog coordinate.
- **Box contents.** The disk image inside a box is a provider format (VMDK, qcow2, VHD, Parallels
  HDD); the registry never unpacks it beyond `metadata.json`, because nothing the client checks
  depends on it, and the byte-level cataloguer `supply-chain-policy.md` describes decides its own
  coverage (Design, "Advisories, OSV and the security-signal rule").
- **The `access_token` query parameter** (`VAGRANT_SERVER_ACCESS_TOKEN_BY_URL`). Vagrant sends the
  token in the URL instead of a header in that mode (captured); `auth.md`'s presentation-forms
  table has one query-parameter form, Open VSX's `token` on its four write routes, and none for
  this format, and a credential in a URL leaks into every log between client and server, so the
  parameter is never an authentication input; it is still redacted wherever a URL is logged
  (Design, "Authentication").

## Design

### The wire surface, as captured

Every route hangs off `/vagrant/{repository}/`, format-first per `format-handler-interface.md`'s
resolved URL-shape decision. A user sets `VAGRANT_SERVER_URL=https://{host}/vagrant/{repository}`
(Vagrant keeps the path, captured) or names the catalog URL directly.

| Surface | Shape, as the pinned clients send it |
|---|---|
| Catalog probe | `HEAD {url}` with `Accept: application/json` and `User-Agent: Vagrant/{version} (+https://www.vagrantup.com; ruby{version})`. The URL is a catalog if the response's `Content-Type` matches `application/json` (`application/json; charset=utf-8` passes); otherwise the URL is treated as a box file and a name is demanded ("Box file was not detected as metadata", captured with `text/plain`). Any error status fails the add at once with "There was an error while downloading the metadata for this box" and the status line, no retry and no body shown (captured with `401`, `403`, `404`, `405` and 500) |
| Catalog read | `GET {url}` with the same headers, then parsed as JSON; a version string `Gem::Version` cannot parse fails the whole add ("formatted in a way that Vagrant cannot parse: 'latest'", captured). `vagrant box outdated` and `vagrant box update` issue the `GET` without the `HEAD` (captured) |
| Shorthand | `{org}/{name}` becomes `{server}/{org}/{name}` on 2.3.7, and on 2.4.9 both `{server}/api/v2/vagrant/{org}/{name}` and `{server}/{org}/{name}`, each probed by `HEAD`, the first answering JSON used (captured: an API path answering `403` fell through to the other). With `VAGRANT_SERVER_URL` unset the server is `https://vagrantcloud.com` (captured) |
| Stored catalog URL | The URL the add used is written to `~/.vagrant.d/boxes/{name with / as -VAGRANTSLASH-}/metadata_url`, userinfo included, in plain text (captured), and every later `update` and `outdated` reads it. 2.3.7 stores `{server}/{org}/{name}`, 2.4.9 the API path (captured), so both paths are permanent contracts |
| Selection | The highest `Gem::Version` satisfying the constraint (default `>= 0`, prereleases included), then the provider: `--provider`, or the only one, or an interactive prompt that fails without a TTY (captured). 2.4.9 then matches the host architecture, falling back to an `unknown` entry marked default; **2.3.7 keeps the last entry per provider name and ignores `architecture` and `default_architecture`** (captured: with `amd64` listed before `arm64`, 2.3.7 installed the `arm64` box on an `amd64` host) |
| Box download | `GET {provider url}` through curl with `--fail --location --max-redirs 10 --continue-at -` into `~/.vagrant.d/tmp/box{sha1 of url}`; no `HEAD`, no conditional header. A fresh download sends no `Range`; a retry after an interrupted or dropped transfer sends `Range: bytes={bytes held}-` and appends (captured on both lines, below) |
| Checksum | After the download, if the entry has both `checksum` and `checksum_type`, the whole file is hashed with `md5`, `sha1`, `sha256`, `sha384` or `sha512` (case-insensitive hex compare) and a mismatch fails with "The checksum of the downloaded box did not match"; an unknown type fails ("not supported by Vagrant: crc32"); an empty checksum skips the check silently (captured, HCP's `"checksum": "", "checksum_type": "none"` included) |
| Unpack | `bsdtar` extracts the box; `metadata.json`'s `provider` must equal the selected provider (source); the box lands in `boxes/{name}/{version}/{architecture}/{provider}/` on 2.4.9 and `boxes/{name}/{version}/{provider}/` on 2.3.7 (captured) |
| Update checks | `vagrant up` checks at most once per box per 3,600 seconds (`BOX_UPDATE_CHECK_INTERVAL`, `box.rb`); `vagrant box outdated --global` reports a failed catalog read as an error line and still exits 0 (captured) |

**Interrupted and dropped downloads, captured with the 600 MB box at 25 MB/s:**

- **Ctrl-C** (SIGINT to Vagrant and curl, as a terminal delivers it) keeps the partial file; the
  interrupted command then hashes the partial file and prints a checksum mismatch, which is noise.
  The next `vagrant box add` re-reads the catalog, prints "Box download is resuming from prior
  download progress", sends `Range: bytes=205914112-` (2.3.7) or `bytes=203161600-` (2.4.9),
  receives `206`, and verifies the checksum over the joined file.
- **A dropped connection** (the stub closed it after 150,000,000 bytes) fails the add ("transfer
  closed with 479155840 bytes remaining" on 2.3.7, "end of response with 479155840 bytes missing"
  on 2.4.9) and also keeps the partial file; the next add resumes from byte 150,000,000.
- **A server that ignores `Range`** and answers `200` makes curl stop after the first 64 KiB
  (exit 33) and Vagrant restart the download from byte 0 without `Range` (captured on both): the
  whole box again.
- **Different bytes behind the same URL** between the interrupted attempt and the resume (a
  megabyte changed at offset 400,000,000) produce a spliced file. With a `sha256` checksum the
  add fails; **without one it succeeds and installs a disk image whose digest differs from the
  published one** (captured on 2.4.9).
- A partial file older than 24 hours is discarded (`RESUME_DELAY` in `box_add.rb`), and
  `--clean` discards it.

Hence the four rules the design is built on: every box URL names bytes that never change, every
box route serves single ranges, every catalog entry carries a checksum, and the URL of a given
box never varies between catalog reads, because the resume file is keyed by the URL.

**Error rendering**, captured, because a refusal nobody can read is a refusal nobody can act on:
neither line prints a response body on any status. A catalog failure prints "There was an error
while downloading the metadata for this box. The error message is shown below: The requested URL
returned error: {status}"; a shorthand failure prints "The box '{org}/{name}' could not be found
or could not be accessed in the remote catalog" with the expanded URL and the same line; a box
failure prints "An error occurred while downloading the remote file ... The requested URL
returned error: {status}". `vagrant box add` exits 1 on each.

### Fallback: what a refusal can and cannot stop

`julia.md` found that Pkg falls back to origin on every refusal, `terraform.md` that Terraform
never does, and `alpine.md` and `rpm.md` that a refused package does not fall back while a
refused index does. Vagrant has three paths, captured on both lines:

- **A catalog add never falls back.** The catalog names one URL per provider entry, and a refused
  box fails the add with exit 1 (captured). Several catalog URLs at once are refused by the client
  itself ("Multiple URLs for a box can't be specified when adding", captured through the real
  `BoxAdd` middleware).
- **A 2.4 shorthand name falls through between its two paths on the same server.** A `403` on
  `/api/v2/vagrant/{org}/{name}` and a JSON `200` on `/{org}/{name}` installed the box (captured).
  Both paths are this registry's, so the rule is that they are one resolution: identical status,
  headers and body for every caller.
- **A direct box URL list falls back on `GET` but not on `HEAD`.** A Vagrantfile may give
  `config.vm.box_url` as a list; the client probes every URL with `HEAD` first, and any probe
  error fails the add outright (captured: `403` on the first), but when the first URL passes
  `HEAD` and then refuses the `GET`, the client prints the error and downloads the next URL, from
  another host (captured, exit 0).

Two rules follow, and the conformance cases assert them. **A policy refusal answers the same
status and body to `HEAD` and `GET`** on every box route, so a direct list fails at the probe and
never reaches a second URL (the resolved refusal-rendering decision below). **The two catalog
paths are one route**: nothing, including a pattern scope or a policy rule, may distinguish them.

The configuration, not the client, is the remaining exposure. With `VAGRANT_SERVER_URL` unset,
every shorthand name in every Vagrantfile resolves on vagrantcloud.com (captured), and a token in
`VAGRANT_CLOUD_TOKEN` is then sent to vagrantcloud.com rather than to this registry (captured: no
header reached `boxes.test`). The operator documentation states both, and that HCP Vagrant's
operations end on December 31, 2026, after which unset configurations fail instead.

### Mapping onto the shared model

The levels are exactly those `data-model.md` provides; no table is added.

- **A `Package` is `{org}/{name}`**, byte for byte as published (the resolved box-name decision
  below). A box is always two segments, because Vagrant's shorthand is `^[^/]+/[^/]+$`
  (box_add.rb) and HCP's names are `{org}/{name}`.
- **A `Version` is the `X.Y.Z` string**. Its document holds the version's `description` and, per
  provider file, the provider name, the architecture, whether it is that provider's default
  architecture, the CAS digest, the size, and the checksum the publisher declared, if any.
- **`File`**: one per `(provider, architecture)` of a version, `{provider}/{architecture}/vagrant.box`,
  keyed by CAS digest.
- **The package-level document** holds the box's `description` and short description. Deleted
  coordinates are not held here: they are core-held `Retirement` records (`data-model.md` AC35;
  `management-api.md`, "Retirement is core-held").
- **The box's generated catalog** is the generator's one package-level document key per box,
  stored by `signing-service.md`'s runtime inline or, above the inline threshold, as a CAS blob
  protected by the fourth GC mark root (`signing-service.md` AC5; `storage-and-gc.md` AC16): the
  live `bento/ubuntu-24.04` document is 11,495 bytes for six versions, so a box with a long
  release history crosses it.
- **A remote repository's current documents** hold, per box it has served, the catalog the
  generator's `FromUpstream` produced from the current upstream revision (Design, "The proxied
  path"), the retained upstream revisions, and the verification record for each cached box (the
  upstream checksum it matched, or the digest of its first verified fetch); every cached box is a
  `File` whose `RemoteFile` records the upstream URL the entry named; none of it is snapshot
  content.

### The hosted publish path and what counts as a write

Nothing on Vagrant's box wire writes. The hosted path is fed by the registry-owned management API,
`management-api.md`. Each operation is one of its closed vocabulary's kinds, declared by this
handler through the optional `Operator` interface (`Operations()` returning `publish`,
`annotate`, `delete-file`, `delete-version` and `delete-package`; `Bindings()` returning none,
because no client route and no reference API drives any of them). `Submit` refuses a `remote` or
`virtual` target `405` `repository-type` before authorization, evaluates every pair `Authorize`
reports, checks the retirement set, and runs `Apply` inside one write transaction, in which the
index runtime regenerates the box's catalog before commit, so each operation is one completed
logical write in one snapshot and a refused one leaves nothing (its "Every operation is one
completed logical write"). The action follows the kind (its "The operation vocabulary"); the
column below is that spec's, not a choice made here. Each kind's trigger is verified by this
registry's integration tests and a `script`-driven conformance case (`management-api.md` AC24,
enforced by `conformance-harness.md` AC26), and its effect by the real clients
(`docs/internal/analysis/management-surfaces-and-the-oracle.md`).

| Operation | Kind | What the operation carries | Effect a client sees | Action |
|---|---|---|---|---|
| Publish a version | `publish` | `{org}/{name}`, an `X.Y.Z` version, an optional description, and one or more box files committed through upload sessions, each declared with its provider, architecture, optional default flag and optional checksum (the resolved multi-provider-publish decision below, was Q4) | The version appears in the box's catalog with every provider entry; `vagrant box add` and `vagrant box outdated` see it on their next catalog read | `push` on `{org}/{name}/{version}` |
| Add a provider file to a version | `publish` | `{org}/{name}`, version, and one box file as above | A new entry under that version | `push` on `{org}/{name}/{version}` |
| Set a provider's default architecture | `annotate` | `{org}/{name}`, version, provider, architecture | The catalog reorders that provider's entries so the new default is last | `push` on `{org}/{name}/{version}` |
| Delete a provider file | `delete-file` | `{org}/{name}`, version, provider, architecture | The entry leaves the catalog; its box route answers `404`; the coordinate is retired | `delete` on `{org}/{name}/{version}` |
| Delete a version | `delete-version` | `{org}/{name}`, version | The version leaves the catalog; its box routes answer `404`; the version and every coordinate under it are retired | `delete` on `{org}/{name}/{version}` |
| Delete a box | `delete-package` | `{org}/{name}` | Every version leaves and is retired; the catalog routes answer `404`; the `Package` row survives (`data-model.md`, "A package outlives its versions") | `delete` on `{org}/{name}` |

Adding a provider file is `publish`, not `attach`, although `management-api.md`'s reconciliation
table places it under `attach` and names "a Vagrant provider file" among that kind's examples.
The kind table defines `attach` by effect as an auxiliary file "that no coordinate binds and no
client verifies as the version's bytes", and a provider file is the opposite on both counts: its
`(version, provider, architecture)` coordinate binds one set of bytes and is retired on deletion,
and the client verifies it against the catalog's checksum and installs it. `publish` ("adds a
version, or files to a version") is the kind whose definition fits, with the same `push` action,
so nothing about authorization changes; the table row is reported for correction rather than
followed against its own definitions.

**Box files are multi-gigabyte, so the upload is the part that must be specified.** Vagrant's own
publisher gives the scale: `vagrant cloud publish` abandons HCP's direct upload for files over
5 GiB (`publish.rb`, "disable direct if over 5G"), and the bento box sampled live is 651 MB
compressed. `management-api.md` fixed its publish shape on this finding ("Publish through the
API"): each box file is an upload session in `data-model.md`'s sense (its AC26), streamed into the
CAS without buffering the whole body in memory or in a temporary file, resumable across a dropped
connection within the session's lifetime with `Content-Range` chunks, its SHA-256 computed in the
stream, and committed only on a verified digest, the implementation OCI's chunked upload shares.
The publish operation then names committed digests and the declared coordinate, so the write
itself is small and its latency does not scale with box size. `Apply` peeks each committed blob,
reading the archive's entries (tar, tar with gzip, or zip, as the box format page lists) until it
finds `metadata.json` at the archive root, and refuses a disagreement before anything is
referenced; a committed blob a refused publish leaves unreferenced is the orphan
`storage-and-gc.md` AC3 already collects.

What `Apply` enforces, each refusal answered `validation` (422) unless stated, with nothing
committed:

- **The name**: two segments, each `[A-Za-z0-9][A-Za-z0-9._-]*` of at most 100 bytes, and never
  containing `-VAGRANTSLASH-` or `-VAGRANTCOLON-`, the strings Vagrant substitutes for `/` and `:`
  in its box directory (`box_collection.rb`), so no two names can land in one local directory.
  Anything else is refused.
- **The version**: `X.Y.Z` of non-negative decimal integers without leading zeros (the resolved
  version-grammar decision below), refused otherwise.
- **The provider**: `[a-z0-9_-]+`, equal to the `provider` in the file's `metadata.json`, which
  the client enforces on unpack; a mismatch, a missing or unparsable `metadata.json`, or an
  archive that is none of the three forms is refused.
- **The architecture**: one of HCP's list (`amd64`, `i386`, `arm`, `arm64`, `ppc64le`, `ppc64`,
  `mips64le`, `mips64`, `mipsle`, `mips`, `s390x`) or `unknown`, and equal to `metadata.json`'s
  `architecture` when that field is present; refused otherwise.
- **A declared checksum** is verified against the uploaded bytes (the box-integrity entry of
  `artifact-verification.md`, below) and a mismatch refused; the catalog always carries the
  SHA-256 this registry computed, whatever was declared.
- **A coordinate `(version, provider, architecture)` that already exists is refused `conflict`
  (409)**, and a retired one is refused `retired` (409) by the shared write path with any bytes,
  including after the deleting snapshot has been pruned and after a backwards repoint, because the
  `Retirement` record is not snapshot content (`management-api.md`, "Retirement is core-held"):
  the cross-format retirement rule, and the rule that keeps a resuming client from splicing (the
  resolved immutability decision below). The CI-retry case this spec first answered with an
  identical-bytes no-op is `management-api.md`'s `Idempotency-Key`: a retry carrying the first
  request's key and payload replays its outcome and creates no snapshot (its AC17), so the
  handler needs no byte comparison of its own.
- **Exactly one default architecture per `(version, provider)`**: the first file published for a
  provider in a version is its default unless the publish marks another, following the
  architecture page's "the first provider in the configuration for a box version is the default
  architecture".
- Retirement granularity is the handler's to report in `Outcome`: `delete-file` retires
  `{org}/{name}/{version}/{provider}/{architecture}`, `delete-version` the version and every
  file coordinate under it, and `delete-package` every version of the box.
- A publish or management operation against a remote or virtual repository answers `405` with
  problem type `repository-type` before authorization.

`data-model.md` requires each format spec to declare its ecosystem's write boundaries. Vagrant's
declaration:

- **One publish is one completed logical write**, however many provider files it carries,
  together with the regeneration of that box's catalog, in one snapshot. The upload sessions that
  precede it are not writes; their committed blobs are in flight in the repository under the
  upload scope until the publish references them.
- **Adding a provider file, setting a default architecture, and each deletion are each one
  write**, each deletion's `Retirement` records written in the same transaction; a retention pass
  over a repository is one write.
- A proxied repository creates no snapshots; catalog revisions and boxes arriving from an
  upstream are cache materialisation.

### Every catalog is a generated per-box document

A box's catalog is produced by the shared index service inside the write that changes it,
**stored, never assembled from version rows on request**, the write-triggered class
`write-triggered-services-prototype.md` defines, without the signature. It is stored with box
URLs as paths relative to the repository, and on every response the generator package expands
each `url` with `server.public_url` and `/vagrant/{repository}/` under the repository's current
name, the transform `npm.md` applies to `dist.tarball` and `chef.md` to its universe; a relative
`url` is not an option, because the client opens it as a local file ("Couldn't open file
/boxes/...", captured). The document is served through `index.ServeDocument` (`signing-service.md`
AC11), which sets the validators, so the handler package sets no `ETag` and no `Last-Modified`
(`internal/format/freshness_boundary_test.go`). `signing-service.md` does not yet state a
serve-time expansion a profile may declare for `ServeDocument` to apply, the gap `chef.md` raised
for its universe; this format is its second consumer, and the fallback, should that spec decline,
is write-time URLs regenerated when `server.public_url` or the repository name changes. Nothing
else in the stored document varies per request, and in particular **no per-caller credential or
capability is ever written into a box URL** (the resolved credential-form decision below), because
the client keys its resume file on the URL.

- **Regeneration inside the write.** A publish, a provider addition, a default change or a
  deletion regenerates that box's catalog before commit, in the same snapshot as the change
  (`signing-service.md`, "The write path dispatches; the handler cannot forget", its AC1; the
  generator's `Affects` names the one box's key). No other box's document is touched, so writes
  to different boxes never contend.
- **Under contention, both land.** Two concurrent publishes of different versions of one box each
  produce a catalog listing the other's version once both are complete, through the per-document
  serialisation and retry `signing-service.md` applies ("Contention: serialise per document,
  then retry", its AC3).
- **Box files outlive the catalog that stops naming them only as the retention rule allows.** A
  box route serves any file a catalog of a retained snapshot names, so a client that read the
  catalog just before a later publish still downloads what it was given. A deletion is the
  exception by design: its box routes answer `404` at once.
- **Caching headers and freshness.** The generator's profile declares the freshness rule `ETag`
  only and `Cache-Control: no-cache` for catalogs, so `ServeDocument` serves a byte-derived `ETag`
  and no `Last-Modified`: no client sends a conditional request (captured), so the headers serve
  intermediaries, and nothing a client holds can hide a rollback, which is why this format needs
  no pointer-scoped freshness (`data-model.md` AC36 covers it without a Vagrant-specific signal).
  Box files are served with `Cache-Control: public, max-age=31536000, immutable`, `Accept-Ranges:
  bytes` and `Content-Type: application/octet-stream`, never a JSON type, since a box answering
  JSON to `HEAD` would be read as a catalog by a direct add.
- **No hosted route answers a redirect**, because a redirect under `--location-trusted` carries
  the client's Bearer token to whatever host the redirect names (captured).
- **A repoint restores the catalogs.** The generated catalogs are snapshot content, so a rollback
  serves exactly the catalogs of the snapshot it targets, and the retirement set survives it by
  construction, because `Retirement` records are not snapshot content (`management-api.md`,
  "Retirement is core-held").

### What the index service must provide

Stated so the dependency could not be lost, and now mapped item by item onto
`signing-service.md`'s generator contract, which names this format its unsigned consumer:

1. **Generation of one box's catalog** from its version-level records: a JSON object with `name`
   (the `{org}/{name}` exactly), `description`, and `versions`, one object per version with
   `version`, `description` when present, and `providers`, each provider entry carrying `name`,
   `architecture`, `default_architecture`, `url` as the relative path
   `{org}/{name}/{version}/{provider}/{architecture}/vagrant.box`, `checksum` as the lowercase hex
   SHA-256 of the file and `checksum_type: "sha256"`. The fields are exactly those
   `box_metadata.rb` reads at 2.4.9 plus the descriptions; nothing is invented. Met by the
   generator package `internal/format/vagrant/index`, pure, called only by the runtime
   (`signing-service.md`, "The generator contract"; its `generator_purity_test.go`).
2. **Ordering for pre-2.4 clients**: versions in ascending `Gem::Version` order, and within each
   version every provider's entries grouped with its default architecture's entry **last**, so
   2.3's last-entry-wins parser selects the default (the resolved legacy-ordering decision below).
   The ordering is part of the generated bytes, never applied at serve time. Met: "Vagrant's
   provider ordering" is among the format knowledge that spec places in the generator package.
3. **Synchronous regeneration inside the write**, within a management request's latency budget,
   with no asynchronous half, and the retry under contention. Met by the write-path runtime
   (its AC1, AC3).
4. **Storage** above the inline threshold as a CAS blob with a byte-derived `ETag`, and retention
   of every box file an unpruned snapshot's catalog names. Met by its storage section and AC5 and
   `ServeDocument`; the files are snapshot content, retained by ordinary reachability.
5. **The virtual merge.** Withdrawn by the resolved virtual-catalog decision below (was Q13): a
   virtual catalog is resolved per box name at request time, so the generator declares no
   `Merge`, the shape `signing-service.md` allows for a format whose virtual is a lookup rather
   than a merged document.
6. **No signature**, and no key: Vagrant verifies nothing but the checksum, so this format is the
   service's first unsigned consumer. Met by its AC24.

Two items this format needs that the list above did not name: the serve-time URL expansion (the
gap above) and `FromUpstream`, the proxied-path generation from a parsed upstream catalog (Design,
"The proxied path"), for which `signing-service.md`'s "The proxied path" names CRAN, LuaRocks,
Chef and opam and whose contract this format uses unchanged.

### What artifact verification must provide

`artifact-verification.md` carries what this format asked of it (its requirements table's
`vagrant.md` row, and its "Integrity: digest, size, checksum set" entry): **a box integrity
entry** that takes a file, an expected checksum and a checksum type from Vagrant's set (`md5`,
`sha1`, `sha256`, `sha384`, `sha512`, compared case-insensitively as the client does), and
answers `match`, `mismatch` or `weak`, the last for an `md5` or `sha1` claim (its AC18). It runs
on the hosted path over a publisher's declared checksum and on the proxied path as the declared
digest set of a stream-and-verify fetch; its hosted and proxied cases are this format's (its
AC24). Vagrant has no signature layer, so the verdict source `supply-chain-policy.md` consumes
answers **absent** for every Vagrant artifact, and a rule requiring a verified signature refuses
every box, which the operator documentation states.

### Names, versions and case

- **Nothing folds.** Names are compared byte for byte (the resolved box-name decision below). A
  request whose spelling differs from the published name answers `404`. HCP instead looks names
  up case-insensitively and echoes the organisation as requested with the box name canonical
  (`BENTO/UBUNTU-24.04` answered with `"name":"BENTO/ubuntu-24.04"`, captured), and the client
  stores the box under whatever `name` the document carries (captured with `Acme/Case`), so
  folding would give one box several local identities.
- **The catalog's `name` must equal the requested name.** A Vagrantfile's `config.vm.box` or
  `--name` that differs from the document's `name` fails with "The box you're adding has a name
  different from the name you requested" (captured on both lines); the hosted document's `name` is
  always the stored `{org}/{name}`, which equals the path the request named.
- **Versions are `X.Y.Z` at publish**, so byte equality and `Gem::Version` equality coincide:
  `1.0` and `1.0.0` are one version to the client, which installed the entry listed as `1.0.0`
  with the other's URL order undefined (captured), and a prerelease such as `1.2.0.rc1` is
  installed as the newest under the default constraint (captured).
- **Percent-decode before lookup**; names contain no characters that need encoding under the
  grammar above.

### Authentication: a Bearer the host decides

Vagrant sends a credential in two ways, and neither is challenged: both are preemptive (captured).

- **Bearer from the Vagrant token.** When a token is available (`VAGRANT_CLOUD_TOKEN`, else the
  token vagrant cloud auth login stored, else `ATLAS_TOKEN`; `client.rb`) and a URL's host equals
  the host of `VAGRANT_SERVER_URL`, the client adds `Authorization: Bearer {token}` to the catalog
  `HEAD` and `GET` and the box `GET` (captured on both lines). The comparison is **host only**:
  scheme and port are ignored, so the token went over plain HTTP to an `http://` box URL on the
  same host (captured). A box URL on another host gets nothing (captured `401` from `files.test`);
  a same-host redirect's cross-host target gets nothing by default and gets the token under
  `--location-trusted` (captured). The first authenticated request in a process prints a warning
  naming the custom server and sleeps five seconds (`CUSTOM_HOST_NOTIFY_WAIT`; the captured adds
  took 6.0 and 6.1 seconds). `config.vm.box_server_url` in a Vagrantfile does not enable it: the
  middleware reads only the environment (`add_authentication.rb` calls `Vagrant.server_url` with
  no configuration).
- **Basic from URL userinfo.** `https://__token__:{token}@host/...` is sent as Basic on the
  catalog requests (captured) and masked as `*****:*****` in output, but it is **not** carried to
  box URLs the catalog names: the box `GET` went without a credential and failed `401` (captured).
  The userinfo is also written to the stored `metadata_url` in plain text (captured).

Per the resolved credential-form decision below, **the Bearer form is the recommended and the
only complete form for a private repository**: `VAGRANT_SERVER_URL=https://{host}/vagrant/{repository}`
and the token in `VAGRANT_CLOUD_TOKEN`. How this meets `auth.md`, whose rules this spec does not
bend:

- `auth.md`'s verifier already accepts Bearer and the Basic password, both **universal** rows of
  its "Presentation forms" table (its AC31), so nothing route-scoped is declared by this handler;
  its client table still has no `vagrant` row, which this pass reports again (the auth half of the
  consequences queue's Open item 23 was never applied).
- **Host scoping is the client's, so the token reaches every repository on the host.** A user
  adding boxes from two repositories of one registry sends one token to both, which a
  single-repository token cannot serve; such a user needs `auth.md`'s explicit multi-repository
  token, which the operator documentation says.
- **No challenge is needed, and none helps**: a credential-less request to a repository that is
  not anonymously readable answers `401` with `WWW-Authenticate: Bearer realm="..."`, identically
  for a private and a missing repository (`auth.md` AC17); a valid token lacking `pull` answers
  `404`; a rejected token answers `401` and is never served as anonymous (`auth.md` AC12).
- **TLS is the server's to enforce**, since the client sends the token over plain HTTP whenever
  the URL says so: `auth.md` AC27 refuses it.
- **`access_token` in a query string is never accepted and always redacted.** In
  `VAGRANT_SERVER_ACCESS_TOKEN_BY_URL` mode the client sends `?access_token={token}` and no header
  (captured), which is answered as the credential-less request it is, because the parameter is
  not a presentation form `auth.md` recognises on any route of this format. The handler never
  reads a credential, so the redaction is the shared layers': the request log never records the
  query string, naming this parameter as the reason, and `telemetry.RedactURL` replaces its value
  in any logged URL (`observability.md`, "Redaction", its AC9); the conformance corpus redacts it
  by `conformance-harness.md` AC13's rule, which names this spec's parameter.
- **No hosted route redirects**, so `--location-trusted` never forwards the token anywhere.

### Addressed objects and pattern scopes

`auth.md`'s pattern scopes narrow a credential within one repository by matching the object each
request addresses, and the format declares which object each route reports ("Pattern scopes"
there; `format-handler-interface.md` AC12). There is no name-enumerating route.

| Route | Object kind | Canonical object |
|---|---|---|
| Catalog, either path | named | `{org}/{name}` |
| Box file (hosted or proxied) | named | `{org}/{name}/{version}` of the file the path resolves to; provider and architecture are not part of it |
| Publish a version, add a provider file (management API) | named | `{org}/{name}/{version}` |
| Set a default architecture, delete a provider file or version (management API) | named | `{org}/{name}/{version}` |
| Delete a box (management API) | named | `{org}/{name}` |

What that gives, applying `auth.md`'s rules rather than re-deciding them. **A patterned `pull`
works end to end**, unlike the index-driven formats: `acme/base/**` matches both `acme/base` and
`acme/base/1.0.0`, since `**` matches zero segments, so both lines add and update `acme/base`
under it and are refused on `acme/other`. A pattern naming only versions (`acme/base/1.0.0`) cannot
read the catalog and fails at the probe, and `acme/*` reads the catalog and is refused the box;
the operator documentation recommends the `{org}/{name}/**` and `{org}/**` shapes. **A patterned
`push` publishes** in-pattern versions and is refused an out-of-pattern one with no snapshot, and
a patterned `delete` likewise.

### Policy refusals on the wire

When a shared resolution call returns the typed refusal `supply-chain-policy.md` defines, on a box
route of either path, the handler answers `403` with a JSON body
`{"errors": [{"status": "403", "title": "...", "detail": "..."}]}` naming the policy and rule, to
**`HEAD` and `GET` alike**, and nothing else changes: the catalog still lists the version, so
`vagrant box outdated` stays truthful. The response is written through the shared refusal writer
`WriteRefusal(w, r, refusal, body)` in `internal/format` (`format-handler-interface.md` AC14;
`supply-chain-policy.md`, its resolved refusal-status-line decision, was Q10), which on HTTP/1.1
puts `Refused by policy: {condition}` in the status line; for a `HEAD` the same status and headers
go out with no body. Per the resolved refusal-rendering decision below and captured on both
lines: the client prints "An error occurred while downloading the remote file ... The requested
URL returned error: 403", curl's rendering of the status code, never the body and never the
phrase, so Vagrant is among the clients to whom the reason reaches only the operator, and
`vagrant box add` exits 1. A refused box is requested once per command, so one attempt produces
one refusal record. `supply-chain-policy.md`'s "When a refusal binds, per format" table records
this format as `holds` for the reason the Fallback section gives: refusals answer `HEAD` and `GET`
alike, so a direct URL list fails at the probe.

The catalog routes never answer a policy refusal: a catalog is the box as a whole, and policy is
evaluated on version resolution, which happens at the box route.

### The proxied path

The handler owns the request and classifies for the proxy layer's fetch-and-cache API per the
settled decisions in `proxy-cache.md`. A remote repository's upstream is a **catalog root** plus a
path template for a box's catalog, defaulting to `{root}/{org}/{name}` (HCP's layout; captured
identical to the API path), with `{root}/{org}/{name}.json` as the other shape a static host
serves. Per the resolved proxied-catalog decision below, **every upstream box URL is rewritten to
this registry**, which is what makes the path a cache at all: an upstream catalog served verbatim
would send clients straight to the upstream's storage.

The transport half is `upstream-adapters.md`'s `https` adapter, whose requirements table records
what this spec asked (the row for `vagrant.md`: AC6, AC7, AC8, AC19); the path template and
everything protocol-shaped stay in this handler:

- **The catalog path template** is the handler's; the remote's optional upstream credential is a
  `bearer` (HCP's form, as Vagrant itself sends it) or `basic` upstream credential kind with role
  `root`, reaching the catalog root's host only (its "Credential scoping and the off-origin
  allowlist", AC6). An `http://` root is refused at configuration `upstream-invalid` (422) unless
  the upstream sets `allow_http` (its AC22, AC23), and no request is made at configuration: an
  unreachable but well-formed upstream is accepted (its AC23).
- **Redirect chains to an allowlist.** An HCP box URL answered `302` to another path on
  vagrantcloud.com, `302` to `api.cloud.hashicorp.com`, and `307` to an S3 presigned URL on
  `vagrantcloud-files-production.s3-accelerate.amazonaws.com` (captured). The adapter follows
  redirects inside itself, up to ten hops (Vagrant's own limit, which it adopted), only to hosts
  in the upstream's `hosts` allowlist, each entered with role `none` so no credential goes beyond
  the catalog root's host; a host outside the list makes no connection and returns
  `HostNotAllowedError`, recorded for the operator; no `Location` reaches the client, and a
  presigned target, itself a credential expiring in 900 seconds (captured `X-Amz-Expires`), is
  never recorded as provenance or cached, the requested location is (its "Redirects", AC7, AC8).
  An operator proxying HCP enters the two redirect hosts above; the list is empty by default
  (its AC7).
- **Conditional revalidation where the upstream supports it**: the adapter returns the upstream's
  validators verbatim, and HCP sends `cache-control: no-store, max-age=0` and neither `ETag` nor
  `Last-Modified` (captured), so revalidating an HCP catalog is an unconditional `GET` after the
  TTL; a static host's validators are used when present. The upstream's `no-store` is not
  honoured as "do not cache", since a cache is what the remote is.
- **Range pass-through is not required**: a miss fetches the whole box, and ranges are served from
  the CAS once it is committed.

Classification and behaviour:

- **The catalog is mutable metadata with the proxy layer's TTL.** A new revision is parsed and
  handed to the generator's `FromUpstream` (`signing-service.md`, "The proxied path", its AC20),
  whose output is stored as the remote's current document, unsigned, and served through the same
  `ServeDocument` and serve-time expansion as a hosted catalog, with the cache-scoped record in
  place of the pointer's (`proxy-cache.md`, "Freshness of what a remote serves"; under this
  profile's `ETag`-only rule no `Last-Modified` is served on either path). The revision's `name`
  must equal the requested name byte for byte or the request answers `404` (the name rule above;
  HCP echoes a requested case, captured); every entry's `url` is replaced by this registry's box
  route for `(version, provider, architecture)`, `unknown` standing for an absent architecture;
  every other field is kept as the upstream wrote it, order included, so a pre-2.4 client selects
  through this registry exactly what it would select from the upstream. Caching a box whose
  upstream entry had no checksum re-runs `FromUpstream` for that box's catalog with the
  verification record, which is how the SHA-256 appears once cached (below).
- **Entries this registry cannot serve are omitted and recorded**: an entry whose upstream URL is
  not `https` (or `http` where the remote allows it), such as a relative path or `file://` that
  the client would read from its own disk (captured), and a version carrying two entries with the
  same `(provider, architecture)`, are left out of the rendered document and named in the
  operator record; the rest of the revision serves.
- **Checksums.** An upstream entry with a checksum keeps it. An entry without one (every HCP
  bento entry, captured) carries, once its box is cached, this registry's SHA-256 with
  `checksum_type: "sha256"` in the rendered document (the resolved proxied-checksum decision
  below), because a client resuming across a change of bytes installs a spliced box when there is
  no checksum (captured).
- **Boxes are immutable artifacts.** A box request resolves its route to an upstream URL through
  the current or a retained cached revision; a route no revision names answers `404` with no
  upstream request, so the remote is not an open relay. When the upstream entry carries a
  checksum, the fetch is stream-and-verify against it as a declared digest set, through the box
  integrity entry above. When it carries none, fetch-and-cache refuses a request with neither a
  digest nor a verifier, so the first fetch uses `proxy-cache.md`'s completion-only mode (its
  resolved completion-only decision, was Q15, AC20) with a structural verifier this handler
  supplies, the same checks `Apply` makes at publish: the spooled body is one of the three archive
  forms and holds a `metadata.json` at its root whose `provider` equals the entry's provider and
  whose `architecture`, when present, equals the entry's. The initiating client streams, and its
  response completes only after the verifier passes; a refusal closes it short and commits
  nothing. The first committed fetch then binds the coordinate to its CAS digest, and any later
  fetch of it (after eviction) is a declared-digest fetch against that digest, so other bytes are
  never committed and are recorded as an immutability violation (the removal table). A body the
  adapter reports `ErrTruncated` or `ErrStalled` on is never committed.
- **A resuming client on a miss waits for the flight.** A client interrupted during the
  initiating fetch of a multi-gigabyte box does not cancel it (`proxy-cache.md`, "Miss
  coalescing": the flight owns its lifecycle), and its resume, a `Range` request, joins as a
  waiter and is answered from the CAS after the verified commit, never forwarded upstream as a
  range.
- **Missing resources are negatively cached** with the short TTL on `404` and `410`; a `429` or
  `5xx` is never cached as absence (`proxy-cache.md` AC9). HCP's not-found body is
  `{"code":5,"message":"box not found","errors":["box not found"]}` (captured).
- **Publish and every management operation against a remote repository answer `405`** with
  problem type `repository-type` (`management-api.md`, "Hosted only").

Upstream removal maps onto the event classes of `proxy-cache.md`'s "Upstream removal or
replacement", as this format's side of that contract; each row names the class. Nothing on the
Vagrant wire is a security signal: a version that disappears from a catalog (an HCP revoke or
delete) says nothing about why.

| Upstream event, as observed at revalidation or fetch | Classification |
|---|---|
| A version or provider entry leaves the catalog | **Removal with no signal**: the rendered catalog follows the upstream, the cached box stays fetchable at its route for clients holding the older catalog and is then evictable, and the divergence is recorded and alerted |
| A new revision lists a different checksum, or a different upstream URL, for a coordinate already cached | **Immutability violation, revision-bound**, in the variant `terraform.md`, `puppet.md` and `homebrew.md` chose (cached bytes kept, divergence recorded and alerted): the route keeps serving the cached bytes, whose checksum the rendered document keeps, and the new upstream bytes are never fetched under the old coordinate, because one URL serves every client and the resume file is keyed on it |
| A re-fetch after eviction of a coordinate with no upstream checksum produces bytes other than those first bound | The same immutability violation; the declared-digest fetch commits nothing under the coordinate and the operator decides |
| A box fails its upstream checksum or the structural verifier, or a body is truncated | **Integrity failure at fetch**: nothing committed, no negative entry, the operator is alerted with the real reason, the next request tries again |

**The migration path off a retiring upstream**, in three steps, the second added by
`replication.md`'s resolved HCP-deadline decision (was Q11 there):

1. **Sync before the deadline.** A remote over HCP Vagrant set to the `immediate` download policy
   (`data-model.md`, "Download policies"; its AC24) fetches every version's boxes of every box
   whose catalog it holds ahead of any request. The Vagrant wire has no listing of box names, so
   the recipe first reads each box's catalog through the remote (one `curl` of the catalog URL, or
   one `vagrant box add` per box), which is what puts the box in the remote's cache for the sync
   to cover.
2. **Freeze the remote `read_only`.** A `read_only` remote does no fetch, no revalidation and no
   eviction and serves its cache indefinitely (`repository-lifecycle.md`, "Read-only";
   `proxy-cache.md` AC23), so it neither revalidates against a dead upstream after
   December 31, 2026 nor evicts what the sync fetched.
3. **Freeze into a `local` repository** (`data-model.md` AC30; `replication.md`'s freeze, Phase 4
   at charter step 10) whenever that phase lands, which turns the cached content into hosted
   content with generated catalogs, SHA-256 checksums and immutable routes; after that no request
   depends on the upstream. Until then the content serves as a cache-only remote, the accepted
   cost that decision records.

The operator documentation gives this recipe with HCP's end-of-operations date, and the
conformance suite proves all three steps against a stand-in (AC21). Recording the vagrantcloud.com
corpus while HCP still operates is a dated commitment carried in `docs/internal/HANDOFF.md`.

### Advisories, OSV and the security-signal rule

OSV has no Vagrant ecosystem (captured `invalid ecosystem`), no Vagrant catalog carries an
advisory, deprecation or quarantine field, and no upstream removal carries a reason, so **the
shared security-signal rule never fires for this format from either channel**, and an
advisory-dependent coordinate rule attached to a Vagrant repository is refused at configuration,
as `supply-chain-policy.md` refuses any rule that cannot bind (its coverage table's Vagrant row,
AC17), unless an operator declares an advisory source in the OSV schema that lists a Vagrant
ecosystem (its resolved advisory-sources decision, was Q9), of which none is known. Coordinate rules that need no
advisory (a name or version pattern) bind on both paths. Byte-level rules depend on the shared
cataloguer's coverage of box archives and the provider disk formats inside them, which that spec
decides; where it does not cover them, byte-level rules are refused at configuration rather than
accepted and unenforced (the resolved advisory decision below). Detection is passive, per
`proxy-cache.md`'s resolved signal-detection decision (was Q12).

Per the resolved preconfigured-upstream decision below, no Vagrant upstream is preconfigured.

### Virtual repositories

A Vagrant catalog names nothing but the box and its URLs, and carries no signature, so a
`virtual` Vagrant repository is expressible with no re-signing: the catalog is served, like
every other, with this registry's URLs. Per the resolved virtual-catalog decision below (was
Q13):

- **Resolution is per box name, in member order, at request time**: the first member holding any
  version of `{org}/{name}` supplies the whole catalog, and later members' versions of that name
  are not merged in. A `local` member holds the name when its head has the box's generated
  catalog; a `remote` member is asked through its own fetch-and-cache path, so a proxied box
  nobody has requested before resolves through the virtual on its first request. The supplying
  member's stored document (its generated catalog, or the remote's `FromUpstream` output) is
  served through `ServeDocument` with the serve-time expansion under the virtual's own mount and
  name, so the virtual's box routes are its own and resolve through the member that supplied the
  name. There is no stored merged document, no `Merge` in the generator's profile and no
  `index.merge` job, which is why a member's publish is visible through the virtual at the next
  request rather than within a merge window.
- **This is where a virtual repository earns its place for Vagrant.** One
  `VAGRANT_SERVER_URL` names one server, so shorthand names can resolve on one repository only; a
  virtual repository over a hosted repository and a remote puts private and proxied boxes behind
  one shorthand namespace, with private names shadowing public ones.
- A publish or management operation against a virtual repository answers `405` with problem type
  `repository-type`.

### Capabilities and rename

`Capabilities()` declares proxy support `supported`, reference-implementation availability
`available` (the pinned static server named below), `Virtual: supported` and `Rename: supported`
(`format-handler-interface.md` AC13). Rename is supported under `repository-lifecycle.md`'s rule
for handlers whose served documents embed the name ("Renaming"): every catalog is stored with
relative URLs and expanded at serve time under the repository's current name, so a rename changes
every served URL at the next request with no snapshot. The client-side cost is that spec's
accepted one (its resolved rename-alias decision, was Q2), in Vagrant's shape: the `metadata_url`
each client stored at add time names the old repository, so `vagrant box update` and `outdated`
fail with the client's not-found line until the box is re-added from the new name, and a partial
download is restarted from zero because the resume file is keyed on the old URL. The case the
harness requires of every format (`conformance/vagrant/rename_test.go`, `repository-lifecycle.md`
AC12, presence enforced by `conformance-harness.md` AC26) proves both halves on both lines (AC26).

### Conformance, the clients and the corpus

The two pinned lines differ in ways the captures made concrete: 2.3.7 takes the last entry per
provider, ignores architecture fields, probes one shorthand path and stores it, and embeds curl
7.87.0; 2.4.9 matches the host architecture, probes two shorthand paths and stores the API path,
refuses a catalog that has no entry for the host's architecture ("doesn't support the provider
you requested", captured with an `arm64`-only box on an `amd64` host, which 2.3.7 installed), and
embeds curl 8.10.1. The catalogue counts one ecosystem; both lines appear in the matrix's Client
column under the Vagrant row, and every hosted and proxied case runs on both unless it names a
line-specific behaviour.

**Every case runs with the client's network restricted to this registry and its stand-ins**,
except the recording session: `conformance-harness.md` confines every client container to the
case network (its resolved client-confinement decision, was Q6, AC23), and the second host AC15
needs, and the redirect hosts of an upstream stand-in, are `hosts` sub-entries of its `upstreams`
entry that resolve inside the client container (AC23 there). No official image exists, so the
harness builds the client image itself exactly as this draft built them, a HashiCorp `.deb`
verified against its release `SHA256SUMS` installed into the pinned Debian base, with the recipe
in the case directory, and each case pins the **built** image by its digest (`conformance-harness.md`
AC4, naming this spec). Each case
appends the harness CA to `/opt/vagrant/embedded/cacert.pem`, the bundle Vagrant's curl uses,
sets `VAGRANT_CHECKPOINT_DISABLE=1` as every capture in this draft did, gives each client a fresh
`VAGRANT_HOME` unless the case continues one (update, resume), passes `--provider` so no prompt is
reached, and budgets the five-second custom-server pause on authenticated cases.

The recorded surface for the replay corpus: against vagrantcloud.com, a public box's catalog at
both paths with `HEAD` and `GET`, a missing box, and one box download's redirect chain with a
range of its final object, recorded while HCP still operates. The reference implementation for
the hosted side is the self-hosting shape HashiCorp's deprecation guidance points users to: a
pinned static server over a hand-authored catalog and box files, so `Capabilities()` declares
reference-implementation availability `available`. The write surface has no reference, an
exception-list entry. Recording gates on the harness's redaction criterion
(`conformance-harness.md` AC13), whose rule for this format names the `Authorization` header, URL
userinfo, the `access_token` parameter and presigned query strings. Deliberate divergences go on
the exception list before their flow is expected to replay: the rewritten box URLs, the added
SHA-256 checksums, the default-last ordering where an upstream orders otherwise, `Cache-Control`
on catalogs, byte-exact name matching where HCP folds case, `405` on remote writes and `409` on
republish.

### Resolved: which entry a pre-2.4 client receives (was Q1)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: the index service groups
each provider's entries within a version with the default architecture's entry last (Design,
"What the index service must provide", item 2; AC3).

The question: 2.3.7 ignores `architecture` and `default_architecture` and keeps the last entry
per provider name (source and capture), so the document's order alone decides what a 2.3 host
installs, and HashiCorp's documentation says the default flag decides it.

**Recommendation:** A. It makes the documented promise true for the documents this registry
generates, at no cost to 2.4 clients, which select by architecture whatever the order (captured
in both orders); publish order would install whatever was uploaded last on every 2.3 host, which
is how 2.3.7 put an `arm64` box on an `amd64` host in the capture.

| Option | You get | It costs |
|---|---|---|
| **A. Default architecture last, per provider** | 2.3 hosts receive the publisher's chosen default; the documented behaviour holds | A reorder when the default changes, which is already a write |
| **B. Publish order, as HCP serves** | Byte-likeness to HCP's documents | 2.3 hosts receive the last-uploaded architecture |
| **C. Omit non-default architectures for pre-2.4 user agents** | Exactly one entry per provider for old clients | A per-request variant keyed on a header, and a stored document that is no longer the served one |

**Why this is yours:** it fixes what every pre-2.4 user of a multi-architecture box gets.

Accepted cost: the proxied path cannot apply it (it keeps upstream order so selection matches the
upstream's), which the exception list records.

### Resolved: how private box downloads are authorized (was Q2)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: the Bearer form
(`VAGRANT_SERVER_URL` plus `VAGRANT_CLOUD_TOKEN`) is the recommended and only complete form for a
private repository; URL userinfo authenticates catalog reads only; no credential or capability is
written into a box URL (Design, "Authentication", "Every catalog is a generated per-box document";
AC4, AC11, AC12).

The question: the Basic form's credential never reaches the box URLs a catalog names (captured),
`terraform.md` solved the same gap with a download capability in the URL, and Vagrant names its
resume file by the SHA-1 of the URL (box_add.rb).

**Recommendation:** A. A per-request capability changes the box URL on every catalog read, so
every resume after an interrupted multi-gigabyte download would start from zero; the Bearer form
is preemptive on the catalog and the box, never persisted to disk by the client, and uses the
variable Vagrant already documents for custom servers.

| Option | You get | It costs |
|---|---|---|
| **A. Bearer via `VAGRANT_SERVER_URL`; userinfo for catalogs only** | Stable box URLs, so resume works; no credential on the client's disk | A five-second warning pause per process; one token reaches every repository on the host, so multi-repository users need the opt-in token |
| **B. `terraform.md`'s download capability in box URLs** | Userinfo users can download | Resume never works for authenticated users |
| **C. Echo the caller's userinfo into box URLs** | Userinfo works end to end | The credential in a response body, against `auth.md` AC7's intent |

**Why this is yours:** it sets the recipe every private-registry user copies.

Accepted cost: the operator documentation explains the pause, the host scoping and the
multi-repository token.

### Resolved: whether a box file can change after publish (was Q3)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: a `(version, provider,
architecture)` coordinate binds one set of bytes for the life of the repository; different bytes
are refused with `409`, deleted coordinates are retired (Design, "The hosted publish path";
AC6).

**Recommendation:** A. A client resuming across a change of bytes splices two files, and without
a checksum installs the result (captured); the cross-format retirement rule already says a
coordinate binds one set of bytes.

| Option | You get | It costs |
|---|---|---|
| **A. Immutable coordinates, retired on delete** | Resume is always safe; dedup and caching are sound | A fixed box needs a new version number |
| **B. Replace allowed, as HCP's provider update allows** | In-place fixes | Silent splicing for any client mid-download, and caches holding stale bytes under a live URL |

**Why this is yours:** it trades a publisher convenience against download integrity.

Accepted cost: the new-version rule in the publisher documentation. Reconciled 2026-09-28: the
identical-bytes republish this record first allowed as a no-op is replaced by
`management-api.md`'s `Idempotency-Key` replay (its AC17), which gives the CI-retry case the same
guarantee through the API's own mechanism; a keyless publish of an existing coordinate is
refused `conflict`, and a retired coordinate `retired`, through the core-held `Retirement` record
(its resolved retirement-placement decision, was Q3).

### Resolved: the write boundary of a multi-provider publish (was Q4)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: one publish carries one
version with one or more provider files and is one write with one regeneration; adding a provider
file later is its own write (Design, "The hosted publish path"; AC6, AC8).

**Recommendation:** A. A 2.3 client reading a version that has only its first uploaded
architecture installs that one (captured last-entry rule), so a version published provider by
provider is briefly wrong for old clients; one write per version closes that window, and the
upload sessions keep the write itself small.

| Option | You get | It costs |
|---|---|---|
| **A. One version, many files, one write** | Atomic versions; no window with a partial provider set | A publish names several committed uploads |
| **B. One file per write** | The simplest API | A regeneration and snapshot per file, and a partial version visible between them |

**Why this is yours:** it fixes a management-API shape that `management-api.md` inherits.

Accepted cost: recorded for `management-api.md`, which adopted it: its "Publish through the API"
is fixed by this format's scale finding, and a batch publish is one write.

### Resolved: the version grammar at publish (was Q5)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: `X.Y.Z` of non-negative
decimal integers without leading zeros, HCP's documented form with zero allowed as `1.0.0` needs (Design, "Names, versions
and case"; AC6).

**Recommendation:** A. The client compares with `Gem::Version`, under which `1.0` equals `1.0.0`
(captured ambiguity) and a prerelease outranks the release before it under the default constraint
(captured), so accepting the client's whole grammar lets one publish silently become every
user's default; `X.Y.Z` without leading zeros makes byte equality and client equality coincide.

| Option | You get | It costs |
|---|---|---|
| **A. `X.Y.Z` only** | One spelling per version; no accidental prerelease defaults | Publishers who used other forms on a private host must renumber |
| **B. Any `Gem::Version`, refusing only client-equal duplicates** | Every form the client accepts | Prereleases become the default install |

**Why this is yours:** it decides which version strings the registry accepts.

Accepted cost: the renumbering note; proxied catalogs keep whatever their upstream publishes.

### Resolved: box name matching (was Q6)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: names match byte for byte;

**Recommendation:** A. The client stores the box under the document's `name` and refuses a

| Option | You get | It costs |

**Why this is yours:** it decides whether migrated Vagrantfiles need editing.

Accepted cost: the migration note naming HCP's folding.

### Resolved: rendering a box policy refusal (was Q7)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: `403` with the

**Recommendation:** A. It is the cross-format rendering; answering `HEAD` too is what stops a

Accepted cost: the operator documentation explains the client's message.

### Resolved: what a proxied catalog serves (was Q8)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: every upstream field and

**Recommendation:** A. Rewriting is what makes the remote a cache, since HCP's box URLs lead to

| Option | You get | It costs |

| **B. Serve upstream catalogs verbatim** | Byte-identical documents | Clients download from the upstream directly, so nothing is cached |
| **C. Regenerate in this registry's canonical order** | One document shape everywhere | 2.3 clients select differently through the cache than from the upstream |

**Why this is yours:** it decides whether the proxy changes what users install.

Accepted cost: the operator record of omitted entries.

### Resolved: checksums on proxied boxes with none upstream (was Q9)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: once a box is cached, the
rendered catalog carries its SHA-256; before that, the entry carries whatever the upstream
published (Design, "The proxied path"; AC17).

**Recommendation:** A. HCP publishes no checksum for the most used public boxes (captured bento),

bytes are immutable at this registry's route, so the checksum can never be wrong for them.

| Option | You get | It costs |
|---|---|---|
| **A. Fill SHA-256 once cached** | Client-side verification for every cached box | The rendered catalog changes when the cache fills |
| **B. Pass the upstream's absence through** | A catalog that never changes by caching | No client verification of the most used boxes |
| **C. Fetch every box before serving its catalog** | A checksum on every entry from the start | A multi-gigabyte fetch per box before any catalog read answers |

**Why this is yours:** it decides whether the cache adds integrity the upstream lacks.

Accepted cost: a rendered document that varies with cache state, recorded on the exception list.

### Resolved: HCP Vagrant's publishing API (was Q10)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: the management API is the
only hosted write path; HCP's API v2 is not served in v1, and the captured `vagrant cloud publish`
sequence is handed to `management-api.md` as an input (Scope; Blocking preconditions).

The question: `vagrant cloud publish` is the ecosystem's only client that publishes, and it speaks

`.../upload` without the completion call instead (source, and captured with

**Recommendation:** A, for reasons other than effort: the staged model (an unreleased version,

constitution forbids a handler to add; 2.3.7's `vagrant_cloud` 3.0.5 drops the `/api/v2` prefix

compatibility surface would serve two path shapes for one API; and HashiCorp is retiring the API, so it has no maintainer to follow.

| Option | You get | It costs |

| **A. Management API only; the sequence recorded for `management-api.md`** | One write path; no un-modelled staging state | Publishers script against this registry's API instead of `vagrant cloud publish` |

**Why this is yours:** it decides whether migrating HCP users keep their publish tooling.

Accepted cost: `management-api.md` weighs a compatibility surface with the captured sequence in

(was Q8) declines HCP's API v2 for this record's reasons (staging state with no entity, a
credential-bearing upload URL, two path shapes, a retired contract).

### Resolved: how a virtual catalog is produced when a member is remote (was Q13, raised and adopted 2026-09-28)

**Adopted 2026-09-28 under the owner's standing delegation.** Option A: a virtual repository's
catalog for a box is resolved at request time, first member in order holding the name, and the
supplying member's stored document is served through `ServeDocument` under the virtual's own URLs;
the generator declares no `Merge` and no `index.merge` job runs (Design, "Virtual repositories";
"What the index service must provide", item 5; AC22). Folded through Scope, Blocking
preconditions and Phase 4.

The question: this spec asked the index service for a virtual merge "re-run when a member's box
changes", and `signing-service.md` built its virtual merge as a deferred, coalesced `index.merge`
job over the members' **current document sets** ("Virtual merges"). A remote member's current
documents are only the catalogs it has already cached, because the Vagrant wire has no listing of
box names, so a stored merge would omit every proxied box nobody had requested through the remote
before, which is exactly the shorthand case a Vagrant virtual exists for (Design, "Virtual
repositories"). `async-operations.md` meanwhile records this spec among those that ask nothing of
the queue.

**Recommendation:** A. Per-name first-member resolution is a lookup, not a merge (no document
combines two members' entries), so storing it buys nothing, and resolving at request time makes a
never-requested proxied box reachable and a member's publish visible without a merge window.

| Option | You get | It costs |
|---|---|---|
| **A. Resolve per name at request time; no stored merge** | Every proxied box reachable through the virtual on first request; a member's change visible at once; no queue dependency | A virtual catalog request costs a lookup per member in order, and a remote member's miss is an upstream fetch on the request path, as it is on the remote itself |
| **B. The stored `index.merge` over current document sets, as first requested** | The service's merge contract used as written | A proxied box absent from the virtual until something requests it through the remote; a staleness window on every member change; a queue dependency this format otherwise lacks |
| **C. Stored merge, with a request-time fallback for names the merge lacks** | Stored documents for known names | Two resolution paths whose answers can disagree for one name |

**Why this is yours:** it decides what a user sees through the one shorthand namespace a Vagrant
virtual repository exists to provide.

Accepted cost: the per-member lookup on each virtual catalog request, and the serve-time
expansion under the virtual's name riding the same `ServeDocument` gap as the hosted catalog.
