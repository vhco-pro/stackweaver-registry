# Plan: LuaRocks format

The LuaRocks rocks-server protocol, hosted, proxied and virtual: a set of per-Lua-version
manifests the client downloads whole and executes as Lua, rockspec and rock files addressed by
name and version relative to the server URL, detached `.asc` signatures, and the luarocks.org
upload API `luarocks upload` drives with an API key carried in the URL path. LuaRocks 3.13.0 on
Lua 5.4 and LuaRocks 3.8.0 on Lua 5.1 are the oracles on both paths, with 3.13.0 on LuaJIT as a
third manifest-selection case.

## Context

LuaRocks sits in Tier 3 of `formats/catalogue.md` as the single-ecosystem family "LuaRocks".
**Its build is gated by `project-charter.md` AC9 and `catalogue.md` AC5**: no handler code for a
Tier 3 ecosystem exists before every Tier 1 format has met its definition of done and the owner
has recorded a `continue` verdict at the charter's build step 8. This spec exists now because the
owner directed on 2026-09-26 that all 33 ecosystems be specced up front (the catalogue's "Every
ecosystem below is specced now; only building is gated"), so the gate decides what is built and
never what is written; a `shrink` verdict parks it.

The rocks-server format has **no protocol specification beyond the client's own code**. A rocks
server is a directory of files a static web server can serve, whose manifests the client's
`luarocks-admin make-manifest` writes; the upload API is whatever luarocks.org (the Lapis
application `luarocks/luarocks-site`) answers. So the grounding for this draft is captured traffic
first and source second, stated up front because the constitution asks for evidence or silence:

  finds nothing), so the clients ran in images built on digest-pinned Debian bases:
  LuaRocks 3.13.0 (released 2026-01-28, the current release) built from its source tarball
  (SHA-256 `245bf6ec560c042cb8948e3d661189292587c5949104677f1eecddc54dbe7e37`) against Lua 5.4.7 on

- **The live upstream.** luarocks.org sampled on 2026-09-27: `manifest-5.4` is 4,148,406 bytes of

  (rockspec only); manifests carry `Last-Modified` and no `ETag`, answer `304` to
  `If-Modified-Since`, and answer `HEAD`. Files carry `Last-Modified`, `Cache-Control: public,
  max-age=3600` and an `ETag` equal to the body's MD5 (`luasocket-3.1.0-1.src.rock`, 398,081
  bytes, MD5 `8d751ccc...`). File names are lowercase although the rockspec says
  `package = "LuaSocket"`, and `LuaSocket-3.1.0-1.rockspec` answers `404` (an HTML body). A `/dev/`

- **The incident.** luarocks.org's page "LuaRocks.org Security Incident, September 2026" (live,
  and `static/md/security_incident_september_2026.md` in the site source) reports a remote code

  rockspec is uploaded, LuaRocks.org runs it in a restricted environment to read the package's
  name and version. The function used to load it accepted precompiled LuaJIT bytecode". Every API
  key was revoked, three malicious packages were removed, and users are told that "LuaRocks
  3.11.1 and older on LuaJIT or Lua 5.1 will run precompiled bytecode if a server sends it in
  place of a rockspec or manifest". The fix (`2719f97`, 2026-09-26) loads text only; the site
  still evaluates every uploaded rockspec in a hooked coroutine (`parse_rockspec`).
- **A rockspec sample.** 400 rockspecs, the lexicographically highest version of 400 names drawn
  at random from the live `manifest-5.4.json`, were checked against the static reading rule this
  spec adopts, with a Lua lexer and no evaluation (Design, "Reading an uploaded rockspec").
- **OSV.** `ecosystems.txt` lists no LuaRocks ecosystem, `LuaRocks/all.zip` answers `404`, the
  query API answers `{"code":3,"message":"invalid ecosystem"}` for `LuaRocks`, `luarocks` and
  `Lua`, and a purl query for `pkg:luarocks/luasocket@3.0rc1-2`, and for the incident's malicious
  `pkg:luarocks/bcrcewon`, returns `{}`, although the purl specification defines the `luarocks`
  type (`types/luarocks-definition.json`).

Where the sources and the captures disagree, the captures win, and the disagreements are recorded
because they would otherwise be built from the source. `download_with_mirrors` reads as a clean
fall-through to the next mirror; on 3.13.0 it crashes ("LuaRocks 3.13.0 bug ... fetch.lua:144:
attempt to concatenate a nil value (local 'name')", captured) and on 3.8.0 it fetches the refused
file from the mirror (captured). And `manif.load_manifest` lists the unversioned `manifest` as a
candidate, but a remote search passes `versioned_only`, so no captured client ever asked a server
for it.

Six things make this format worth a careful spec. **The index is Lua the client executes**, a
repository-wide document generated per Lua version, which the upstream's own server produced by
evaluating uploaded Lua and was compromised through, and which an older client executes even as
bytecode (captured on 3.8.0): the registry must generate it from records it read without
evaluating anything, and must never relay an upstream's Lua to a client. **Nothing downloaded is
checked by default**: a tampered rock installed and ran its payload on both clients (captured),
the only default check being that a rock's embedded rockspec names the requested version.
**The client unions every configured server and takes the highest version**, and falls through
to the next server when ours refuses the manifest (captured, with luarocks.org behind every
`--server` by default), the dependency-confusion shape. **A rollback is adopted by the next
`luarocks install`, unless a `304` hides it** (both captured), so `Last-Modified` is part of the
rollback contract. **A rockspec-only version sends the client to a third-party host** for its
source (captured, live), outside anything the registry can cache or refuse. And **the upload
credential travels in the URL path**, which the client silently downgrades to plain HTTP when
LuaSec is missing (captured) and prints in its errors (captured).

## Blocking preconditions

**The handler interface re-open must complete before this handler starts**, as for every
handler (`format-handler-interface.md` AC8). LuaRocks is Tier 3, so the catalogue's Tier 1 gate
(its AC5) and the charter's breadth verdict (its AC9, build step 8) both precede it; the re-open
is recorded here anyway, from this side, because a gate enforced on one side only is enforced
nowhere.

**The shared signing and index service must be `planned` before Phase 1.** Every manifest is a
write-triggered generated document produced by `docs/internal/plans/foundation/signing-service.md`
(to be authored in the spec loop), which the charter builds at step 7 as the production form of
what the step 4a prototype learned. What this format requires of that service is stated in
Design ("What the signing and index service must provide"), never designed here; nothing is asked
of its signing half, because nothing on this wire is signed by a server.

**The data model must carry a monotonic per-pointer change time before Phase 1 serves a
manifest.** The resolved `Last-Modified` decision below derives every manifest's `Last-Modified`
from the moment the serving pointer last changed, by a write or by a repoint, strictly increasing
at one-second resolution. That is a field on the existing `Pointer`, raised as a revision of
`data-model.md` and compatible with the pointer's last repoint time `conan.md` raised for its
revision times; never a table this handler owns.

**`auth.md` must accept a registry token as a URL path segment on the upload routes before
Phase 2.** `luarocks upload` has no other place to put a credential (Design, "Authentication").
That is a fifth presentation form, raised as a revision of `auth.md`, never assumed here; until
it lands, hosted repositories are populated through the management API only.

**The management API must be `planned` before Phase 3.** Removing a version, a package or one
rock of a version are operations of `docs/internal/plans/foundation/management-api.md` (to be
authored in the spec loop), whose core the charter builds at step 2 and completes at step 9; no
LuaRocks client command reaches a server over HTTP to remove anything.

**The proxy layer must offer a completion-only fetch with a handler-supplied verifier, and the
upstream adapters a rocks-server adapter, before Phase 4.** No LuaRocks manifest carries a digest,
so what binds a rock or rockspec is a check the handler can compute only over the complete body
(Design, "The proxied path"). The completion-only mode is already requested of `proxy-cache.md` by
`go-modules.md`, `nuget.md`, `conan.md` and `chef.md`, the verifier hook by `conan.md` and
`chef.md`; this spec adds no new shape to that request. The adapter, which revalidates manifests
with `If-Modified-Since`, prefers an upstream's `.json` manifest and follows the `/dev/` and
`/manifests/{user}/` trees, is requested of `docs/internal/plans/foundation/upstream-adapters.md`
(to be authored in the spec loop; charter step 4).

Nothing is required of `docs/internal/plans/foundation/async-operations.md` (both upload requests
complete inside themselves, captured). Of `docs/internal/plans/foundation/artifact-verification.md`
(to be authored in the spec loop; charter step 4b) this format asks only an optional verdict
source (Design, "Signing, provenance and policy"); v1 does not depend on it.

## Scope

**In scope:**

- The rocks-server read surface under the format-first mount `/luarocks/{repository}/`:
  `manifest-{5.1..5.5}` in Lua, `.zip` and `.json` encodings, the unversioned `manifest` in the
  same three, the `/dev/` tree of each, rockspec files, rock files of any arch, and `.asc`
  signature files; `GET` and `HEAD`.
- Manifests as write-triggered, unsigned, repository-wide documents: a record set regenerated
  inside every write that changes it, stored, restored by a repoint, merged for a virtual
  repository, and rendered into every encoding by the shared service with a data-only serializer.
- A non-evaluating reader for uploaded rockspecs, rockspecs inside uploaded rocks, and upstream
  Lua manifests: the registry never executes Lua, on either path.
- The luarocks.org upload API under the same mount: `api/tool_version`, `api/1/{key}/status`,
  `check_rockspec`, `upload` and `upload_rock/{id}`, with signature parts; the write-boundary
  declaration `data-model.md` requires; immutability of a version's rockspec and of each rock;
  retirement of removed versions.
- Private reads by a registry token presented as Basic after a challenge, and uploads by a
  registry token in the URL path; the uniform challenge; per-route addressed objects and the
  pattern-refusal case `auth.md` AC8 requires; the rendering of a shared policy refusal.
- Removal of a version, a package and a single rock as bindings onto registry-owned management
  operations.
- `Last-Modified` derived from the serving pointer so a rollback or promotion reaches a client
  holding a newer manifest.
- The development split: `scm`, `cvs`, `svn`, `git` and `dev` versions listed only in the `/dev/`
  manifests.
- The proxied path against luarocks.org or any rocks server: classification per route, manifests
  parsed and regenerated rather than relayed, completion-only verification of every rock and
  rockspec against its coordinate, first-fetch digest pinning, `If-Modified-Since` revalidation,
  negative caching, the upstream's `/dev/` and `/manifests/{user}/` trees, and this format's rows
  of the removal table.
- Virtual repositories with per-name member-ordered resolution.
- LuaRocks 3.13.0 (Lua 5.4, and LuaJIT 2.1 for manifest selection) and 3.8.0 (Lua 5.1) as the
  conformance oracles on both paths, through each client's wget, curl and LuaSocket paths where
  they differ.

**Out of scope for v1**, each with its reason, recorded because the interface spec's definition
of done requires the deliberately unimplemented surface to be named:

- **The `luarocks-admin add` and `remove` transports** (rsync, sftp, ftp: `admin/cmd/add.lua`,
  `admin/cmd/remove.lua`). They copy files into the server's directory and upload a manifest the
  client generated, which is the one document this registry must generate itself; accepting it
  would mean accepting client-written Lua as the index.
- **Hosted namespaces** (`/manifests/{user}/` on a hosted repository). A namespace names an
  upstream account that owns a package name (`Users` in luarocks-site); a hosted repository has no
  per-user name ownership to express, and author pinning is what a virtual repository's per-name
  shadowing gives registry-side (the resolved namespaces decision below). The proxied path serves
  an upstream's namespaces.
- **The web and account surface of luarocks.org**: module pages, `index.html`, endorsements,
  labels, manifests other than the root and `/dev/` (`/m/{manifest}/`), API key management,
  two-factor tokens and `verify_tfa`, audits. No pinned client reads them for resolution or
  publish; credentials are issued through `auth.md`'s own surface.
- **A server-side two-factor gate on uploads.** luarocks.org can demand an `X-TFA-Token`; the
  released clients cannot send one (3.13.0's `upload/api.lua` has no such header) and the
  unreleased client asks a human for a code. A registry token is already scoped, expiring and
  revocable (`auth.md`), which is the control this repository offers for CI.
- **The `/api/1/bearer/` convention.** luarocks-site accepts the key as `Authorization: Bearer`
  when the path segment is the literal `bearer` (commit `b09ad98`); no released or unreleased
  client sends it, so it has no oracle here.
- **Fetching or caching the sources a rockspec names.** A rockspec's `source.url` points at the
  author's host, and the client fetches it directly (captured). Rewriting it would change the
  author's bytes, so the registry serves rockspecs as uploaded; the resolved rockspec-only
  decision below gives operators an option to keep such versions out of served manifests.
- **luarocks.org as a preconfigured upstream** (the resolved preconfigured-upstream decision
  below): user-configured in v1, for sequencing.

## Design

### The wire surface, as captured

Every path hangs off the repository URL the client is given, `https://{host}/luarocks/{repository}`,
format-first per `format-handler-interface.md`'s resolved URL-shape decision. A client reads it as
a rocks server (`rocks_servers` in its configuration, `--server` or `--only-server`), and uploads
to it as `--server` for `luarocks upload`, which appends `/api/...` to whatever path it is given
(captured under `/luarocks/team`). File URLs are **relative**: the client builds every file URL
as `{server}/{name}-{version}.{arch}.rock` or `.rockspec` (`path.make_url`), so no served
document carries a URL.

| Surface | Shape, as the pinned clients send it |
|---|---|
| Manifest | `GET {base}/manifest-{lua}.zip`, then `manifest-{lua}` on any failure, never the unversioned `manifest` (captured on both clients; a remote search passes `versioned_only`). `{lua}` is the client's Lua version: `5.4` from 3.13.0 on Lua 5.4, `5.1` from 3.8.0 and from 3.13.0 on LuaJIT, which first asks for `manifest-5.1.json` (captured). One fetch per invocation, reused in memory for every dependency (captured); a copy fetched in the last 10 seconds is reused with no request (`fetch_caching`'s `.check` file) |
| Rock | `GET {base}/{name}-{version}.{arch}.rock` for the entry the client's version picker chose: a binary arch over `src`, `src` over `rockspec`. The embedded rockspec is what the client builds from; no separate rockspec request (captured) |
| Rockspec | `GET {base}/{name}-{version}.rockspec` when a version lists only `rockspec`, followed by a fetch of its `source.url` from wherever it points (captured against the second stub and, live, `github.com`) |
| Signature | `GET {file}.asc` after the file, only under `luarocks install --verify` (captured) |
| Development | `luarocks --dev` rewrites every server to `{server}/dev` (captured: `{base}/dev/manifest-5.4.zip`), and files then resolve under `{base}/dev/` |
| Namespace | `luarocks install {ns}/{name}` reads `{base}/manifests/{ns}/manifest-{lua}.zip` (captured) and resolves files under that path |
| Upload | `GET {server}/api/tool_version?current=1.0.0` before every call, its answer ignored (both clients discard `check_version`'s result; captured with it refused `401`); `GET /api/1/{key}/status` only under `--api-key` (not under `--temp-key`, captured); `GET /api/1/{key}/check_rockspec?package={p}&version={v}`; `POST /api/1/{key}/upload`, `multipart/form-data` with a `rockspec_file` part named `{name}-{version}.rockspec` (and `rockspec_sig` under `--sign`); then, unless `--skip-pack` or a development version, `POST /api/1/{key}/upload_rock/{version.id}` with a `rock_file` part named `{name}-{version}.src.rock` (and `rock_sig`). Headers: `User-Agent: LuaRocks/{version} linux-x86_64 via wget` (or `via curl`, `via LuaSocket`);
the LuaSocket upload path sends `User-Agent: LuaSocket 3.0.0`; wget adds `Cache-Control: no-cache`
and `Pragma: no-cache`, and wget and curl send `If-Modified-Since` from a cached copy (captured).
3.13.0 running as root keeps no cache between invocations unless `/var/cache/luarocks`, its root
`local_cache`, exists: nothing creates it, so each invocation used a fresh temporary cache and sent
no conditional request, and with the directory created it revalidated with `If-Modified-Since`
and was answered `304` (both captured); 3.8.0 as root caches under `~/.cache/luarocks` and
revalidates (captured).

**The two versions agree on the wire** for every read route, path spelling and status handling
above; they differ in the default server group (`luarocks config rocks_servers`: luarocks.org, the
moonrocks GitHub mirror and `https://loadk.com/luarocks/` on 3.13.0; luarocks.org, the same mirror,
`https://luafr.org/luarocks/` and the plain-HTTP `http://luarocks.logiceditor.com/rocks` on
3.8.0), in the highest Lua version `make-manifest` writes, in whether a bytecode manifest
runs, in the mirror-fallback crash, and in what the upload path needs installed.

### Five client behaviours that decide the design

**The manifest is executed, and an old client executes bytecode.** The client loads a manifest
with `persist.load_into_table`, which runs it as a chunk in an environment table. A manifest
replaced by precompiled Lua 5.1 bytecode installed normally through 3.8.0 on Lua 5.1, while 3.13.0
refused the Lua 5.4 equivalent ("No results matching query", captured), matching the incident
page's warning. luarocks.org's own server evaluated uploaded rockspecs the same way and was
compromised through it (the incident), and `luarocks-admin make-manifest` evaluates every rockspec
in the directory: a rockspec ending in `while true do end` hung it until `timeout` killed it
(captured). So **the registry never evaluates Lua and never relays Lua it did not generate**
(Design, "Reading an uploaded rockspec", "Generating the manifests", "The proxied path").

**Nothing downloaded is checked by default.** A source rock whose module was altered to run
`os.execute('echo PWNED')` installed and printed `PWNED` on `require` on both clients (captured).
What the client does check: a rock's embedded rockspec must be named for the requested version, so
the `1.0-1` rock served as `1.1-1` failed with "File not found: acme-util-1.1-1.rockspec" on both
(captured), and the client's rockspec loader refuses a rockspec whose contents disagree with its
file name. `luarocks install --verify` fetches `{file}.asc` and runs `gpg --verify` against the
user's keyring: no `.asc` fails, a signature by a key the keyring lacks fails ("Can't check
signature: No public key"), and a signature by any key it holds passes (all captured), with no
binding between signer and package. A rockspec's optional `source.md5` is checked against a
source it fetches (`fetch.lua`). This registry is therefore where a rock's identity and bytes are
bound.

**The client unions every server and takes the highest version, and falls through when ours
refuses.** `search_repos` walks every group in `rocks_servers`, and within a group the mirrors
until one answers; its version picker then takes the highest version across all of them, and
the first group's entry on a tie. With this registry first and a second server holding
acme-util 9.9-1, both clients installed 9.9-1 from the second (captured). A manifest answered
`401`, `403`, `404` or `500` is a warning ("Failed searching manifest"), and resolution continues
from the next group (captured on 3.13.0 for `401`, `403` and `500`, and for `404` under `--dev`). `--server` prepends to the default list
rather than replacing it (`process_server_args`), so luarocks.org's group sits behind any server a
user adds; only `--only-server` or a configured `rocks_servers` removes it. A failed **rock**
download in a group of its own halts the install (captured on both, with the second server
holding the same version and receiving no request for it), while inside a mirror group 3.8.0
fetched the same file name from the next mirror and installed it (captured). The consequences: a
policy refusal is `403` at the file and the manifest keeps listing the refused version, so a
resolver reaches the refusal rather than another server's copy (Design, "Policy refusals on the
wire"); the operator documentation says to configure a virtual repository as the only rocks
server, never beside luarocks.org and never as a mirror.

**A rollback is adopted, unless a `304` hides it.** After a manifest without acme-util 1.1-1
replaced one with it, `luarocks search` listed only 1.0-1 and `luarocks install acme-util`
installed 1.0-1 and removed 1.1-1 ("Removing acme-util 1.1-1... Removal successful"), on both
clients (captured); LuaRocks has no lock file that pins what an earlier install chose. But 3.8.0
revalidated with `If-Modified-Since` set to the previous manifest's `Last-Modified`, and when the
server answered `304`, as any server comparing an older restored `Last-Modified` against it would,
the client kept listing 1.1-1 (captured). So `Last-Modified` must never go backwards on a pointer
(the resolved `Last-Modified` decision below).

**A rockspec-only version leaves the registry.** When a version lists only `rockspec`, the client
fetches the rockspec and then its `source.url` (captured: the second stub received
`GET /src/acme-util-1.0.tar.gz`; live, `inspect` 3.1.3-0 came from `github.com`). 5,638 of
luarocks.org's 34,472 versions are rockspec-only, and every development version is, because
`luarocks upload` never packs one (`cmd/upload.lua`). The registry can apply policy to the
rockspec and nothing after it (the resolved rockspec-only decision below).

### What the registry verifies

On hosted ingest, and where meaningful on every proxied fetch:

1. **A rockspec is read, never run** (Design, "Reading an uploaded rockspec"): its `package`,
   `version` and `dependencies` come from the static reading rule, or the upload is refused.
2. **Names and versions are manifest-safe.** A package name matches `^[A-Za-z0-9._-]{1,255}$`,
   ASCII, and its identity is its lowercased form, as the client lowercases every query
   (`queries.lua`; `ACME-Util` resolved `acme-util`, captured) and every file name
   (`rockspecs.lua` sets `name = package:lower()`). A hosted version matches `^[a-z0-9.]+-[0-9]+$`:
   the client's schema is `[%w.]+-[%d]+` (`type/rockspec.lua`), and an upper-case letter would
   break the client's own filename check once the file name is lowercased as luarocks.org does.
   Every string that reaches a manifest passes luarocks-site's `is_valid_manifest_string` grammar
   `^[a-zA-Z0-9._-]+$`, arches included.
3. **A rock is a clean zip holding its own rockspec**: no absolute entry, no `..`, no link; its
   file name is `{name}-{version}.{arch}.rock` for the version it is uploaded to (luarocks-site's
   `parse_rock_fname` and "Rock doesn't match version"); it holds `{name}-{version}.rockspec` at
   its root, which the static reading rule reads to the same lowercased name and version.
4. **The `lua` constraint** is the first entry of `dependencies` naming `lua`, parsed under
   LuaRocks' dependency grammar and compared with its version ordering (`core/vers.lua`) against
   Lua 5.1 to 5.5, giving the set of per-Lua-version manifests the version appears in, as
   `filter_by_lua_version` computes it; no `lua` entry means every Lua version.
5. **On a proxied fetch**, the same checks bind a rock or rockspec to the coordinate the upstream
   manifest listed, and once a coordinate's bytes are committed a later fetch of it (after
   eviction) must produce the same CAS digest.

### Reading an uploaded rockspec

Per the resolved rockspec-reading decision below, the registry reads a rockspec with a Lua
**lexer and parser that build a syntax tree and never execute it**, and a constant folder over a
closed expression language. There is no interpreter anywhere in the process: the handler package
imports none and uses no cgo, which an architecture test enforces (AC4), so no input can reach a
bytecode loader, a debug hook or a memory-unsafe VM, the three things the incident and the site's
current `parse_rockspec` depend on.

The rule, which must equal what the client computes when it evaluates the same file:

- The file is at most 1 MiB of text; a leading `#!` line is skipped as the client skips it; the
  first remaining non-whitespace byte is not ESC (`\27`, the bytecode signature); it parses as a
  Lua chunk, with nesting bounded.
- `package` and `version` are each assigned **exactly once, at top level**, to a constant
  expression: string and number literals, `..` concatenation, and references to top-level
  `local` names that were bound to a constant expression and are never assigned again.
  `dependencies` is assigned at most once at top level, to a table constructor whose positional
  entries are constant expressions.
- Those three names may be **read** anywhere (`package:match(...)`, `version:gsub(...)` appear in
  real rockspecs), but are never assigned anywhere else, never declared `local`, and `_ENV` never
  appears. In the client's loading environment no library exists (the loader
  gives an empty table), so assignment to the identifier is the only way a chunk can change those
  fields; forbidding it everywhere else makes the static reading exact, whatever functions the
  rest of the file defines or calls.
- Descriptive fields (`description.summary`, `license`, `homepage`) are taken where they are
  constant, and absent otherwise.

Measured on the 400-rockspec sample: a literal-only rule accepts 281 (the nvim ecosystem's
generated rockspecs build `version = modrev .. '-' .. specrev` from locals); the adopted rule
accepts 388; of the other 12, two are misreadings by the approximating checker (a read of
`version` inside a table constructor), and 10 compute `version` with a string method
(`("%s-%s"):format(...)`, or `gsub` chains in the LaTeX packages). Those are refused on hosted
upload with an `errors[]` message naming the construct, and the uploader publishes a rockspec that
states its version; about 2.5 percent of real rockspecs, recorded as a divergence from
luarocks.org, which accepts them by running them. The proxied path never needs the rule to pass
(Design, "The proxied path").

### Mapping onto the shared model

The levels are exactly those `data-model.md` provides; no table is added.

- **`Package.name` is the lowercased package name**, or `{ns}/{name}` for proxied namespaced
  content (the resolved namespaces decision below). The package-level document holds the spelling
  of `package` as the first rockspec gave it (display only; the wire uses the lowercased name
  throughout, as luarocks.org does) and the **retirement set** of removed versions.
- **`Version.version` is the LuaRocks version string** `{version}-{revision}` exactly as served.
  The version-level document holds the statically read fields: the `lua` constraint and the set
  of Lua versions it admits, the dependency list, the descriptive fields, whether the version is a
  development version, and the arch of each rock.
- **One `File` per artifact**: `{name}-{version}.rockspec`, `{name}-{version}.{arch}.rock` for each
  arch, and `{file}.asc` beside either when a signature was uploaded, each `Blob` keyed by the CAS
  digest of the bytes exactly as uploaded and served byte for byte.
- **The repository-level document holds the manifest record set** (below) and the repository's
  `require source rocks` option (the resolved rockspec-only decision).

### Generating the manifests: a write-triggered record set

Per the resolved manifest-generation decision below, a manifest is **never written by a handler,
never produced by `luarocks-admin`, and never relayed from an upstream**. The shared service keeps
one **record set** per repository and renders every served manifest from it:

- **The record set** is `{name: {version: {arches, lua_versions, development}}}`, names in byte
  order of their lowercased form, produced inside the write that changes it (an upload of a
  rockspec, an upload of a rock, a removal). It contains no URL, because none is served.
- **The rendering** of a manifest scope (root or `/dev/`), a Lua version (5.1 to 5.5, or all for
  the unversioned `manifest`) and an encoding is a pure function of the record set: the scope
  keeps development or non-development versions, the Lua version keeps the entries whose
  `lua_versions` include it, and the encoding is one of:
  - **Lua**, in the layout `persist.save_from_table` writes (`commands = {}`, `modules = {}`, then
    `repository = {...}` with sorted keys, three-space indentation, one `{ arch = "..." }` table
    per artifact, `rockspec` first), so a rendering replays byte for byte against
    `make-manifest`'s output for the same content;
  - **zip**, holding exactly one entry named as the document without `.zip` (the client deletes
    and re-extracts that name, then loads it: `manif.load_manifest`), with a fixed entry time and
    fixed compression so the bytes depend on content only;
  - **JSON**, the same structure, for LuaJIT clients (`manifest-5.1.json` first, captured) and as
    luarocks.org serves it.
  Thirty-six documents per repository (two scopes, six Lua selections, three encodings); a
  rendering is memoised by the shared service keyed by the record set's digest, the scope, the Lua
  selection and the encoding, and can be dropped and recomputed at any time, since it is not
  snapshot state.
- **The serializer is data-only.** It writes only table constructors, the three fixed top-level
  assignments, and strings that have already passed the manifest string grammar, so no input can
  place an expression, a call or a statement in the output; a key is written bare only when it is
  a Lua identifier and not a keyword, and bracketed and quoted otherwise, the rule
  `write_table_key_assignment` applies (a package called `end` stays valid Lua; `__gc`, a real
  luarocks.org name, is a plain key). The output is text and never begins with ESC. A property
  test (AC3) loads every rendering through both real clients' loaders and through the registry's
  own reader, and requires the same records from all three.
- **Unknown Lua versions answer `404`**, as luarocks.org's route validation does
  (`one_of {"5.1", ..., "5.5"}`); a future client for a newer Lua gets "No results" until the
  generator's version list grows, which is configuration of the shared service.

**What the signing and index service must provide.** Stated so the dependency on
`docs/internal/plans/foundation/signing-service.md` (to be authored in the spec loop) cannot be
lost, and precisely enough that the service can be specced against it:

1. **Unsigned generation** of the record set from the version-level records of every current
   version, in the ordering above; nothing is signed and the service's signing half is not used.
2. **Regeneration inside the triggering write**, landing in the same completed logical write and
   the same snapshot, so no snapshot's manifest names a file the snapshot does not hold
   (`data-model.md`'s one-write-one-snapshot rule; the prototype's question 3), under the
   revision-token retry `data-model.md` makes mandatory, so two concurrent uploads both land.
3. **Incremental cost**: a write touching one package reworks that package's entries and copies
   the rest, so an upload into a luarocks.org-sized repository does not re-read every version
   record (AC20 holds the budget).
4. **Storage as CAS-backed metadata above the inline threshold** (the fourth mark root,
   `storage-and-gc.md` AC16), since a luarocks.org-sized record set is megabytes.
5. **The renderer and the data-only serializer**, for the three encodings, the two scopes and the
   configured Lua versions, deterministic and memoised; the handler never builds Lua text, which
   an architecture test enforces (AC4).
6. **`Last-Modified` from the pointer, not from the content** (Design, "Last-Modified, rollback
   and promotion").
7. **The virtual merge**, per name in member order (below), re-run when a member's record set
   changes.
8. **The same generation on the proxied path** from records parsed out of upstream manifests, so
   hosted, proxied and virtual repositories share one generator and one stored form.

### The publish path and what counts as a write

`luarocks upload` is a real client command, so publishing is in npm's and Cargo's category in
`docs/internal/analysis/management-surfaces-and-the-oracle.md`: trigger and effect are both
oracle-testable. Removal has no client trigger over HTTP (`luarocks-admin remove` is rsync only)
and is driven through the management API, PyPI's category. `data-model.md` requires each format
spec to declare its write boundaries, and per the resolved write-boundary decision below:

- **The rockspec upload is one completed logical write**: one `POST .../upload`, one snapshot
  holding the version, its rockspec file and a record set listing it with arch `rockspec`. The
  answer is luarocks-site's shape, `{"module": {...}, "version": {"id": N, "version_name": ...},
  "module_url": ..., "manifests": [...], "is_new": ...}`, where `version.id` is an opaque,
  repository-scoped identifier of the version the client echoes into the next route.
- **Each rock upload is a second, separate write**: one `POST .../upload_rock/{id}`, one snapshot
  adding the rock file and its arch. A rockspec-only version is legitimate (`--skip-pack`, every
  development version), so the two cannot be one write, and between them a resolver sees the
  version as rockspec-only, which the `require source rocks` option (below) keeps out of served
  manifests for repositories that opt in.
- **Both are synchronous**, so no `Operation` is recorded. `check_rockspec` and `status` write
  nothing.
- **A refused request writes nothing**: authentication failure (`401`), missing authorization
  (`403`, or `404` for a pattern refusal), an unreadable or invalid rockspec or rock (`400`), a
  version or rock that exists or is retired (`409`), a policy refusal (`403`). Every refusal
  carries luarocks-site's body `{"errors": [...]}` as `application/json`, which the LuaSocket
  path prints (captured).
- **A version's rockspec is immutable, each rock is immutable, and a removed version is retired.**
  luarocks.org replaces a rockspec or rock on re-upload and increments a revision counter
  (`do_rockspec_upload`, `do_rock_upload`); here a rockspec upload for an existing or retired
  version answers `409`, whatever its bytes, and so does a rock for an arch the version already
  has. The client's own `check_rockspec` answer stops a plain re-upload before it is sent
  ("Revision 1.2-1 already exists on the server", captured on both); `--force` sends it and gets
  the `409` (captured wording printed on the LuaSocket path). `check_rockspec` reports a retired
  version as existing, so the client stops before sending.
- **A proxied repository creates no snapshots**: arrival and revalidation are cache
  materialisation.

Two concurrent uploads of different packages, or different versions of one, each
read-modify-write the record set through the revision-token retry and both land; two concurrent
rockspec uploads of the same version produce one success and one `409`.

### Removes are bindings

Per the cross-format precedent (`pypi.md`, `npm.md`, `cargo.md`, `conan.md`, `chef.md`), each is an
operation of the registry-owned management API, `docs/internal/plans/foundation/management-api.md`
(to be authored in the spec loop). LuaRocks has no HTTP client binding for any of them:

| Operation | Effect a client sees | Action |
|---|---|---|
| Remove a version | The version leaves every manifest; its files answer `404`; it enters the retirement set | `delete` |
| Remove a package | Every version leaves every manifest and enters the retirement set; the `Package` row stays | `delete` |
| Remove one rock of a version | That arch leaves the version's entry; the rockspec and other rocks stay; the arch may be uploaded again only if the version is not retired | `delete` |

Rules, applying the precedent rather than re-deciding it: each operation is one completed logical
write, exactly one snapshot, none for a refused one, and no blob-store object deleted directly
(`storage-and-gc.md` AC15); authorization is the settled `(repository, action)` vocabulary with no
new action; hosted only, a proxied or virtual repository answering `405`; a removal of something
absent answers `404`; removing a package's last version leaves the `Package` row and its
retirement set (`data-model.md` AC33). What this format requires of `management-api.md`: the
three operations on the object `{name}`, the version and arch as arguments where they apply, the
retirement set carried forward by every later write and preserved across a backwards repoint.

### Last-Modified, rollback and promotion

Per the resolved `Last-Modified` decision below, every rendering served through a pointer carries
**`Last-Modified` equal to that pointer's change time**: the moment it last moved, by a write
advancing it or by a promotion or rollback repointing it, recorded at one-second resolution and
**strictly greater than the previous value**, so two writes inside one second still produce two
distinct values. `If-Modified-Since` at or after it answers `304`; anything earlier answers `200`.
Every rendering also carries a strong `ETag` over its bytes, which no pinned client sends but a
stand-in upstream or a proxy in front of this one can use. Files carry the `Last-Modified` of the
write that created them and an `ETag` over their bytes, since a coordinate's bytes never change.

What this buys, per the captures: a rollback restores the record set with the snapshot
(`data-model.md` AC13), the pointer's change time moves forward, the client's
`If-Modified-Since` from the newer manifest is earlier than it, so the client receives the
restored manifest and the next `luarocks install {name}` installs the restored version (the
captured downgrade), where a `Last-Modified` taken from the restored content would have been
answered `304` and hidden it (captured). A promotion serves the source's records with the target
pointer's own change time. The accepted cost is that a pointer's `Last-Modified` changes on every
write to the repository, including writes that change nothing a given Lua version's manifest
lists, so a client refetches a byte-identical manifest now and then; the zip form is small
(126 KB for luarocks.org's `manifest-5.4.zip`).

**The proxied analogue**: when an upstream removes its newest version, the next revalidation drops
it from the proxied record set (the removal table below), and a client's next install resolves the
previous version, exactly as it would against the upstream directly.

### Development versions

A version whose name begins `scm-`, `cvs-`, `svn-`, `git-` or `dev-` (case-insensitively,
luarocks-site's `version_name_is_development`) is a development version, and per the resolved
development-split decision below it appears **only in the `/dev/` manifests**, with its files
served under `{base}/dev/` as well as `{base}/`. The reason is ordering: LuaRocks ranks `dev` and
`scm` above every number (`core/vers.lua` gives them deltas of 120,000,000 and 110,000,000), so
a root manifest listing `scm-1` would make every plain `luarocks install` pick it over the newest
release. `luarocks install --dev --server={base}` reads `{base}/dev/` (captured).

### Rockspec-only versions

Per the resolved rockspec-only decision below, a rockspec-only version is served by default, as
luarocks.org serves 5,638 of them, and the operator documentation states that installing one
fetches its `source.url` from the author's host, outside the registry's cache, policy and offline
mode (`proxy-cache.md`'s single offline switch cannot cover a host the client contacts directly).
A repository may set `require source rocks`, stored in its repository-level document: served
manifests then omit every version with no rock, so a resolver picks the newest version that has
one, or finds nothing. Development versions are rockspec-only by construction, so the option
empties the `/dev/` manifests, which the operator documentation says.

### Content negotiation and the other traps

- **The encoding is in the path**, never negotiated: `.zip`, `.json` or none. Every rendering is
  served `200` with `Content-Type` `application/zip`, `application/json` or `text/x-lua`, rocks as
  `application/x-rock`, rockspecs as `text/x-rockspec` and signatures as `application/pgp-signature`,
  gzip-encoded where the client accepts it (wget sends `Accept-Encoding: identity` and curl sends
  none, captured, so in practice never). No client reads `Content-Type`.
- **`HEAD`** answers every `GET` route with the same headers, because 3.13.0's LuaSocket
  downloader revalidates a cached file with `HEAD` and compares `Last-Modified` exactly
  (`fs/lua.lua`, `http_request`), and luarocks.org answers it.
- **Names in paths are lowercase.** A request for a mixed-case file name answers `404`, as
  luarocks.org's does, because the client only ever builds lowercase names.
- **The unversioned `manifest`** is served in all three encodings for tools and humans although
  no pinned client requests it.
- **The file routes are served, never redirected**, because every client follows the URL it
  built and a handler never opens storage directly.

### Authentication: a key in the path for uploads, Basic for reads

The client table in `auth.md` has no LuaRocks row, and what `luarocks upload` sends is none of the
verifier's four presentation forms. This section reconciles both surfaces explicitly, per the
resolved decisions below, and every check runs in the shared authentication layer.

**Uploads: a registry token as the `{key}` path segment.** Both clients put the key in the URL,
`{server}/api/1/{key}/{route}` (captured; `raw_method`), and nowhere else; the unreleased client
keeps it there and adds only a two-factor header. So, per the resolved upload-credential decision
below, **the central verifier accepts a registry token as the path segment after `api/1/` on this
format's upload routes only**, resolving to the same principal and scopes as the other forms. What
follows from a credential in a path, named rather than discovered:

- **Redaction covers the path.** The segment is credential material for `auth.md` AC7's scan and
  for the harness's redaction (`conformance-harness.md` AC13), in access logs, traces, metrics
  labels and error bodies.
- **Plaintext is refused before lookup.** Without LuaSec, 3.13.0's LuaSocket path rewrites an
  `https://` upload server to `http://` and sends the key in the clear after printing only
  "LuaSec is not available; using plain HTTP" (captured). The registry refuses a key-bearing path
  over a connection it did not terminate with TLS, identically for a valid and an invalid key,
  without looking it up, as `auth.md` AC27 requires of the other forms; the operator documentation
  tells users to install LuaSec or rely on 3.13.0's default curl path, which keeps `https`.
- **The client echoes it.** A failed status call on the wget path printed
  "failed downloading http://.../api/1/badkey/status" (captured), and `--api-key` stores the key in
  plaintext in `~/.luarocks/upload_config.lua` (captured). The documented CI recipe is therefore
  `--temp-key`, which neither stores the key nor calls `status` (captured).
- **Error bodies**: an unknown, expired or revoked token answers `401` with
  `{"errors": ["Invalid key"]}`, which 3.8.0 prints with its "(use the --api-key flag to change)"
  hint and the LuaSocket path as "Server error: Invalid key" (captured); never `403`, since the
  caller did not authenticate.
- `api/tool_version` answers the constant `{"version": "1.0.0"}` and is authorized as a read of
  the repository with no object: on a private repository a credential-less call is challenged and
  the client ignores the failure (captured).

**Reads: a registry token as the Basic password, after a challenge.** No LuaRocks configuration
sends a credential by itself except URL userinfo through curl or LuaSocket: wget, the default
downloader in both images, sends Basic only after a `401` carrying `WWW-Authenticate: Basic`, and
then on every request, taking the credential from userinfo in the server URL or from `~/.netrc`
(both captured on both clients); curl sends userinfo preemptively and ignores `.netrc` (captured).
The userinfo reaches every URL, because file URLs are built from the server URL. So the existing
Basic form suffices, and the challenge must carry `WWW-Authenticate: Basic realm="..."`, or wget
never sends anything. The documented recipe is `~/.netrc` with wget, because a token in userinfo
is printed by `luarocks search` beside every result and in every "Failed downloading" warning
(captured).

**The challenge and the existence rule**, applying `auth.md` as written:

- A credential-less request to a repository that is not anonymously readable answers `401` with
  the Basic challenge and `{"errors": [...]}`, byte-identical for a private and a missing
  repository (`auth.md` AC17).
- A rejected token answers `401` and is never served as anonymous (`auth.md` AC12).
- A valid credential lacking `pull` answers `404` (the existence rule). On the manifest, the
  client warns and resolves from its next server group; with this registry as its only server it
  prints "No results matching query were found" (captured for a `404`).
- An upload needs `push`; `check_rockspec` and `status` are authorized as `push` so that neither
  is an existence oracle for a `pull`-only credential.

### Addressed objects and pattern scopes

`auth.md`'s pattern scopes narrow a credential within one repository by matching the object each
request addresses, and the format declares which object each route reports
(`format-handler-interface.md` AC12). Per the resolved addressed-object decision below, the
canonical object is the **lowercased package name**:

| Route | Action | Object kind | Canonical object |
|---|---|---|---|
| Every manifest, in every scope, Lua version and encoding | `pull` | none | - (enumerates every name) |
| `{name}-{version}.rockspec`, `.{arch}.rock`, `.asc`, under `{base}/` or `{base}/dev/` | `pull` | named | `{name}` |
| Proxied `/manifests/{ns}/...` manifests / files | `pull` | none / named | - / `{ns}/{name}` |
| `api/tool_version` | `pull` | none | - |
| `api/1/{key}/status` | `push` | none | - |
| `api/1/{key}/check_rockspec` | `push` | named | the `package` query parameter, lowercased |
| `api/1/{key}/upload` | `push` | named | the name component of the `rockspec_file` part's filename, read before the rockspec bytes; the static reading must agree or the upload is refused `400` |
| `api/1/{key}/upload_rock/{id}` | `push` | named | the name component of the `rock_file` part's filename, read before the rock bytes; the version `{id}` names must belong to that package or the upload is refused `400` |

The part filename is the client's (`cmd/upload.lua` sends the rockspec under its own file name,
which the client's rockspec loader has already required to be `{name}-{version}.rockspec`, and the
packed rock under `{name}-{version}.src.rock`; both captured). A part whose filename does not have
that shape, including the literal `rockspec` the loader also allows, makes `Scope(r)` return an
error, which denies the request as an unauthorized one.

What that gives and costs, applying `auth.md`'s rules rather than re-deciding them:

- **A patterned `pull` cannot resolve anything**, because resolution starts at a manifest, whose
  object is none (the same consequence `cargo.md`, `conan.md` and `chef.md` accepted). A patterned
  `pull` reads in-pattern files through `curl`.
- **A patterned `push` uploads under `--temp-key`**, which skips `status`; under `--api-key` the
  `status` call, whose object is none, is refused and the upload stops. The working recipe is
  `--temp-key` with `push` patterned `acme-*`.
- **A pattern refusal is answered as absence**: `404` with `{"errors": ["Not found"]}` on every
  route, indistinguishable from a package that does not exist, so a pattern is never an oracle
  over names outside it.

### Policy refusals on the wire

When a shared resolution call returns the typed refusal `supply-chain-policy.md` defines, on a
rock, rockspec or signature of either path, the handler answers `403` with
`{"errors": ["{policy and rule, or the signal}"]}` as `application/json`. `403` rather than the
existence rule's `404`, because the caller is authorized and the content is what is refused.
Per the resolved policy-refusal decision below, **manifests keep listing a refused version**,
so a resolver that selects it reaches the refusal and halts (captured: with a second server group
holding the same version, the install failed and the second server received no request for that
file), rather than silently taking a lower version or another server's copy; the no-elision
precedent of `conda.md`, `debian.md`, `conan.md` and `chef.md`. What the user sees is generic, since
no download path shows a body ("Could not fetch rock file ... failed downloading", captured); the
operator documentation says so. A policy refusal at upload (a byte-dependent rule on the rock)
uses the same body, which the LuaSocket path prints and 3.13.0's curl path reduces to
"API failure: /upload" (captured).

### Signing, provenance and policy

No rocks server signs anything. An uploader may sign with `luarocks upload --sign`, which sends
detached OpenPGP signatures as `rockspec_sig` and `rock_sig` (`cmd/upload.lua`); the registry
stores them as `.asc` files beside what they sign and serves them for `luarocks install --verify`
(AC28). The registry does not verify them in v1, since the client verifies against its own
keyring and nothing in the ecosystem binds a key to a package; where an operator configures
trusted keys, `docs/internal/plans/foundation/artifact-verification.md` (to be authored in the
spec loop) is the place a verdict would come from: what this format needs of it is a detached
OpenPGP signature over the exact file bytes, keys configured per repository, and a verdict per
file, with no LuaRocks-specific logic.

**Advisory coverage is absent.** OSV has no LuaRocks ecosystem (Context), so the policy engine's
coordinate-level matching finds nothing for a LuaRocks coordinate, an advisory-dependent rule
attached to a LuaRocks repository is refused at configuration as `supply-chain-policy.md` AC11
requires, and the feed channel of the shared security-signal rule never condemns one: the
incident's three malicious packages have no advisory (`pkg:luarocks/bcrcewon` returns `{}`). What
remains is the byte-level cataloguer, which sees Lua source, C source and vendored files inside a
rock's zip, and licence rules, which depend on its coverage and are refused at configuration where
it has none; the consequence is listed for `supply-chain-policy.md`.

### The proxied path

The handler owns the request and classifies for the proxy layer's fetch-and-cache API per the
settled decisions in `proxy-cache.md`. The upstream is a rocks-server base URL
(`https://luarocks.org`, a static rocks server, or another registry), validated at configuration by
fetching `manifest-5.4.zip` or `manifest-5.1.zip` and requiring a manifest the reader accepts. An
upstream credential, where one is needed, is presented by the adapter, and the client's credential
is never forwarded.

| Route | Classification |
|---|---|
| Manifests, root, `/dev/` and `/manifests/{ns}/`, per Lua version | Mutable metadata with a TTL, revalidated with `If-Modified-Since` (luarocks.org answers `304`, captured). The adapter fetches the upstream's `.json` where it serves one and otherwise its zip or Lua form; the handler parses it into records and the shared service regenerates every encoding from them. **Upstream manifest bytes are never served** |
| Rockspec, rock, `.asc` | Immutable by coordinate here: fetched once, verified before commit (below), pinned, cached indefinitely |
| Upload API | `405` |

**Parsing an upstream manifest** uses the same reader as a rockspec with a stricter rule: the
chunk is exactly the top-level assignments of `repository`, `modules` and `commands` to table
constructors of string keys, string values and nested constructors, with no locals, calls,
operators or other statements, and not bytecode; a JSON manifest is parsed as JSON. Anything else
is an integrity failure: the previous records keep serving under `proxy-cache.md`'s serve-stale
rules, and the operator is alerted. So the captured bytecode manifest is never delivered to a
3.8.0 client through this registry (AC21), and neither is anything an upstream could embed in Lua.
Entries whose name, version or arch fail the manifest string grammar are left out with a
divergence recorded.

**Verification before commit.** No manifest carries a digest, and luarocks.org replaces files in
place on re-upload (its rock upload handler increments the rock's revision), so the fetch uses the
completion-only mode with a handler-supplied verifier (Blocking preconditions): for a rock, the
zip hygiene and embedded-rockspec identity of "What the registry verifies" items 2 and 3 against
the coordinate the manifest listed; for a rockspec, that the static reading, where it succeeds,
names the coordinate. A rockspec the static rule cannot read is committed on the coordinate alone,
because the client refuses one whose evaluated contents disagree with its file name
(the same loader check); the divergence is recorded, and the ingest rule is not weakened.
Nothing is committed unless it passes; the initiating client's connection is aborted before its
final bytes on a failure, and coalesced waiters receive bytes only from the CAS after the verified
commit, as the settled waiter rule requires. **The first verified fetch pins the coordinate**: its
CAS digest is recorded on the `File`, and a refetch after eviction producing a different digest is
an integrity failure, so one coordinate serves one set of bytes for its life here although the
upstream promises nothing. The upstream's `ETag` equals the file's MD5 on luarocks.org (captured)
and is not relied on. What this cannot catch is a tamper that keeps name and version on first
fetch, which is stated as the ecosystem's limit.

- **Missing files are negatively cached** with the short TTL; a `429` or `5xx` is never cached as
  absence (`proxy-cache.md` AC9).
- **The upstream manifests are large**: 4 MB of Lua or 1.6 MB of JSON per Lua version on
  luarocks.org, fetched only when the TTL has lapsed, usually answered `304`, and stored as
  CAS-backed metadata.

Upstream removal maps onto the settled purge-or-flag table as LuaRocks' side of that contract:

| Upstream event, as observed at revalidation | Classification |
|---|---|
| A new version or arch, or a changed `lua` constraint | An **ordinary metadata change**, propagated at the next revalidation |
| A version or package vanishes from the upstream manifest | Drop it from the proxied record set; keep serving cached files to a request for that coordinate; record an operator-visible divergence. The wire carries no reason |
| A file answers `404` where it was listed | Keep serving the cached copy by coordinate; record a divergence |
| A refetched file's digest differs from the pinned one, or it fails verification | An **integrity failure at fetch**: never committed, the pinned copy keeps serving if cached, and the operator is alerted |

Detection happens at revalidation, passively, per `proxy-cache.md`'s resolved passive-detection
decision (was Q12). **No row is an explicit security signal**: luarocks.org removed the incident's
malicious packages without any marker on the wire, and OSV carries nothing for them, so a cache
that held one would drop it from every manifest (no new resolution selects it) and keep serving
its exact file to a request naming it, with a divergence raised for the operator. That is the
shared security-signal rule applied as written, stated here as this ecosystem's coverage gap
rather than patched per format.

### Virtual repositories

A virtual repository of format `luarocks` is possible: no manifest is signed, names a repository
or carries a URL, and files resolve relative to the server URL the client was given. Per the
resolved virtual-repository decision below, resolution is **per package name, in member order**:

- **Each manifest lists, for each name, the entries of the first member holding that name**, and
  nothing from later members under that name, whatever versions they hold. A hosted member placed
  before a luarocks.org remote therefore shadows the upstream's package of the same name entirely,
  so the captured confusion (a higher version on another server winning the union) cannot occur
  for a client whose only rocks server is the virtual repository.
- **Files resolve in the member that supplied the name**, so a rock never comes from a different
  member than the manifest entry that led to it.
- `/dev/` manifests merge the same way; `/manifests/{ns}/` resolves in the first remote member
  that serves the namespace.
- A virtual repository creates no snapshots; its record set is re-merged by the shared service
  when a member's changes, and the upload API answers `405`.

The accepted cost: a private package shadows every upstream version of its name, so a team that
wants both must rename; the operator documentation says so beside the recipe
(`rocks_servers = { "https://{host}/luarocks/{virtual}" }`).

### Conformance, the clients and the corpus

Two clients on two Lua versions, from the pinned images: LuaRocks 3.13.0 on Lua 5.4 and 3.8.0 on
Lua 5.1, each through wget (default), curl (wget absent) and, for uploads, LuaSocket (the 3.8.0
image needs `lua-cjson` and LuaSocket to upload at all), plus 3.13.0 on LuaJIT for the `.json`
manifest. No official image exists for either version, so the harness builds them from the pinned
bases and the pinned source tarball or Debian package version, and pins the resulting digests in
the case. The catalogue counts one ecosystem and no multiplier row.

Five assertion traps are recorded where the cases are written. **The ten-second window hides the
server**: a manifest fetched within 10 seconds is reused with no request, so a case that changes
server state between two client runs waits 11 seconds or asserts the absence of a request.
**3.13.0 as root keeps no cache** unless `/var/cache/luarocks` exists, so a revalidation
case creates it before the first run. **The exit code hides fall-through**: resolution succeeds from another server
group after this registry refused, so a refusal case configures this registry as the only server
(`--only-server`) or asserts at the network layer. **An install removes other versions of the
package**, so a case asserting what is installed reads `luarocks list`, not the exit code. **3.13.0
crashes inside a mirror group** on any download failure, so no case puts this registry in a mirror
group with another server; the operator documentation forbids that configuration anyway.

The recorded surface for the replay corpus, named now because a thin recording script yields a
thin specification: against luarocks.org, a cold install of a package with a src rock, of a
rockspec-only package, a `--dev` install, a namespaced install, a search, a conditional manifest
fetch, a `.json` manifest fetch, a missing file and a missing version; against the reference
(`luarocks-admin make-manifest` over a directory served statically, and luarocks-site run from its
repository's `Dockerfile` with a user and key seeded), an upload with and without `--sign`, a
duplicate upload with `--force`, and an invalid key. Recording gates on the harness's redaction
criterion (`conformance-harness.md` AC13); the `/api/1/{key}/` path segment, `Authorization`
values and URL userinfo are what the allowlist must name. Every deliberate divergence from the
reference goes on the recorded exception list before its flow is expected to replay: rockspecs
refused by the static reading rule, `409` for re-uploads and retired versions, the development
split on hosted repositories built by `make-manifest` (which does not split), the `.zip` and
`.json` forms a static server built by `make-manifest` lacks, pointer-derived `Last-Modified`,
and the JSON error bodies on file routes where a static server sends HTML.

`Capabilities()` declares proxy support and the reference implementation `available`
(`format-handler-interface.md` AC13), the implementations being `make-manifest` over a static
server for reads and luarocks-site for uploads.

## Open Questions

None open. The fourteen questions this draft raised were each written in the template's decision
shape and then adopted at their own recommendation under the owner's standing delegation of
2026-09-26, so the loop can continue; each is recorded below as adopted rather than decided,
folded through Scope, Design, the criteria and the Test Plan in the same pass, and reversible by

### Resolved: how an uploaded rockspec is read (was Q1)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: a Lua lexer and parser
build a syntax tree that is never executed, and a constant folder over literals, `..` and
constant top-level locals reads `package`, `version` and `dependencies`, which may be assigned
only once at top level and read anywhere; everything else is refused (Design, "Reading an
uploaded rockspec"; AC4, AC6).

The question: a rockspec is a Lua program, the metadata the registry needs is the value of three
globals after it runs, and the upstream's server was compromised by running it (the incident).

**Recommendation:** A. It needs no interpreter in the process, so no sandbox exists to escape; it
is exact, because in the client's library-less environment only an assignment to the identifier
can change those fields; and it accepts 388 of 400 sampled real rockspecs.

| Option | You get | It costs |
|---|---|---|
| **A. Parse and constant-fold, never execute** | No Lua runs server-side; the reading equals the client's; 97 percent of sampled rockspecs accepted | About 2.5 percent of real rockspecs (string-method versions) refused on hosted upload, a divergence from luarocks.org |
| **B. Evaluate in an embedded, memory-safe interpreter with instruction limits** | Every rockspec luarocks.org accepts | A sandbox is exactly the surface the incident exploited; the constitution's rule for this format is never to evaluate uploaded Lua |
| **C. Literal assignments only** | The simplest reader | 30 percent of sampled rockspecs refused, including every generated nvim rockspec |

**Why this is yours:** it refuses some real-world uploads to keep a security property.

Accepted cost: the refused idioms, their error message, and the exception-list entry.

### Resolved: how manifests are generated and stored (was Q2)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: the shared service stores
one URL-free record set per repository, regenerated inside each write, and renders the 36
documents from it on request, deterministically, memoised by record-set digest (Design,
"Generating the manifests"; AC2, AC3, AC20).

The question: a repository serves two scopes, six Lua selections and three encodings, each
repository-wide; they could be generated in every write, rendered from version records on every
request, or rendered from one stored record set.

**Recommendation:** A. One aggregation per write, no write amplification across 36 documents, and
a rendering is a pure function that can always be recomputed, so a cache miss costs time and
never correctness.

| Option | You get | It costs |
|---|---|---|
| **A. Stored record set, renderings on request, memoised** | One stored document per write; renderings byte-stable and disposable | A first request per snapshot pays a render (and a deflate for zip) |
| **B. All 36 documents generated in each write** | Pure stream copy on serve | 36 CAS-backed documents per upload in a luarocks.org-sized repository, most never requested |
| **C. Rendered on request from version records** | No stored document | O(repository) reads per manifest request, and no share in the write-triggered service CRAN, Helm, Debian and Chef share |

**Why this is yours:** it fixes the split of work between the shared service and the handler for
this format's index.

Accepted cost: the render on first request and the memo's bound.

### Resolved: Last-Modified and rollback (was Q3)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: `Last-Modified` is the
serving pointer's change time, strictly increasing at one-second resolution across writes and
repoints, with standard `If-Modified-Since` handling (Design, "Last-Modified, rollback and
promotion"; AC14, AC15).

The question: the client revalidates with `If-Modified-Since` and keeps its copy on `304`
(captured), so a rollback served with the restored content's older time is invisible to it
(captured), while two writes inside one second share a time.

**Recommendation:** A. It makes every pointer change visible to a revalidating client with the
revalidation the client already performs.

| Option | You get | It costs |
|---|---|---|
| **A. Pointer change time, strictly increasing** | Rollbacks and same-second writes reach caching clients; `304` still saves bandwidth | A `data-model.md` revision; an occasional refetch of an unchanged Lua version's manifest |
| **B. The content's write time** | Nothing new in the model | Rollbacks hidden behind `304` (captured), same-second writes lost |
| **C. Never answer `304`** | Always correct | Every client invocation downloads the manifest in full |

**Why this is yours:** it adds a field to the shared model for a client behaviour.

Accepted cost: the `data-model.md` revision, compatible with `conan.md`'s.

### Resolved: how an upload is authenticated (was Q4)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: the central verifier
accepts a registry token as the `{key}` path segment of this format's upload routes, with the
segment redacted everywhere and plaintext refused before lookup (Design, "Authentication"; AC8,
AC9).

The question: `luarocks upload` carries its credential only as a URL path segment (captured on
both clients and in the unreleased client), which none of `auth.md`'s four presentation forms is.

**Recommendation:** A. It serves the ecosystem's publish command unchanged, so trigger and effect
stay oracle-testable, and the costs of a credential in a path are bounded by redaction and the TLS
rule the other forms already obey.

| Option | You get | It costs |
|---|---|---|
| **A. Token as the path segment, upload routes only** | `luarocks upload` works on both clients | A fifth presentation form in `auth.md`; path redaction in logs, traces and the corpus |
| **B. Upload only through the management API** | No new form | The ecosystem's publish command fails here, and every team needs a bespoke upload step |
| **C. Also accept luarocks-site's `/api/1/bearer/` with `Authorization: Bearer`** | A header form for future clients | A route no released or unreleased client sends, with no oracle |

**Why this is yours:** it admits a credential in a URL into the security foundation.

Accepted cost: the `auth.md` revision and the redaction scope.

### Resolved: what an upload writes (was Q5)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: the rockspec upload and
each rock upload are separate writes; a version's rockspec and each rock are immutable, `409` on
re-upload with or without `--force`; a removed version is retired (Design, "The publish path";
AC5, AC7).

**Recommendation:** A. A rockspec-only version is legitimate, so the two requests cannot be one
write, and luarocks.org's in-place replacement (captured in its source) is exactly what makes a
coordinate untrustworthy; retirement keeps a removed coordinate from returning with other bytes.

| Option | You get | It costs |
|---|---|---|
| **A. Two writes; immutable rockspec and rocks; retirement** | One set of bytes per coordinate for the repository's life | A window in which a version is rockspec-only; `--force` workflows fail, on the exception list |
| **B. luarocks.org's behaviour: replace on re-upload** | Replay-faithful | A coordinate changes bytes under clients that cached it |
| **C. Hold the rockspec invisible until a rock arrives** | No rockspec-only window | Breaks `--skip-pack` and every development version, which never gets a rock |

**Why this is yours:** it diverges from the reference server to keep a cross-format guarantee.

Accepted cost: the window, the divergence and its operator note.

### Resolved: rockspec-only versions (was Q6)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: served by default, with a
per-repository `require source rocks` option that omits them from served manifests (Design,
"Rockspec-only versions"; AC18).

The question: installing a rockspec-only version fetches its source from the author's host
(captured, live), outside the registry's cache, policy and offline mode; 5,638 of luarocks.org's
versions are rockspec-only.

**Recommendation:** A. Serving them matches what users expect of a luarocks.org cache, and the
option gives an air-gapped or policy-strict repository a guarantee that every install is satisfied
from the registry.

| Option | You get | It costs |
|---|---|---|
| **A. Serve; opt-in omission** | Default parity with luarocks.org; a strict mode where it matters | One repository option; the operator note on what the default lets through |
| **B. Always serve** | No option | No way to keep installs inside the registry |
| **C. Never serve** | Every install satisfied from the registry | A sixth of luarocks.org, and every development version, unavailable |

**Why this is yours:** it trades ecosystem coverage against a containment guarantee.

Accepted cost: the option and its documentation.

### Resolved: development versions (was Q7)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: development versions
appear only in the `/dev/` manifests, as luarocks.org does (Design, "Development versions"; AC17).

**Recommendation:** A. LuaRocks ranks `scm` and `dev` above every release (`core/vers.lua`), so
listing them in the root manifest makes plain installs pick them.

| Option | You get | It costs |
|---|---|---|
| **A. `/dev/` only** | Plain installs pick releases; `--dev` works as against luarocks.org | A static `make-manifest` server does not split, on the exception list |
| **B. One manifest** | `make-manifest` parity | Every package with an `scm` version installs it by default |

**Why this is yours:** it diverges from the reference tool to follow the reference server.

Accepted cost: the exception-list entry.

### Resolved: namespaces (was Q8)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: proxied repositories serve
an upstream's `/manifests/{ns}/` tree with `{ns}/{name}` as the package identity; hosted
repositories answer `404` there (Scope; Design, "Mapping onto the shared model"; AC16, AC25).

**Recommendation:** A. Namespaced installs are how luarocks.org users pin an author, so a cache
must serve them, while a hosted repository has no per-user name ownership to express and its
virtual shadowing already pins names registry-side.

| Option | You get | It costs |
|---|---|---|
| **A. Proxied only** | Author-pinned installs through the cache | A second identity shape in the addressed object for proxied content |
| **B. Neither path** | One identity shape | `luarocks install user/name` fails through the cache |
| **C. Both paths, namespace per principal** | Hosted author pinning | A per-user name ownership model the registry does not have |

**Why this is yours:** it decides whether a hosted repository models upstream accounts.

Accepted cost: the proxied-only identity shape.

### Resolved: virtual repositories (was Q9)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: per-name resolution, the
first member holding a name supplying all of that name's entries (Design, "Virtual
repositories"; AC26).

The question: nothing binds a manifest to a repository, so a merge is expressible; the rule
matters because the client's own union takes the highest version across servers (captured).

**Recommendation:** A. Member order is `data-model.md`'s resolution rule, and per-name shadowing is
the defence against the captured confusion.

| Option | You get | It costs |
|---|---|---|
| **A. Per name, first member wins** | Private names cannot be overridden by upstream versions | A private package hides every upstream version of its name |
| **B. Per version, union of all members** | Every version of every member visible | Reproduces the client's confusion inside the registry |
| **C. No virtual repositories** | Nothing to specify | Users configure several servers and the client's union decides for them |

**Why this is yours:** it sets the precedence between private and public content.

Accepted cost: the documented shadowing.

### Resolved: the addressed object, and what a pattern refusal looks like (was Q10)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: every file and upload
route reports the lowercased package name (the upload routes from the part filename), manifests
and `status` none, and a pattern refusal answers `404` (Design, "Addressed objects and pattern
scopes"; AC10).

**Recommendation:** A. It applies `auth.md` as written, as `cargo.md`, `conan.md` and `chef.md`
did; the usable recipe narrows what CI may upload; and `404` keeps a pattern from being an oracle.

| Option | You get | It costs |
|---|---|---|
| **A. Name object; manifests none; refusal `404`** | No new object kind; no oracle; upload narrowing works under `--temp-key` | A patterned-only `pull` cannot resolve; patterned `push` fails under `--api-key` |
| **B. Exempt manifests from the pattern rule** | Patterned `pull` resolves | A manifest enumerates every name, the leak the none rule exists to stop |
| **C. Pattern refusal as `403`** | Distinguishable refusals | An oracle over names outside the pattern |

**Why this is yours:** it accepts client-wide limitations rather than bending a security rule you
settled.

Accepted cost: the documented recipe and limitations.

### Resolved: how a policy refusal is rendered (was Q11)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: `403` with
`{"errors": [...]}` on files and uploads, and no elision from any manifest (Design, "Policy
refusals on the wire"; AC11).

**Recommendation:** A. A refused file halts the install even with another server group holding the
version (captured), and listing the refused version is what makes the resolver reach the refusal.

| Option | You get | It costs |
|---|---|---|
| **A. `403`, listed in manifests** | The refusal holds whatever servers the user configured | No download path shows the reason |
| **B. Elide refused versions** | Resolvers pick an allowed version silently | The client takes the refused version from any other server group, and nobody learns why |
| **C. `404`** | Consistent with absence | Still halts on a file, but reads as a missing file |

**Why this is yours:** it trades user-visible explanation against whether a refusal holds.

Accepted cost: the operator documentation explaining the generic message.

### Resolved: how a proxied file is verified (was Q12)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: completion-only
verification of zip hygiene and embedded-rockspec identity, the static reading of a rockspec where
it succeeds, and the first verified digest pinned on the coordinate (Design, "The proxied path";
AC23).

**Recommendation:** A. With no upstream digest and in-place replacement upstream, these are the
only bindings available, and the pin makes the coordinate immutable here from the first fetch.

| Option | You get | It costs |
|---|---|---|
| **A. Identity verified; first digest pinned** | The captured swap is never delivered; later upstream replacement is detected | A tamper that keeps name and version passes the first fetch |
| **B. Serve upstream bytes unverified** | Nothing to build | The registry repeats the client's blindness |
| **C. Refuse to proxy an ecosystem without digests** | No trust on first use | No luarocks.org cache |

**Why this is yours:** it accepts trust on first use where the ecosystem offers nothing stronger.

Accepted cost: the stated first-fetch limit.

### Resolved: upstream Lua manifests (was Q13)

**Adopted 2026-09-26 under the owner's standing delegation.** Option A: the adapter prefers an
upstream's JSON manifest; a Lua manifest is parsed under the strict literal rule; the shared
service regenerates every served encoding, and upstream manifest bytes never reach a client
(Design, "The proxied path"; AC21).

**Recommendation:** A. It keeps the constitution's rule on both paths: every byte of Lua a client
executes through this registry was written by the registry's serializer.

| Option | You get | It costs |
|---|---|---|
| **A. Parse and regenerate; prefer JSON** | A compromised upstream cannot push bytecode or code to 3.8.0 clients through the cache | A parse and a render per revalidation |
| **B. Relay upstream bytes after a check** | Byte-identical upstream manifests | A check that must understand everything the client's loader accepts, bytecode included |

**Why this is yours:** it decides whether the cache is a transparent relay or a regenerating one.

Accepted cost: the per-revalidation work.

**Recommendation:** B, for sequencing: LuaRocks is Tier 3 and built only if the breadth gate says

| Option | You get | It costs |

| **B. User-configured in v1, revisited at the verdict** | No sibling amendment | No nightly run against the real luarocks.org until then |
